# 시스템 구성

## 전체 구조

ProtView는 같은 컴퓨터 안에서 도는 두 프로세스와, 필요할 때만 띄우는 격리된 작업 프로세스로 이루어진다.

```
브라우저 (127.0.0.1:3000)
  └─ Next.js 15 프런트엔드 (frontend/)
       ├─ Mol* 5.11.0 뷰어 — 구조 바이트를 로컬 API에서 받아 WebGL로 렌더링
       └─ /api 요청을 로컬 백엔드 8000번으로 전달
            │ HTTP (loopback)
            ▼
FastAPI 백엔드 (backend/mw/api/app.py, 127.0.0.1:8000)
  ├─ Run.call 실행 경로 (runtime/orchestrator.py) ─ 도구 레지스트리 (tools/, config/tools.yaml)
  ├─ ObjectStore + EventLog (core/) ─ runs/<run_id>/ 아래 불변 객체·이벤트·SQLite 색인
  ├─ 참조 스냅샷 읽기 (reference_snapshots.py) ─ .deps/reference/ (MW_REFERENCE_DIR, 읽기 전용)
  │     └─ 쓰는 쪽: scripts/import_reference_snapshots.py ← ../kbase_kinase/ref (사용자가 실행, 서버는 kbase를 읽지 않음)
  ├─ 반응 참조 스냅샷 읽기 (reaction_snapshots.py) ─ .deps/reaction_reference/ (MW_REACTION_REFERENCE_DIR, 읽기 전용)
  │     └─ 쓰는 쪽: scripts/import_reaction_references.py ← HTTPS GET만: www.ebi.ac.uk(M-CSA)·rest.uniprot.org·www.rhea-db.org
  │          (사용자가 터미널에서 실행, mw를 import하지 않음. 서버·도구·작업은 이 명령을 부르지 않음)
  ├─ 전례 참조 스냅샷 읽기 (precedent_snapshots.py) ─ .deps/precedent_reference/ (MW_PRECEDENT_REFERENCE_DIR, 읽기 전용)
  │     └─ 쓰는 쪽: scripts/import_precedent_snapshots.py ← ../kbase_kinase의 dist/ 세 파일·ref/pubmed 최신 서지
  │          (사용자가 실행, 네트워크 없음: 로컬 파일과 읽기 전용 git만. mw를 import하지 않음, 서버는 kbase를 읽지 않음)
  ├─ JobQueue + guardian (jobs/) ─ POSIX 프로세스 그룹으로 작업 프로세스 감독
  │     ├─ OpenMM 작업 프로세스 (프로젝트 .venv 인터프리터)
  │     ├─ ProLIF 작업 프로세스 (.deps/prolif/venv-locked 별도 인터프리터)
  │     ├─ RDKit 리간드 작업 프로세스 (M17 ligand_worker.py, 같은 venv-locked 인터프리터)
  │     ├─ qvina 도킹 작업 프로세스 (M18 docking_worker.py, .deps/docking/venv-locked 별도 인터프리터,
  │     │    자식으로 .deps/qvina/env/bin/qvina2 고정 실행 파일)
  │     ├─ qvina 일괄 도킹 작업 프로세스 (M19 docking_batch_worker.py, 같은 인터프리터, docking_worker.py를
  │     │    파일 경로로 불러 행마다 같은 계산, 자식 qvina2)
  │     ├─ 변이 구조 모델링 작업 프로세스 (M21 openmm_mutation_worker.py, 프로젝트 .venv 인터프리터,
  │     │    PDBFixer를 import하는 두 모듈 중 하나, M7 openmm_worker.py의 방법 확인·mmCIF 쓰기를 바꾸지 않고 씀)
  │     ├─ 구조 보완 작업 프로세스 (M29 structure_repair_worker.py, 프로젝트 .venv 인터프리터, PDBFixer를 import하는
  │     │    다른 하나. 추가 원자 좌표만 만들어 돌려주고, 접합·검증·M7 사전 검사·게시는 서버가 함)
  │     ├─ 리간드 GA 작업 프로세스 (M22 ligand_ga_worker.py, .deps/docking/venv-locked 인터프리터,
  │     │    docking_worker.py를 파일 경로로 불러 개체마다 같은 계산, RDKit은 Morgan 지문에만, 자식 qvina2)
  │     ├─ 서열 GA 작업 프로세스 (M23 sequence_ga_worker.py, .deps/docking/venv-locked 인터프리터, 한 프로세스 그룹)
  │     │    ├─ 자식: 모델링 프로그램 sequence_model_worker.py ([<repo>/.venv/bin/python, "-I", 프로그램],
  │     │    │    M21 openmm_mutation_worker.py를 바꾸지 않고 불러 씀)
  │     │    └─ docking_worker.py(파일 경로)의 함수로 개체 변이 구조 도킹, 자식 qvina2
  │     └─ fpocket 작업 프로세스 (프로젝트 .venv, .deps/fpocket/env/bin/fpocket 고정 실행 파일)
  └─ EgressGate (egress/) ─ 외부 HTTP 출구 (예외는 위 반응 참조 가져오기 명령 하나, 결정 0034)
        └─ OpenRouter Decisions API (POST https://openrouter.ai/api/alpha/decisions)
           — 뷰어 의도·M3: 해당 run에서 온라인 모드를 명시적으로 켰을 때만 (VIEWER_GATE)
           — M24 과학 전송: 과학 전송 동의가 켜진 run에서 사람이 미리보기 본문을 승인했을 때만 (SCIENCE_GATE)
             (M25 루프 투영도 같은 라우트·같은 게이트로만, 승인 이벤트 앞의 루프 검사를 더 통과해야 함)
```

프런트엔드는 과학 값을 직접 계산하지 않는다. 화면의 모든 수치는 백엔드 handle을 읽어서 표시한다. 백엔드는 과학 계산의 유일한 실행자이고, 계산 경로는 동기 `Run.call`과 비동기 `JobQueue` 두 가지뿐이다.

M29 작업 모듈도 프로젝트 `.venv`에서 돌며 서버 쪽에서 가져오는 것은 의존성 없는 `structure_repair_constants.py`, `mutation_model_constants.METHOD_KEYS`, M7 `openmm_worker`의 방법 확인뿐이고, 결과는 추가 원자 목록과 엔진 버전을 담은 `result.json` 하나다(관측 원자는 돌려주지 않음). 서버 쪽 M29 모듈 11개는 PDBFixer·네트워크 모듈·`subprocess`를 import하지 않으며, 읽기 필드 모듈 `structure_origin_reads`가 import하는 것은 `mutation_handoff`·`structure_repair_constants`·`core.errors`·`structure_origin`(과 표준 라이브러리 `typing`)뿐이고, 이 모듈을 import하는 모듈은 `api/app.py`·`docking_reads`·`mutation_model_reads`·`mutation_reads`뿐이다(시험 `test_structure_repair_downstream_reads.py`. JEV 전송·루프 모듈과 M23 읽기·보고서의 응답에는 응답 계층 `app.py`가 `structure_origin`·JW1을 더함). M22 GA 작업 모듈은 도킹 인터프리터에서 `docking_worker.py`와 의존성 없는 `ligand_ga_constants.py`만 파일 경로로 불러 쓰고 RDKit은 Morgan 지문에만 직접 import한다. M23 GA 작업 모듈은 같은 도킹 인터프리터에서 `docking_worker.py`와 `sequence_ga_constants.py`만 파일 경로로 불러 개체 도킹을 하고 OpenMM·PDBFixer를 import하지 않는다. 개체 모델링은 그 자식인 프로젝트 `.venv`의 `sequence_model_worker.py`가 M21 `openmm_mutation_worker.py`를 바꾸지 않고 불러 하며 RDKit·Meeko·MDAnalysis를 import하지 않는다(인터프리터 경로는 `resolve()`하지 않음). run 한도 증액 `Run.raise_limits`를 부르는 코드는 `docking_batch_jobs`·`ligand_ga_jobs`·`sequence_ga_jobs`의 `limit_approval` 셋이고 각각 자기 HTTP 라우트 하나에서만 불린다. M26 가져오기 명령은 `mw`를 import하지 않고 의존성 없는 `reaction_knowledge_constants.py`만 파일 경로로 불러 쓰며, 서버·도구·작업은 이 명령을 부르지 않는다. 둘은 반응 참조 폴더의 파일로만 이어지고, 서버 쪽 M26 모듈은 네트워크 모듈을 import하지 않는다. M27 가져오기 명령도 `mw`를 import하지 않고 의존성 없는 `precedent_constants.py`만 파일 경로로 불러 쓰며(네트워크 없음), 서버와는 전례 참조 폴더의 파일로만 이어진다. 서버 쪽 M27 모듈은 네트워크 모듈·`subprocess`·화학 패키지를 import하지 않고 kbase 경로를 모른다.

## 대표 흐름: 업로드부터 보고서까지

1. `POST /runs` → run 디렉터리를 만들고, 설정·예산 한도·모드(`local_only`)를 담은 `run_started` 이벤트를 기록한다.
2. `POST /runs/{id}/uploads` → 최대 25 MiB의 PDB/mmCIF 바이트를 받아 검증된 업로드 ID를 돌려준다. 원래 파일 경로는 저장하지 않는다.
3. `POST /runs/{id}/commands` (`load_structure`, `model_index`) → `Run.call`이 인자를 정규화하고, 도구 이름·버전·유효 인자·입력 바이트 지문으로 호출 키를 만든다. 캐시에 없으면 gemmi로 파싱해 `structure` 객체를 저장한다. 객체 저장 → `object_created` 이벤트(전체 payload 포함) → SQLite 색인 순서로 기록한다.
4. `prepare_structure` → altloc·물·수소 정책을 적용하고 `prepared_structure`와 `preparation_manifest`를 만든다.
5. `compute_interactions` (정확한 리간드 인스턴스, cutoff 2.5–6.0 Å) → 중원자 사이 거리 행을 `interaction_set`에 저장한다. 접촉이 없으면 `null_result=true`인 성공이다.
6. 프런트엔드는 handle envelope(요약, 미리보기 최대 5행)을 받고, 전체 행은 `/objects?handle=…`에서 페이지 단위로 읽는다. 구조 바이트는 `/structures/bytes`에서 받아 Mol*에 올린다.
7. `POST /runs/{id}/reports` (`interaction_handle`) → 행에서 수치를 다시 계산해 필드 단위 증거로 검증한 `report_manifest@1`을 저장하고, Markdown/JSON 다운로드를 제공한다.

## 비싼 계산의 작업 경로

OpenMM 최소화, ProLIF 화학 계산, fpocket 포켓 검출, M17 RDKit 리간드 점검·생성, M18 qvina 도킹, M19 일괄 도킹, M21 변이 구조 모델링, M22 리간드 GA, M23 서열 GA, M29 구조 보완은 `Run.call`로 실행하지 않는다. `/jobs`(제출, queued) → `/jobs/{id}/start`를 부르면, run의 첫 비싼 계산일 때 409로 승인 요청을 기록한다 → 사용자가 `/jobs/approve`로 승인을 명시적으로 기록한다 → 다시 `/start`를 부른다. OpenMM은 제출 전에 `/jobs/preflight`로 입력 적합성을 먼저 확인한다. 시작하면 run 실행 소유권을 얻은 뒤 비싼 계산 1단위를 예약하고, 새 프로세스 세션에서 고정된 모듈 진입점을 띄운다. 작업 프로세스는 개인 입력 파일로 제한된 JSON을 받는다. 결과는 스키마와 작업·시도 ID를 검증한 뒤에만 객체로 저장한다. 시간 초과나 취소가 나면 프로세스 그룹에 SIGTERM, 유예 후 SIGKILL을 보내고, 그룹이 비었음을 확인한 다음에 종료 상태를 기록한다. 예약은 작업 종류마다 다르다: M19는 새로 계산할 행 수(재사용 행은 과금하지 않음)를, M22는 `reserved_units`를, M23은 `2 × (reserved_evaluations + 1)`을 시작 때 예약하며 M22·M23은 환불하지 않는다. M29 구조 보완은 작업 하나에 1단위이고 실패·취소·시간 초과에도 환불하지 않는다.

## 분석 흐름 (M13)

`POST /analysis/plans`는 템플릿과 저장된 객체 메타데이터·capability만 읽어 불변 계획을 저장한다(과학 호출 없음). 실행을 만들고 계획을 승인하면, 사용자가 "다음 단계 실행"을 누를 때마다 driver가 짧은 워크플로 잠금 안에서 요청을 입장시키고 이전 자식 결과를 조정한 뒤, 다음 단계의 dispatch 기록을 남기고 잠금을 놓은 채 자식 하나를 실행한다. `run_call` 단계는 `Run.call`, `durable_job` 단계는 `JobQueue` 제출+시작, `report` 단계는 기존 보고서 함수다. 자식에는 내부 `ExecutionLink(execution_id, step_id, operation_id)`가 붙어, 자식 입장과 같은 전이 안에서 승인·순서·중지·인자 일치를 확인하고 물리 시도마다 시도 수를 먼저 기록한다. 링크는 이벤트의 `execution_link` 필드로 남고, 재시작 뒤에는 이 링크로 정확한 자식을 찾아 복구한다. 백그라운드 루프는 없고, 끝난 작업의 반영도 다음 요청이 한다. 흐름은 외부 요청을 하지 않는다.

## 참조 스냅샷과 번호 대응 (M15)

참조 데이터는 사용자가 실행하는 가져오기 명령 `scripts/import_reference_snapshots.py`만 쓴다. 이 명령이 `../kbase_kinase/ref`의 가공 스냅샷을 해시 대조 뒤 `.deps/reference/sets/<set_hash>/`로 복사하고 `active.json`을 rename으로 바꾼다. 서버는 이 폴더만 읽는다. `POST /commands`의 `map_residue_numbering`은 `Run.call`에서 사전 검사 훅이 세트를 고정하고 구조·스냅샷으로 입력을 검증한 뒤(세트 해시가 호출 키에 들어감), 구현이 같은 세트로 SIFTS 답·정렬 답·행 상태·KLIFS 번호를 만들어 `reference_snapshot_set@1`(처음 쓰는 세트면)과 `residue_numbering_map@1`을 저장한다. 대응 객체는 세트 해시와 계산에 쓴 참조 행을 담으므로 참조 폴더 없이 이벤트만으로 다시 열린다. 지식 탭은 읽기 API로 스냅샷·대응을 보여 주고, 보고서는 기존 `method_reports` 경로로 만든다. 네트워크는 쓰지 않는다.

## 참조 주석 (M16)

구조 분석 탭 패널에서 사용자가 현재 표시 구조와 같은 handle의 번호 대응과(선택적으로) 기하 접촉 결과를 고르면, `POST /commands`의 `annotate_reference_sites`가 `Run.call` 값싼 도구로 `reference_site_annotation@1`을 저장한다. 결과는 대응 객체의 행과 접촉 행을 그대로 옮겨 담으므로 이벤트만으로 다시 열린다. 패널은 읽기 API로 주석을 받아 MolstarViewer 브리지에 넘기고, 브리지는 검증된 원자 카탈로그로만 점선 끝 원자를 찾아 그린 뒤 native readback으로 적용을 확인한다. 주석이 켜진 보기는 `viewer_scene@2`, 그 그림은 `viewer_figure@2`(범례 합성 여부 기록)로 저장되고, 보고서는 기존 `method_reports` 경로로 만든다. 네트워크는 쓰지 않는다.

## 리간드 후보 (M17)

리간드 탭에서 사용자가 부모 SDF와 building block 파일을 `/chemical/imports`로 가져오고 반응 규칙을 쓰면, 화면이 `POST /jobs`로 `rdkit_inspect_v1`을 제출·승인·시작한다. 서버는 RDKit 없이 입장을 검사하고 가져오기 바이트를 스테이징하며, guardian이 `.deps/prolif/venv-locked`의 `ligand_worker.py`를 띄운다. 작업 모듈이 낸 점검 결과(원자 표·결합·수소, 번호 붙은 2D SVG, 속성, block·규칙 검증)를 서버가 검증해 `ligand_inspection@1`로 저장한다. 사용자가 원자 표에서 부위를 체크하면 `POST /ligand/preview`가 저장된 결합 목록으로 부위를 검사하고(이벤트 없음), 생성 요청 `rdkit_enumerate_v1`은 같은 검사를 입장에서 다시 한 뒤 점검 객체의 `valid` 규칙 텍스트와 함께 작업 모듈에 넘긴다. 결과 `ligand_candidate_set@1`은 필터와 무관하게 모든 후보를 담는다. 후보 표는 `/ligand/candidate_sets/rows`가 저장값에 필터·정렬·페이지를 적용해 돌려주고, 보고서는 기존 `method_reports` 경로로 요약 증거만 만든다. 두 객체는 이벤트만으로 다시 열린다. 네트워크는 쓰지 않는다.

## 리간드 도킹 (M18)

리간드 탭 도킹 영역에서 사용자가 수용체(+결합 사이드카)와 리간드 SDF를 `/chemical/imports`로 가져오고(M11 종류 그대로), 수용체에 비표준 잔기가 있으면 `GET /docking/receptor_instances`(gemmi, 이벤트 없음)에서 뺄 인스턴스 하나를 고른다. 리간드 출처(3D SDF 또는 M17 후보 + 부모 SDF)·방식·상자·값·확인 세 항목을 정하면 화면이 `POST /jobs`로 `qvina_dock_v1`을 제출·승인·시작한다. 서버는 RDKit·Meeko 없이 입장을 검사하고(작업 인자, 같은 run handle, 후보 집합·부모 해시, 수용체 M11 규칙·인스턴스 일치를 gemmi로), 가져오기 바이트를 스테이징하며, guardian이 `.deps/docking/venv-locked`의 `docking_worker.py`를 띄운다. 작업 모듈은 수용체를 다시 검사한 뒤 M11 화학 추론 그래프 → Meeko로 수용체 PDBQT를, Meeko로 리간드 PDBQT를 만들고, `.deps/qvina/env/bin/qvina2`를 자식으로 실행한다(자유: 검색, 코어 고정: RDKit 구속 형태마다 `--score_only`). 포즈를 입력 원자 순서로 되돌려 포즈 SDF·상자 밖 원자·최소 거리·기하 접촉을 만들고, 서버가 이를 검증해(접촉의 수용체 원자·거리를 수용체 가져오기로 재대조) `docking_result@1`로 저장한다. 읽기는 `/docking/*`가 매번 완료된 게시에 대조해 돌려주고, 보고서는 기존 `method_reports` 경로로 만든다. 결과는 이벤트만으로 다시 열린다(qvina·Meeko 없이). 작업 모듈은 화학 패키지 import 전에 Python socket을 막고, 제품 실행 중 네트워크는 쓰지 않는다.

## 리간드 일괄 도킹 (M19)

리간드 탭 일괄 영역에서 사용자가 M18 도킹 영역으로 가져온 수용체·부모 SDF와 M17 후보 집합을 고르고, M17 필터 결과(`/ligand/candidate_sets/rows`) 위에서 후보를 체크하고, 방식·부모 기준 행·상자·값·확인을 정한다. 화면은 `POST /docking/batches/preflight`(이벤트 없는 읽기)로 행별 재사용·새 계산 수 N·필요 예산·부족분을 받는다. 부족하면 사람이 `POST /docking/batches/limit_approval`을 눌러 run 한도를 부족분만큼 올린다(`budget_limit_updated`, `by: "human"`). 그다음 `POST /jobs`로 `qvina_batch_dock_v1`을 제출·승인·시작한다. 서버는 RDKit·Meeko 없이 행마다 M18 입장 검사를 하고, 시작 때 run 실행 잠금 안에서 재사용 행을 정해 N단위를 예약한 뒤 수용체·부모 SDF와 행 목록을 스테이징한다. guardian이 `docking_batch_worker.py`를 띄우면 작업 모듈이 수용체를 한 번 준비하고 행마다 M18 `dock_row`로 `qvina2`를 돌리며, 행마다 `rows/` 아래 시작·결과·상태 파일을 내구적으로 쓴다. 작업이 어떻게 끝나든(완료, 취소, 시간 소진, 크래시, 서버 재시작 복구) 서버는 그룹 정리를 확인한 뒤 검증 가능한 행 결과를 `docking_result@1`로 게시하고(`docking_batch_row_published`), 스테이징 관찰과 종료 원인으로 요약 `docking_batch_result@1`을 만들어 마지막에 게시한다(`docking_batch_published`). 화면은 작업 기록의 `batch` 진행(상태 파일 수, 요약 handle·상태)을 폴링하고, 요약 상세(`/docking/batches/detail`)로 표를 그리며, 행의 "상세 열기"는 M18 도킹 영역의 `/docking/results/*` 상세로 넘긴다. 보고서는 기존 `method_reports` 경로다. 일괄이 도는 동안 run 실행 잠금과 전역 작업 슬롯을 쥐므로 같은 run의 다른 계산과 다른 run의 비싼 작업이 기다린다. 네트워크는 쓰지 않는다.

## 변이 후보 (M20)

단백질 공학 탭 변이 후보 화면에서 사용자가 이 run의 전처리 구조, 위치 출처(같은 구조의 포켓 결과·순번, 리간드 껍질 반경, 직접 고른 잔기), 리간드, 허용 잔기, 보호·해제 목록, 금속 거리와 선택적인 번호 대응·주석·반응 지식 결과(M26)를 정하면, `POST /commands`의 `generate_mutation_candidates`가 `Run.call` 값싼 도구로 돈다. 도구 모듈 `tools/mutations.py`의 사전 검사 훅이 입장을 구현 전에 검사하고(포켓 결과는 `pocket_bundle.validated_pocket_set`, 반응 결과는 `reaction_knowledge.validated_result`로 다시 검증), 순수 모듈 `mutation_candidates.py`가 저장된 전처리 좌표와 저장 객체에서 복사한 값으로 위치·보호·후보를 만든 뒤 `validated_set`을 통과한 `mutation_candidate_set@1`만 저장한다. 작업 큐·예산 단위·외부 엔진·참조 폴더·네트워크를 쓰지 않는다. 읽기는 `/mutation_candidate_sets*`(`mutation_reads.py`, 이벤트 없음)이고 보고서는 기존 `method_reports` 경로(`analysis_type: "mutation_candidates"`)다. 후보 행의 "변이 구조 모델링"은 후보 집합과 번호만 M21 영역 요청 칸에 넘기고 아무것도 보내지 않는다. `mutation_candidates.py`의 SHA-256은 M21·M23 호출 키에 들어간다.

## 변이 구조 모델링 (M21)

사람이 넘겨받은 후보에 seed·두 리터럴 확인·cutoff를 정하면 화면이 `POST /jobs`로 `openmm_mutation_model_v1`을 제출·승인·시작한다. 서버(`mutation_model_bundle.py`)는 OpenMM·PDBFixer를 실행하지 않고 입장(`mutation_model_inputs.py`) → M7과 같은 dry-run 계획 → 사용할 수 없음(412)·M7 사전 검사 → 호출 키 순서로 검사하고(시작 전에는 예약·과금 없음), M7 사전 검사의 중원자 투영·변이 위치·seed를 스테이징한다. guardian이 프로젝트 `.venv`의 `openmm_mutation_worker.py`를 띄우면 작업 모듈이 야생형 기준과 변이형 두 구조를 같은 코드 경로로 만들고(변이형만 PDBFixer로 변이 잔기를 바꿈) 각 구조를 M7과 같은 OpenMM 방법으로 최소화해 전위·변이 위치 SASA·접촉을 낸다. 서버는 출력을 작업 선택·고정 방법과 대조하고 `mutation_model_math.validated_model`로 값을 다시 계산해 확인한 뒤 두 mmCIF(`mutation_model_structure@1`)와 `mutation_model@1`을 게시한다. 읽기는 `/mutation_models*`(목록·상세·쪽별 접촉·mmCIF·`docking_pairs`, 이벤트 없음), 보고서는 `method_reports` 경로(`analysis_type: "mutation_model"`)다. 같은 조건 도킹은 새 라우트 없이 단독 M18 작업 둘이며, M18 입력의 `receptor_source: {kind: "mutation_model", mutation_model, side: "wild_type_reference"|"mutant"}`로 그 쪽 저장 mmCIF와 저장 위상에서 만든 결합 사이드카를 수용체로 쓴다. 두 구조의 차이는 어디에서도 계산하지 않는다.

## 리간드 GA 설계 (M22)

리간드 탭 GA 영역에서 사용자가 M18 도킹 영역이 가져온 수용체·사이드카·부모 SDF, 게시된 M17 후보 집합과 M17 필터, 상자·도킹 값·확인, GA 파라미터를 정하면 화면이 `POST /ligand/ga/preflight`(이벤트 없는 읽기)로 풀·재사용 가능 개체·`reserved_units`·부족분을 받는다. 부족하면 사람이 `POST /ligand/ga/limit_approval`을 눌러 run 한도를 부족분만큼 올리고, 그다음 `POST /jobs`로 `qvina_ga_dock_v1`을 제출·승인·시작한다. 서버(`ligand_ga_jobs.py`·`ligand_ga_inputs.py`)는 RDKit·Meeko 없이 입장을 검사하고, 시작 때 run 실행 잠금 안에서 재사용 계획을 정해 `reserved_units`를 예약한 뒤 가벼운 입력을 스테이징한다. guardian이 `.deps/docking/venv-locked`의 `ligand_ga_worker.py`를 띄우면 작업 모듈이 `docking_worker.py`를 파일 경로로 불러 수용체를 한 번 준비하고, 개체(후보 하나의 단독 M18 자유 도킹)마다 `dock_row`로 `qvina2`를 돌리며, 유사 후보 고르기에 쓰는 Morgan Tanimoto 유사도만 RDKit으로 계산한다. 같은 인자의 검증된 M18 결과가 있는 개체는 다시 도킹하지 않는다. 작업이 어떻게 끝나든 서버는 그룹 정리를 확인한 뒤 새 도킹을 `docking_result@1`로 먼저 게시하고(`ligand_ga_individual_published`) 요약 `ligand_ga_result@1`을 마지막에 게시한다(`ligand_ga_published`). 읽기는 `/ligand/ga/results*`(`ligand_ga_reads.py`), 개체 행 "상세 열기"는 M18 도킹 영역으로 넘기고, 보고서는 `method_reports` 경로(`analysis_type: "ligand_ga"`)다. 네트워크는 쓰지 않는다.

## 서열 GA 설계 (M23)

단백질 공학 탭 서열 GA 영역에서 사용자가 게시된 M20 후보 집합, M11 `ligand_sdf` 가져오기, M21 `PairInputs`의 상자·도킹 값·확인, 두 리터럴 확인, GA 파라미터를 정하면 `POST /sequence_ga/preflight`(이벤트 없는 읽기)가 조합 공간·재사용·`2 × (reserved_evaluations + 1)` 예약·부족분을 돌려준다. 부족하면 사람이 `POST /sequence_ga/limit_approval`을 누르고, 그다음 `POST /jobs`로 `sequence_ga_dock_v1`을 제출·승인·시작한다. 서버(`sequence_ga_jobs.py`·`sequence_ga_inputs.py`)는 RDKit·Meeko·MDAnalysis·PDBFixer를 import하지 않고 `qvina2`를 실행하지 않으며 OpenMM은 M7 `dependencies()`·`preflight()`로만 쓴다. guardian이 `.deps/docking/venv-locked`의 `sequence_ga_worker.py`를 띄우면, 작업 모듈은 야생형 기준 행과 새 평가마다 프로젝트 `.venv`의 `sequence_model_worker.py`를 `[<repo>/.venv/bin/python, "-I", 프로그램]` 자식으로 실행해(개체 작업 폴더의 `model_input.json` → `model.cif`·`model.json` 등 파일로만 주고받음) 서로 다른 위치 변이 1–4개를 구조 순서대로 M21 함수로 적용한 모델을 만들고, 그 모델에 `docking_worker.py`(파일 경로) `dock_row`로 사용자 SDF를 자유 도킹한다. 작업이 어떻게 끝나든 서버는 그룹 정리 뒤 기준 행과 새 개체마다 모델 mmCIF(`mutation_set_model_structure@1`) → 모델(`mutation_set_model@1`, `sequence_model_bundle.validated_model`) → `docking_result@1`을 게시하고(`sequence_ga_individual_published`) 요약 `sequence_ga_result@1`을 마지막에 게시한다(`sequence_ga_published`). M18의 `receptor_source` `mutation_model`은 서버 쪽에서만 `mutation_set_model@1`도 받는다. 읽기는 `/sequence_ga/results*`(`sequence_ga_reads.py`, 개체·모델 mmCIF 포함), 보고서는 `method_reports` 경로(`analysis_type: "sequence_ga"`)다. 서열이 다른 구조의 OpenMM 전위는 비교하지 않는다. 네트워크는 쓰지 않는다.

## JEV 과학 전송 (M24)

지식·보고서 탭 JEV 영역에서 사용자가 이 run의 과학 전송 동의를 켜고(`POST /jev/consent`, 이벤트 하나, 뷰어 모드 불변), 게시된 M17 리간드 후보 집합 또는 M20 변이 후보 집합에서 후보를 최대 20개 고르면, 화면이 `POST /commands`로 값싼 도구 `build_jev_projection`을 부른다. 사전 검사 훅이 같은 run·게시·검증·선택·필터·구조를 검사하고, 구현이 저장 객체(변이는 전처리 구조 좌표에서 이웃·구간까지)로 허용 목록 와이어와 정확한 요청 본문의 바이트 수·SHA-256을 담은 `jev_projection@1`을 저장한다(외부 요청 없음). `POST /jev/preview`는 그 투영을 다시 검증해 보낼 본문 문자열·해시·예약값·차단 이유를 돌려주고(이벤트 없음), 사람이 확인을 체크하고 누르면 `POST /jev/sends`가 해시 일치·멱등·진행 중을 확인한 뒤 `SCIENCE_GATE.request_science`를 부른다. 게이트는 run 실행 잠금 안에서 승인 이벤트를 먼저 쓰고, 거절 검사 → 키 → 외부 토큰·USD 예약 → `prepared` 감사(승인한 본문 그대로) → dispatch를 기록한 뒤 OpenRouter에 한 번 보내고 기존 규칙으로 정산한다. 검증을 통과한 답은 제안 객체 `jev_choice@1`로 저장되고 모든 전송은 `jev_send_outcome`으로 끝난다. 전송 기록·늦은 응답·상한은 이벤트에서 다시 만들며, 보고서는 기존 `method_reports` 경로로 저장 객체·이벤트만 읽어 만든다. JEV의 선택은 어떤 작업·도구도 일으키지 않는다.

## JEV 설계 루프 (M25)

리간드 탭 또는 단백질 공학 탭의 JEV 루프 영역에서 사용자가 게시된 후보 집합 하나에서 풀(2–20)·목표·루프 seed·반복 상한·계산 조건을 정하면 `POST /jev_loops`가 입장 검사 뒤 `jev_loop_created` 하나를 쓴다. 루프 기록 `jev_loop@1`은 저장하지 않고 `GET /jev_loops/{loop_id}`가 이벤트 로그를 한 번 읽어 작업 기록·저장 결과·제안에서 도출한다. 바퀴마다 사람이 "보낼 내용 만들기"를 누르면 `POST /commands`의 `build_jev_loop_projection`이 루프 기록으로 전송마다 섞은 순서의 `jev_loop_projection@1`을 저장하고(외부 요청 없음), 미리보기·전송은 M24 `/jev/preview`·`/jev/sends` 그대로다(승인 콜백 안에서 루프 검사 뒤 승인 이벤트, 게이트는 스키마로 루프 검증·본문·응답 해석만 가름, 답은 `jev_loop_choice@1`). 사람이 JEV의 선택이나 직접 지정한 후보로 `POST /jev_loops/{loop_id}/compute`를 누르면 라우트가 run 실행 잠금 안에서 `jev_loop_compute_approved`를 쓰고 단독 M18(리간드)·M21(단백질 모델링) 작업과 같은 인자·호출 키의 작업을 `JobQueue`에 제출한 뒤, 잠금을 놓고 기존 시작 라우트처럼 시작한다(첫 비싼 계산 승인은 기존 `/jobs/approve`). 단백질은 모델이 게시되면 사람이 같은 라우트로 변이 구조 도킹을 시작하거나 `abandon_docking`으로 포기한다. 작업은 기존 큐·guardian·작업 모듈이 돌리고 루프는 그 기록을 읽기만 한다. `POST /jev_loops/{loop_id}/end`가 요약 `jev_loop_result@1`을 저장한 뒤 `jev_loop_ended`를 쓰고, 보고서는 기존 `method_reports` 경로(`analysis_type: "jev_loop"`)다. 백그라운드·자동 다음 바퀴·자동 계산 시작은 없고 새 한도 증액 경로도 없다.

## 효소 반응 지식 (M26)

반응 참조 데이터는 사용자가 터미널에서 실행하는 가져오기 명령 `scripts/import_reaction_references.py`만 쓴다. 이 명령이 M-CSA API(`www.ebi.ac.uk`)·UniProt REST(`rest.uniprot.org`)·Rhea(`www.rhea-db.org`)에 HTTPS GET만 보내 받은 응답에서 허용 필드만 가공하고, 모든 형식 검사를 통과했을 때만 `.deps/reaction_reference/sets/<set_hash>/`에 원자적으로 설치한 뒤 `active.json`(`reaction_active@1`)을 rename으로 바꾼다. 요청 시도는 설치된 세트의 `files/request_log.jsonl`에 남는다. 서버는 이 폴더만 읽고, M15 참조 폴더와는 따로다. 지식·보고서 탭의 "효소 반응 지식" 영역에서 사용자가 같은 run의 구조, 확인한 PDB ID, 체인과 accession, 선택적으로 같은 구조의 번호 대응을 고르면(M-CSA 제안은 `GET /reaction_reference/pdb/{pdb_id}`), `POST /commands`의 `link_reaction_knowledge`가 `Run.call` 값싼 도구로 돈다. 사전 검사 훅이 사용 중 세트를 고정하고(없거나 손상이면 412) 입장을 검사한 뒤(세트 해시가 호출 키에 들어감), 구현이 같은 세트로 체인마다 M-CSA 절(M-CSA가 적은 PDB·저자 체인·번호와 구조 잔기 이름 대조)·UniProt 절·반응 절을 만들어 `reaction_knowledge@1`을 저장한다. 결과는 쓴 세트 기록과 참조 행을 담으므로 참조 폴더 없이 이벤트만으로 다시 열린다. 읽기는 `/reaction_reference/*`·`/reaction_knowledge*`(이벤트 없음)이고, 보고서는 기존 `method_reports` 경로(`analysis_type: "reaction_knowledge"`)다. 뷰어 표시는 없고 M13 흐름은 이 도구를 부르지 않는다.

기존 흐름에서 바뀐 것: M20 `generate_mutation_candidates`는 선택 입력 `catalytic_annotation`(같은 run의 `reaction_knowledge@1`)을 받아 v2 집합(`mw.mutation_candidates/v2`)을 만든다. 도구 층이 결과를 `validated_result`로 검증해 보호에 필요한 값만 `mutation_candidates.py`의 순수 함수에 넘기고, 그중 M-CSA "대응됨" 행만 보호 근거(`catalytic_residue`)가 되며 검사 칸 `protection_checks.catalytic_residue_database`가 함께 저장된다. 이 단계 뒤 새 집합은 모두 v2이고 저장된 v1 집합은 바이트 그대로 유효하다. M21·M23·M24·M25는 두 세대를 모두 받고, 후보 집합을 고르는 곳은 `catalytic_residue_database.status`로 "촉매 잔기 검사 안 함"을 표시한다. M24 변이 투영·제안(`jev_choice@1`)·보고서의 다섯째 한계 문장은 와이어의 이 상태에 따라 J6(`not_available`, 바이트 그대로)·J6n·J6c(`J6_BY_CATALYTIC_STATUS`)이고, M26 반응 자료는 JEV 와이어에 들어가지 않는다. `mutation_candidates.py`가 바뀌어 M21·M23 호출 키가 달라졌다(영향은 `docs/engineering-notes.md`의 M26 함정).

## 키나아제 전례 (M27)

전례 참조 데이터는 사용자가 터미널에서 실행하는 가져오기 명령 `scripts/import_precedent_snapshots.py`만 쓴다. 이 명령은 네트워크를 쓰지 않는다: 로컬 `kbase_kinase` 체크아웃의 `dist/moves.jsonl`·`dist/moves_flagged.jsonl`·`dist/references.jsonl`과 `ref/pubmed`의 가장 최근 서지 스냅샷을 읽어, `KBASE_PINS` 세 값·kbase 매니페스트의 SHA-256·바이트·행 수·모든 레코드의 형식과 `content_hash` 재계산이 맞을 때만 읽기 전용 `git -C`로 커밋·`dirty`를 기록하고 바이트 그대로 `.deps/precedent_reference/sets/<set_hash>/`에 원자적으로 설치한 뒤 `active.json`(`precedent_active@1`)을 rename으로 바꾼다. 서버는 이 폴더만 읽고, M15·M26 참조 폴더와는 따로다.

흐름: 가져오기 → 로컬 참조 폴더 → 서버 고정 → 도구 → 이벤트·저장 객체 → 읽기·보고서 → 지식 탭 영역. 지식·보고서 탭의 "키나아제 전례" 영역에서 사용자가 같은 run의 번호 대응(M15 `residue_numbering_map@1`), 체인, `moves_flagged` 포함 여부를 고르고 "전례 연결"을 누르면, `POST /commands`의 `link_kinase_precedents`가 `Run.call` 값싼 도구로 돈다. 사전 검사 훅이 사용 중 세트를 고정·해석하고(없거나 손상이면 412) 번호 대응을 저장소에서 읽어 입장 다섯을 검사한 뒤(세트 해시가 호출 키에 들어감), 구현이 같은 세트로 체인 판정(accession 하나 + mapped ≥ 1) → 같은 accession 표적의 전례 모음 → 포함할 원본 레코드의 `content_hash` 재확인 → 두 경로를 뺀 사본·무결성 확인 값·서지 → `validated_result`를 거쳐 `kinase_precedents@1`을 저장한다(1 MiB 초과는 429, 자르지 않음). 결과는 세트 기록과 전례 사본을 담으므로 참조 폴더 없이 이벤트만으로 다시 열린다. 읽기는 `/precedent_reference/status`·`/runs/{id}/kinase_precedents*`(이벤트 없음)이고, 결과 상세는 서버가 한 표적의 전례를 거르고 정렬해 한 쪽씩 돌려준다. 보고서는 기존 `method_reports` 경로(`analysis_type: "kinase_precedents"`, 요약 + 출처 목록)다. 뷰어 표시는 없고 M13 흐름·M17·M19·M24·M25는 이 도구나 결과를 쓰지 않는다. 기존 흐름의 코드·형식·호출 키 해시 파일은 바뀌지 않았다.

## 구조 보완 (M29)

M21·M23·M25 단백질 루프와 M21·M23 모델을 수용체로 쓰는 도킹은 모두 M7 OpenMM 사전 검사를 입구로 쓰고, M7은 표준 단백질 중원자 템플릿과 정확히 같은 구조만 받는다. 실제 결정 구조는 곁사슬 원자 결손·내부 틈·C 말단 OXT 결손·같은 저자 체인 이름의 조각 분리 때문에 이 입구에서 흔히 막히므로, 사용자가 명시적으로 요청하면 승인된 결손만 PDBFixer로 보완한 새 전처리 구조를 만들어 모델링 경로에서만 쓴다.

흐름: 업로드 → 전처리(`prepared_structure@1`) → (M21 입장에서 M7 사전 검사 거절) → 구조 보완 사전 검사 → `repair_structure` 작업(`pdbfixer_repair_v1`: 작업 모듈의 PDBFixer가 추가 원자만 만들고, 서버가 접합·검증·M7 사전 검사·게시) → 보완 `prepared_structure@1`(전처리 기록에 `repair`) → M20 후보 집합 → M21·M23·M25 단백질 루프·M24 변이 투영, M18은 M21·M23 모델을 수용체 출처로 거쳐서만.

단백질 공학 탭 맨 위 "구조 보완" 영역에서 사용자가 이 run의 전처리 구조를 고르면 `GET /structure_repair/preflight`(`structure_repair_preflight@1`, 이벤트·도구·작업 없음)가 결함 목록(체인 조각·곁사슬 결손 잔기·C 말단 OXT·틈·MSE), 걸림돌, 예상 추가 잔기·원자 수, 예산 부족분, 작업 입장 결과, 해당 한계 문장을 돌려준다. 결함 분석(`structure_repair.analyze`)은 서버가 PDBFixer 없이 gemmi와 설치된 Amber14 템플릿 XML만으로 하고, 틈 잔기의 이름·저자 번호·label 번호는 전처리 기록의 `source_handle`이 가리키는 원본 `structure_source` 바이트의 서열·미관측 잔기 목록(mmCIF `_entity_poly_seq`·`_pdbx_unobs_or_zero_occ_residues`, PDB `SEQRES`·`REMARK 465`)에서 읽는다(추측하지 않음). 사람이 확인(`repair_policy: "complete_missing_atoms_v1"`)을 체크하고 누르면 화면이 `POST /jobs`로 `pdbfixer_repair_v1`을 제출·승인·시작한다(run의 첫 비싼 계산이면 기존 승인, 작업 하나 = 1단위). 서버(`structure_repair_jobs.py`)는 입장(422 `input_invalid` 다섯 → 412 셋 → 422 `repair_not_possible`과 걸림돌 목록 → 429 스테이징 크기)을 작업을 만들기 전에 검사하고, 단백질 폴리머 잔기(조각을 저자 체인별로 합침)와 틈 목록을 스테이징한다. guardian이 프로젝트 `.venv`의 `structure_repair_worker.py`를 띄우면 작업 모듈이 MSE의 이름·SE 원자만 MET·SD로 바꾼 뒤 PDBFixer(CPU 스레드 1, seed 1)에 틈 목록을 직접 넣어 결손 원자를 더하고, 관측 원자가 1e-9 Å 안에서 그대로 돌아왔는지 확인한 뒤 추가 원자만 돌려준다. 서버는 그룹 정리를 확인한 뒤 추가 원자를 전처리 구조에 접합하고(`build_repaired`: 조각 합치기, MSE→MET, 새 원자 좌표 소수 넷째 자리와 `calc_flag` `c`), 순수 검증기 `validated_repair`(관측 원자 불변, 추가 원자·새 잔기 규칙, 기록 재생성)와 저장 전 읽기 전용 겹침 보기 위의 M7 `preflight`를 모두 통과했을 때만 큐가 run 전이 잠금 안에서 보완 좌표 → 보완 기록 `structure_repair@1` → 전처리 기록(`repair: {record, source}`, 틈을 메웠으면 `missing_residues: "modeled_internal_gaps"`) → 보완 구조 순서로 저장하고 `structure_repair_published`(네 handle)를 쓴다. 하나라도 통과하지 못하면 객체를 하나도 남기지 않고 닫힌 실패 코드로 끝난다(예약한 1단위는 환불하지 않음). 같은 전처리 구조를 다시 요청하면 같은 호출 키의 같은 작업을 돌려준다. 읽기는 `/structure_repairs*`(목록·상세·추가 원자 쪽·보완 mmCIF 내려받기, 이벤트 없음, 매번 게시 증거와 기록을 재검증)이고, 보고서는 기존 `method_reports` 경로(`analysis_type: "structure_repair"`, `structure_repair_markdown@1`)다. 보완 기록에는 구조 handle이 없고 게시 이벤트로 기록에서 구조를 찾으므로, 원본 입력·네트워크·엔진 없이 이벤트만으로 다시 열린다(재검증은 설치된 템플릿 XML을 읽고, 없으면 증거 무효가 아니라 412 `openmm_unavailable`).

받는 곳과 거절: 보완 구조를 받는 곳은 모델링 경로뿐이다. `Run.call`은 `generate_mutation_candidates` 밖의 모든 도구 인자에서 보완 구조를 사전 검사 전에 거절하고(`REPAIRED_STRUCTURE_TOOLS`), 작업 큐는 M7 단독 최소화 등의 제출에서, API 라우트(뷰어 세션·보기·그림, `inspect_complex`, 일반 보고서, M7·포켓 사전 검사 읽기, M13 계획)는 `_repaired_refusal`로, 모듈 입구(`chemical_inputs`·`pocket_input`·`tools/site_annotation`)는 `reject_if_repaired`로 422 `repaired_structure_not_accepted`를 돌려준다. 구조 분석 탭의 뷰어 소스 목록도 보완 구조를 거르므로 보완 구조는 Mol*에 올라가지 않는다. M20은 보완 구조를 받을 때 포켓 결과·번호 대응·참조 주석·촉매 연결 결과를 보완 구조나 그 원본 전처리 구조(`repair.source`)의 것으로 받고(원본 결과의 행은 잔기 7필드 정확 일치로 연결), 저장된 후보 집합은 해시 파일 `mutation_candidates.py`가 만든 그대로 둔다. 읽기 계층(`mutation_handoff`)이 보완 기록으로 모델링 잔기 위치를 "검사 안 함(모델링 잔기)"(`reference_not_checked`)으로, 모델링 원자가 위치·보호 판정에 든 위치를 `modeled_basis`(SO2)로 덮어 보인다.

기존 흐름에서 바뀐 것: 후보 집합·변이 모델·서열 GA 결과·JEV 전송과 루프·M18 도킹 결과(수용체가 보완 구조 기반 모델일 때)의 읽기 응답은 보완 구조일 때만 `structure_origin`(보완 기록·보완 구조·원본 구조 handle, 개수, SO1)을 더하고, 그 밖의 응답 바이트는 같다. M20·M21·M24(변이)·M25(단백질 갈래)·M18 보고서는 보완 구조일 때만 "## 구조 출처" 절이 든 새 형식 버전(`mutation_candidates_markdown@3`·`mutation_model_markdown@2`·`jev_choice_markdown@2`·`jev_loop_markdown@2`·`ligand_docking_markdown@2`)으로 만들고, 저장된 이전 버전은 같은 바이트로 다시 열린다. M23 서열 GA 보고서·읽기는 호출 키 해시 파일이라 바꾸지 않았고, M23 응답의 `structure_origin`은 `app.py`가 더하며 보완 사실은 화면과 같은 후보 집합의 M20 `@3`·보완 보고서가 싣는다. JEV 전송 본문·와이어·`jev_choice@1`·감사 열은 그대로이고 미리보기·승인 응답에만 `repair_warning`(JW1)이 붙는다. 호출 키 해시 파일 27개·골든·M13 흐름 코드는 바뀌지 않았다. 네트워크는 쓰지 않는다.

수락 도구(제품 밖, 실행 방법은 `docs/operations.md`): 실행기 `scripts/m29_offscreen_acceptance.py`와 `m29_common.py`·`m29_api_cases.py`·`m29_oracle.py`, 하네스 `frontend/tests/offscreen/structure-repair-flow.cjs`. 실행기·공용·사례·기대값 모듈은 `mw`를 import하지 않고(기대값은 `m29_oracle.py`가 입력 파일과 설치된 템플릿 XML에서 독립으로 계산), 제품에는 loopback HTTP, Electron 오프스크린 하네스, 하위 프로세스(`mw.structure_repair_constants`만 읽어 고정 문장·닫힌 집합을 내보내는 `m29_export_fixed_sentences.py`, 단계 백엔드인 M25 fixture 서버)로만 닿는다. `backend/mw`는 이 도구를 import하지 않는다.

## 외부 경계

- 넘어가는 것: 해당 run에서 온라인 모드와 뷰어 전용 동의를 켠 뒤, 사용자가 입력한 뷰어 요청 문장(최대 512자)과 생성된 별칭 대상 카탈로그(최대 256개)만 OpenRouter로 간다. M3 경로에서는 접촉 집계 숫자 몇 개만 간다. M24 과학 전송은 과학 전송 동의가 켜진 run에서 사람이 승인한 투영 본문 하나씩만 간다: 리간드 후보(정규 SMILES, RDKit 추정 속성, PAINS 일치, 생성 방식 종류) 또는 변이 후보(잔기 7필드, 서열 구간 앞뒤 5개, 5.0 Å 이웃 잔기 이름, 리간드까지 거리, 보호 검사 상태, 포켓 요약), 고정 질문. M25 루프 전송은 같은 경로로 같은 종류의 후보 필드에 목표(`goal`)·계산된 후보 표시(`computed`, 활용형만 저장된 qvina 점수)·목표별 지시문을 더하고 후보 순서·별칭을 전송마다 섞는다. 서열 구간·이웃 잔기 이름으로 단백질이 알려질 수 있다.
- 넘어가지 않는 것(현재 코드 기준): 좌표, 구조 파일, 전체 서열, 원자 이름, 리간드 인스턴스 이름, 번호 대응·KLIFS 값, M26 반응 자료(M-CSA·UniProt·Rhea 값), M27 전례 자료(kbase 전례·서지·참조), M29 보완 기록·구조 출처(보완 구조 기준 변이 후보도 보낼 수 있지만 본문은 보완 사실을 담지 않고, 미리보기·승인 화면에만 JW1), 로컬 경로, handle, run ID, 후보 id, 루프 ID·루프 seed·바퀴 번호, 자격 증명, 이전 대화.
- 정책(결정 0015, 2026-09-29): 구조·좌표·서열·리간드·분석 결과는 외부 모델로 보내도 된다. 실제로 보내는 과학 데이터는 M24의 두 투영과 M25의 두 루프 투영뿐이며, 새 종류는 게이트 투영·미리보기·예산·감사를 함께 만들어야 보낸다. 자격 증명은 계속 전송 금지다.
- 게이트 밖 예외(결정 0034): 사용자가 터미널에서 실행하는 M26 반응 참조 가져오기 명령 `scripts/import_reaction_references.py` 하나가 허용 호스트 셋(`www.ebi.ac.uk`·`rest.uniprot.org`·`www.rhea-db.org`)에 HTTPS GET만 보낸다. 보내는 것은 URL 질의(쪽 번호·accession 목록·열 이름)뿐이고 키·쿠키·사용자 데이터는 없으며, 리다이렉트·환경 프록시를 따르지 않고 호스트·스킴을 바꾸는 옵션도 없다. 서버·도구·작업·보고서·화면은 이 명령을 부르지 않는다. 고정 규칙과 요청 기록은 `docs/security.md`.
- 브라우저의 글꼴·스크립트·Mol* 자산·예시 구조는 모두 로컬 번들이다. 오프스크린 QA는 loopback이 아닌 요청을 전부 차단하고 기록한다.
- 초기 설치(`pip`, `npm ci`, ProLIF·도킹 wheelhouse, fpocket·qvina conda archive 준비)와 위 M26 가져오기 명령에만 네트워크가 필요하다. 서버와 작업 프로세스는 실행 중에 다운로드하지 않는다. M15 참조 스냅샷 가져오기 명령(`scripts/import_reference_snapshots.py`)과 M27 전례 가져오기 명령(`scripts/import_precedent_snapshots.py`)은 로컬 kbase 체크아웃에서 복사할 뿐 네트워크를 쓰지 않는다(M27 개발·검증 중 외부 요청은 사람이 허용한 RCSB 공개 구조 2개뿐이었다, `docs/security.md`). M29 구조 보완 작업 모듈도 PDBFixer의 내려받기 경로를 쓰지 않고, M29 개발·검증 중 외부 요청은 사람이 허용한 RCSB 공개 구조 5개(8VF6·1RNH·4INS·1AY7·1CLL, QA 입력 준비)뿐이었다(`docs/security.md` "M29 구조 보완의 외부 요청").

## 저장소 배치

`runs/<run_id>/`에는 `events.jsonl`(원본 데이터), 불변 객체 파일, 없애도 되는 SQLite 색인, 작업 시도 디렉터리가 있다. 위치는 `MW_RUNS_DIR`로 바꿀 수 있다. 참조 스냅샷은 run 밖의 `.deps/reference/`(M15, `MW_REFERENCE_DIR`), `.deps/reaction_reference/`(M26, `MW_REACTION_REFERENCE_DIR`, 세트마다 요청 기록 `files/request_log.jsonl`), `.deps/precedent_reference/`(M27, `MW_PRECEDENT_REFERENCE_DIR`)에 따로 있고, 세 가져오기 명령 모두 이전 세트 폴더를 지우지 않는다. M27 결과 객체는 실제 kbase 전례 문구를 run 이벤트에 담으므로 run 폴더는 공유하지 않는 자료다. M29 보완 구조와 보완 기록도 run 안의 불변 객체·이벤트이며 원본 전처리 구조는 바뀌지 않고 그대로 남는다. 객체와 색인을 지워도 이벤트만으로 전부 다시 만들 수 있다. 이 복구 방식은 작은 구조 작업을 전제로 하며, 큰 궤적 데이터는 다루지 않는다.
