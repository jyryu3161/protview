# M4 POSIX implementation addendum

GPT-6 Astra, 2026-09-24. Selected implementation guidance for JOBS_CONTRACT.md, targeting the actual Darwin/Python 3.11 runtime. No new scientific protocol is required. Parent installed psutil 7.2.2 in the project environment; Sol must declare it as a direct backend dependency. No proprietary engine installation or external model call is part of this work.

## 1. Use a small guardian, not the scientific worker as the ownership anchor

Use a fixed, code-owned bootstrap/guardian module launched with the project interpreter, shell=False, close_fds=True and start_new_session=True. Keep the Popen object. The guardian becomes the new session/group leader and runs only bounded control/supervision logic. It starts the fixed scientific adapter (or an internal fixture adapter in tests) as a separate child in its existing group. The adapter must not call setsid/setpgid or daemonize. The guardian stays alive when that child exits, so a leader-exited scientific process does not remove the group ownership anchor.

The production request never chooses the module, argv, environment, input path or fixture. The selected production protocol map can be empty: the four energy protocols remain honestly unavailable. Tests inject a fixed fixture adapter through an internal constructor, not a request flag or environment variable.

Construct a minimal environment: an explicit fixed system PATH if needed, LANG=C, PYTHONUTF8=1, PYTHONUNBUFFERED=1, and a confined per-attempt TMPDIR. Do not copy os.environ, PYTHONPATH, DYLD/LD injection settings, model credentials or user-supplied overrides. Use the absolute project interpreter. Only bounded IDs/control-FD numbers belong in argv; data uses confined files or the private control channel.

## 2. Reserve → bootstrap identity → authorize execution

Use a private socketpair (or equivalent bidirectional pipe pair) inherited only by the guardian via pass_fds. Close the unused ends immediately. The scientific child must not inherit either control endpoint; otherwise parent death may not produce EOF. A random launch_nonce/attempt token authenticates this specific launch. It is not an external credential, but its receipt/input file is still private, run-confined and not exposed in generic UI output.

The required order under the M2 run owner is:

1. Validate capabilities/handles/args, cancellation, persisted approval, remaining wall and expense. Persist a unique attempt reservation and dispatch_intent with job_id, attempt_id and launch_nonce before Popen.
2. Guardian starts without importing/initializing the scientific engine or spawning descendants. It obtains its own PID, PGID, session ID and OS-reported process create_time; verifies pid == pgid == session; writes an atomic, fsynced bootstrap receipt in the already confined attempt directory; and sends a bounded HELLO carrying the nonce and identity on the inherited channel.
3. Parent verifies the nonce, actual Popen PID, process identity and fresh group/session membership. Persist/fsync launch_identity and execution_authorized events, then send GO for the same attempt/nonce. Only GO permits the scientific child to start. The guardian validates the fixed adapter and input again.
4. Before GO, EOF, a malformed command, cancellation or a short bootstrap timeout exits without scientific work. After GO, parent-channel EOF enters the same bounded group cleanup as timeout/cancel. It must never leave the adapter executing merely because the API parent died.

This closes the parent spawn/identity-event window: a child without GO cannot do science, and its independently fsynced receipt can be checked on restart. A persisted authorization without confirmed delivery remains an interrupted/unknown launch, with its reservation retained; it never authorizes automatic replay. If both receipt and confirmed identity are missing, do not assume exit just because time elapsed: retain cleanup_pending until absence/cleanup is established. Use real child barriers to test parent death before HELLO, after HELLO before durable authorization, and after GO.

## 3. Identity and cleanup on Darwin

Use psutil.Process.create_time read from the OS, not a timestamp generated when an event is appended. Bind it to the launch_nonce, authenticated channel/receipt, PID, PGID, session and same-user ownership. PID/create_time alone is not the whole authorization: the private launch handshake and retained guardian make it a particular owned invocation. Do not require an undocumented Darwin kernel-unique-ID API; the installed public SDK exposes group enumeration but not a portable proc_uniqidentifierinfo contract.

Recreate fresh psutil.Process objects for restart checks; do not trust a process_iter cache as identity validation. Enumerate the whole process table and filter with os.getpgid, checking process identity/status and tolerating disappeared PIDs. Do not rely on children(recursive=True): when an intermediate parent exits, its descendants can disappear from that tree view. Apple also exposes proc_listpgrppids for a Darwin-specific enumeration implementation, but no native extension is necessary for this MVP. [psutil process identity/tree documentation](https://psutil.readthedocs.io/stable/), [Apple public libproc interface](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/libproc/libproc.h).

Normal control requests ask the authenticated guardian to clean its own group. Before termination it captures member identities; TERM ignores the guardian's own termination signal while reaching adapter/helpers. Continue checking surviving group members for a bounded grace, even if the scientific child exited and closed pipes. Then KILL surviving owned members/group, reap direct children, and verify no live group members remain. A group-wide SIGKILL also kills the guardian; the parent must reap its Popen child and finish verification. On a clean no-helper exit the guardian can acknowledge cleanup and exit normally. Apply this process to success as well as failure: a valid result plus abandoned helper is not done.

If the parent is gone, guardian performs the same cleanup on EOF, including KILL escalation. The reopened API obtains the free run lock, checks receipt/identity and reconciles cleanup. If the guardian still owns cleanup, observe it for the bounded cleanup window rather than starting replacement work. An unrelated PID with a mismatching creation identity is never signaled. A PGID integer alone, permission error, missing identity, or inconclusive enumeration produces cleanup_pending. If the original guardian is gone, signal only independently verified known survivors; do not kill a newly observed group merely because its PGID matches an old integer. Discovery/cleanup failures are visible and block replacement attempts.

A zombie is not a running helper, but direct children still require wait/communicate. On Darwin the supervisor cannot waitpid arbitrary reparented grandchildren; report their verified non-running/disappeared status and allow their actual parent/launchd to reap them. Preserve known member identity evidence so PID reuse does not become a false live/dead conclusion.

## 4. Keep events and M2 accounting authoritative

A per-run jobs.sqlite index is sufficient. Acquire the existing M2 run owner first, reconcile authoritative events, then take a separate short per-run transition lock before BEGIN IMMEDIATE on the job index for claim/CAS. Never hold an index transaction while waiting to acquire the run owner. Append/fsync job_claimed before updating/committing the row. If the row update fails, replay the already durable event; a rolled-back row cannot authorize a second claim. Parent and guardian must not independently append competing terminal run events: guardian reports bounded lifecycle evidence, the owner commits scientific/job state.

Extract a shared M2 reserve_attempt(attempt_id, root_call_id, tool, ...) primitive used by Run.call and queued execution. It checks approval/cancel/budget and appends one budget_reserved unit, with identity-based idempotency; queue submission does not reserve. Existing egress reservations remain their separately audited policy. A real launch failure, bootstrap interruption or unknown Popen outcome retains the unit. A retry requires an explicit new attempt and the existing finite root allowance. Never wrap queued dispatch in a second charged Run.call interval.

Use one active owner interval for supervision and cleanup; the guardian's timing is diagnostic, not another debit. Persist a dispatch start/remaining allowance so an interrupted owner can be conservatively reconciled once; add actual restart cleanup time once. Idle queued/offline time is free. Budget exhaustion never prevents cleanup. Done requires validated output objects, confirmed cleanup and a terminal CAS for that attempt. Use one short `transitions.lock` shared by job cancel, run-wide cancel, reservation eligibility and terminal commit; cancellation must never acquire the long execution owner. Acquire locks consistently: run owner when needed → transition lock → index transaction → event append lock. Do not hold the transition lock during worker execution, pipe draining, cleanup or result-object construction.

Persist/validate candidate output objects before the final short critical section; an unreferenced object is not a completed scientific result. Under the transition lock, reread the active attempt, cancellation state and prior terminal event, choose exactly one outcome, append/fsync the authoritative terminal event, then update its index row. Job/run cancel uses the same short lock to check terminal state and atomically publish its cancel token/event. Thus a cancellation winning the lock before success commit prevents done even if the object was just created; a success already committed makes later cancellation return already_terminal. Reserve eligibility likewise rechecks cancellation and appends its reservation under this lock, so a queued cancel winning first consumes no unit. Preserve the existing separately signalable run-wide cancellation, but route its publication through this shared short guard. A plain cancellation precheck followed later by unguarded terminal append is not a CAS and is insufficient.
