## Selected product

Offer predefined local analysis goals with explicit input selectors, a concrete plan preview, separate plan approval and scientific approval, step-by-step execution, cancellation/recovery, result navigation and evidence-linked reports. Label every generated plan `source=local_rules`, never model intelligence. Freeform natural-language planning and model-assisted scientific execution remain unavailable with a specific explanation: separate scientific projection/consent and a new approved live-call allocation are required. The historical four M8 calls are exhausted. M8 viewer consent confers no workflow/model/scientific authority. No provider call, external structure, arbitrary tool name, script, URL, executable, filesystem path or user-defined expression is accepted.

Initial supported goal templates:

| Goal | Explicit inputs and fixed steps | Existing lane |
| --- | --- | --- |
| Inspect one ligand | Exact selected structure/prepared source, preparation policy if needed, exact ligand, cutoff/categories; optional prepare → geometric contacts → FreeSASA → respective saved reports | Run.call for preparation/contacts/SASA; existing report builders |
| Measure atoms | Exact accepted source and two M10 AtomRefs → distance → report | M10 Run.call + report |
| Compare structures | Exact reference/moving handles and full explicit M10 CA-pair map → alignment → report | M10 Run.call + report |
| Assign chemical interactions | Accepted M11 imported chemistry/input handles, exact receptor/ligand record/mapping and preparation acknowledgments → required M11 conversion/calculation steps → report | M11 durable jobs; no inline inference |
| Find cavities | Accepted source/model, explicit chains and M12 exclusion policy → detector projection/detection → report | M12 declared runtime preparation and durable job lane |
| Minimize protein | Exact supported source and protein_only/rebuild_pH7 acknowledgments → OpenMM job → method report | Existing durable OpenMM job lane |

These presets expose full supported lanes rather than one monolithic arbitrary-tool dispatcher. Chemistry uploads/import decisions happen in the existing M11 UI before planning; no hidden protonation or graph inference during plan generation. Missing ligand, ambiguous atom map, absent engine, incompatible version or unsupported source gives a visible prerequisite/block reason and no executable substitute. Never choose the first ligand, auto-align chains, substitute a detector, or rank mutations from available geometry/energies. Existing plain controls remain usable independently.

## Immutable plan contract

Store `analysis_plan@1`, kind `analysis_plan`, with schema, `planner=local_rules@1`, goal enum, compatibility manifest, normalized explicit inputs/decisions, ordered steps, fixed limits, unmet prerequisites and `plan_only=true`. A plan is not a measured result. Its hash excludes timestamps, approvals, request IDs, progress and browser identity. Identical content deduplicates; edits create a new handle and invalidate approval for the new execution. Names/notes, if offered, are bounded escaped local display text and never code, paths or egress.

Each step has generated stable `step_id=s01…s08`, fixed operation enum, operation version, lane enum (`run_call`, `durable_job`, `report`), accepted input/output kind+schema pairs, normalized fixed parameters, and dependencies only on earlier steps. A binding is either `{kind:"existing",handle,expected_kind,expected_schema}` or `{kind:"step_output",step_id,output_name,expected_kind,expected_schema}`. No string interpolation, recursive expression, arbitrary JSON pointer or dynamic tool/provider selection. Server compiles from checked-in templates; client cannot submit executable steps. Selection decisions include full source/model/auth/label/insertion/atom identity and explicit method assumptions. After preparation, revalidate the selected identity against actual prepared bytes; do not silently remap a removed ligand/atom.

Compatibility records exact tool/protocol/report schema versions, method/dependency manifest handles or hashes and the planner template version. Revalidate at approval and dispatch. If accepted M11/M12 exported protocol IDs differ from prospective names, map them once through a reviewed internal adapter table; do not add aliases claiming unsupported behavior. Changed implementation compatibility requires a new plan or explicit blocked result, never silent reinterpretation of old content.

Planning may read/validate already stored bytes/metadata/capabilities and ordinary pure preflight; it cannot call scientific implementations, infer chemistry, submit jobs, create prepared molecular results or produce numerical previews. Costs are fixed resource ceilings/known remaining budgets, not fabricated runtime/accuracy predictions. Display deferred bindings and unmet prerequisites honestly. Default maximum8 steps,100 plans/executions per run,64KiB plan JSON and24 physical scientific attempts per execution; input limits of each method also apply. Total workflow active execution wall ceiling1800s, further bounded by existing run/step budgets. Plan creation itself is not an expensive scientific attempt.

## Dry-run and approvals

M13 dry-run always stops at immutable plan/validation output, including cheap preparation/contact/distance tools. Existing `Run.call` dry-run executes cheap tools and only stubs expensive ones; **do not use that behavior to implement workflow dry-run**. Never submit a job or build measured reports in workflow dry-run. A dry-run execution cannot be promoted in place; create an explicit real execution of the reviewed plan in an eligible run. Existing nonworkflow dry-run semantics remain unchanged.

Plan approval is a durable event bound to `(execution_id, plan_handle, canonical_plan_hash, exact step set, compatibility manifest)` and visibly says which actions/results are authorized. It does not set `expensive_first_call`, scientific job approval, online consent or budget limits. Real expensive work still requires the existing ordinary scientific approval flow; prior valid run scientific approval may satisfy that gate, but never substitutes for this plan's approval. UI displays these two approvals independently and cannot accept a stale plan approval after inputs change. Approval/revocation are strict recorded actions; revocation blocks future steps and invokes the scoped cancellation behavior for owned in-flight work. No blanket approval to future plans or automatic limit increases.

## Actual runtime integration and execution identity

Inspected baseline APIs: `Run.call(...,decided_by="rule",execution_mode="autonomous",branch_id=...)` owns execution via `_mutation/_owner`, validates arguments/caches and records tool_called/tool_succeeded; `Run._transition()` is a short cross-process state lock. `Run.cancel()` writes the persistent whole-run cancel marker and therefore **must not implement workflow Stop**. `JobQueue.submit/start/request_cancel/retry` retain durable job ownership/attempt semantics. Existing `inspect_complex@1` is a fixed legacy workflow with causal event verification; preserve its behavior and reports, not its limitations as permission for new crash gaps.

Create a mutable event-backed execution record referencing the immutable plan. Strict status meanings: awaiting_approval, ready, executing, waiting_job, awaiting_scientific_approval, blocked, failed, cancelled, complete (plus plan_only). Execution progress contains exact resolved input handles, output/report handles, durable child call/job IDs, attempt counts and causal event links. Reads/list/reopen never execute, retry, regenerate reports or automatically resume. Explicit Advance performs at most one next scientific/report step or one job transition; a bounded polling GET may observe an owned job's durable outcome but cannot spawn the next step. UI provides usable Start/Continue-next-step, job approval/start, retry where permitted and Stop controls. No background autonomous loop or parallel scientific branch is introduced.

Serialize workflow driver mutations with a short-lived same-run workflow ownership lock distinct from the nonreentrant Run owner; do not hold `Run._transition()` during Run.call/job execution. Scientific tools still execute only through Run.call; jobs only through existing supervisor/reservation paths. At most one driver operation per execution is admitted; normal run owner/global job concurrency still arbitrate other workflows/manual work. Busy is a visible wait/retry state, not permission to bypass the owner or spawn a second worker. Report steps use reviewed existing immutable report functions under their normal serialization; they cannot execute scientific methods as a shortcut.

## Durable admission, idempotency and crash recovery

Every mutating route takes canonical request UUID plus expected execution revision. Under a short transition, durably bind UUID→payload hash→execution/operation before child side effects. Same UUID+payload returns the recorded outcome or current pending state without re-execution; conflicting reuse409; stale revision409. Execution/step/operation IDs are generated by the server, typed and same-run. Duplicate Start/Advance/Retry from two tabs must never create competing work.

Persist a step-dispatch record with concrete normalized args, tool/protocol version, expected output types, operation ID and approved plan hash **before** dispatch. Add a narrow internal execution-link field to Run.call/JobQueue/report publication as needed: stable `(execution_id,step_id,operation_id)` travels in child admission/call/cache/job/report events and is not a public arbitrary-event API. Validate that the linked step is approved, next, uncancelled and exact-argument compatible under the same transition as child admission. Do not infer linkage from the most recent tool with the same name or a fragile event-count window.

Close each crash window explicitly:

1. Before child admission: pending dispatch can be reconciled as not started. A future explicit Advance may execute that same admitted operation once after verifying no child evidence.
2. After child admission but before success: recover by exact child operation link and existing runtime orphan/job supervisor semantics. Do not create a second job or silently rerun an interrupted scientific call on GET/restart. Expose interrupted/failed/cleanup-pending and the actual consumed budget. Retry, if allowed, is an explicit new attempt under the same bounded step.
3. After tool_succeeded/cache_hit/job terminal/report object but before workflow_step_completed: reconcile the exact durable child result and append the missing workflow observation without invoking Run.call again, consuming repeat/no-progress guards or creating a new physical attempt. Validate tool/version/key/arguments, handle kind/schema/hash, branch/operation link, native job receipt/cleanup and immutable report evidence.
4. After step completion but before overall execution outcome: rebuild next/complete state from validated completed-step records. Never rerun completed steps.

Cache reuse is explicit and attributed to original physical provenance plus this operation's verified observation. Existing successful manual results can be reused only through normal validated cache rules; job submission deduplication can return an existing job, so record whether the workflow owns the job or merely observes shared/preexisting work. Report publication also needs operation idempotency/reconciliation; a crash-created valid report must not get rewritten. Conflicting/duplicate/corrupt causal records fail closed with a visible recovery error. Events alone restore plan/execution/outputs/reports and consumed budgets with original input paths and all engines unavailable.

## Scoped cancellation and boundaries

Stop immediately appends an execution-specific cancellation event under the short transition; it must work while the long scientific owner is busy. Never call Run.cancel or write its permanent cancellation file. Check this scope before argument resolution, reservation/admission, child start, retries/backoff, step observation and next-step dispatch. Add an internal scoped cancellation callback/token to ToolContext/Run invocation so supported synchronous tools can cooperatively stop; do not weaken existing whole-run cancellation. Existing bounded noncooperative native work may finish before stopping: record its actual physical output/charge, mark execution cancelled and start no downstream work. Never label it physically interrupted unless it was.

For a job created/owned by this execution, call existing JobQueue.request_cancel(job_id), await ordinary cleanup/reconciliation, retain failed/cancelled budget charge and suppress stale result adoption. A shared or preexisting manual job is not cancelled by this execution's Stop: detach the workflow observer, leave the unrelated job intact and explain this in UI. Job ownership must be established atomically at submission, not guessed from matching parameters. Cancellation racing dispatch is checked atomically before reservation/start; an already admitted physical attempt remains truthfully accounted. Cancellation is terminal for this execution; a new explicitly approved execution can reuse completed immutable evidence without resetting run budgets. Other workflows/manual tools in the run remain usable.

## Failures, bounds and scientific_null

Use existing typed failure classes. No automatic changed-input repair, prerequisites execution, backend substitution or scientifically different fallback is authorized. Input/precondition errors block until the user creates a corrected plan; fatal/resource failures are terminal or require explicit bounded retry when the method's existing semantics permit it. Run.call may retain its existing transient schedule(2,4,8s), constrained by run, operation and workflow ceilings; do not wrap another automatic retry loop around it. Durable jobs have no automatic workflow retry. Permit at most one explicit retry of a retryable failed/interrupted step, without resetting previous attempt accounting. Max24 physical attempts includes failed/cancelled native and tool attempts, counted durably before every physical start. Existing expensive-attempt reservation/charging remains unchanged; cheap calls do not consume expensive units merely because workflow attempts are counted. Each method/run's stricter limits prevail. All counters survive restart.

scientific_null is successful empty science: complete that step, generate its normal honest empty report and finish dependent report steps. It does not trigger repeat/repair or imply failure. A missing ligand/required chemistry is an unmet prerequisite, not scientific_null. Repeated cached Advance/GET is not progress; only a new uniquely validated step outcome advances position. Preserve existing Run autonomous branch repeat/no-progress/oscillation guards. Recovery reconciliation must not increment those guards by manufacturing new cached proposals. Plan has no cycles, unbounded branches, recursive workflow invocation or arbitrary “until successful” goals. Waiting for user approval is not claimed compute time; active attempt/backoff and actual waiting limits remain explicit and durable.
