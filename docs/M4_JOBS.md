# M4 jobs implementation and verification handoff

Implementation owner: GPT-6 Sol. This is an implementation report, not an Astra review or phase acceptance record.

## What is implemented

- `backend/mw/jobs/queue.py` stores job intent, claims, attempts, cancellation, cleanup verification, candidates and terminal outcomes as fsynced run events. `jobs.sqlite` is a disposable query index rebuilt from those events. A claim holds the run execution owner, then `transitions.lock`, then a short SQLite `BEGIN IMMEDIATE` transaction; its event is durable before the row update. Job cancellation and terminal publication share the short transition lock. Running cancellation does not wait for the long execution owner. A candidate object and group cleanup event are verified before the terminal compare and swap; a cancellation that wins the lock prevents `done`. Reopened API runs reconcile unclosed jobs; a running job blocks new physical `Run.call` work until cleanup is resolved.
- `Run.reserve_attempt` in `backend/mw/runtime/orchestrator.py` is the single expensive-unit reservation primitive for synchronous `Run.call` and queued attempts. It checks persisted approval, cancellation, wall and expensive allowance, and deduplicates by attempt ID. For jobs it counts unique durable reservations bound to the root job and tool under the transition lock; a reservation interrupted before dispatch intent still increments the reconstructed attempt ordinal. Four such units remain charged over retry/reopen, and the fifth is rejected before another reservation or launch. The queue charges one monotonic interval from post-reservation dispatch through supervision, fallback cleanup, result validation and terminal or cleanup-pending work, including failures. Exhaustion checkpoints after cleanup. Orphan reconciliation records one bounded UTC interval up to the original timeout/allowance, then actual active cleanup time; a terminal event committed just before a crash also has its missing charge settled once. Queue idle and clean offline gaps are free.
- `backend/mw/jobs/guardian.py` is a fixed session/group anchor launched through the absolute virtual-environment executable symlink without dereferencing it, `shell=False`, `close_fds=True`, `start_new_session=True`, one inherited private socket and a minimal fixed environment. It writes an atomic, fsynced receipt containing an OS `psutil.Process.create_time`, PID, PGID, session, UID and random launch nonce, then sends HELLO. The parent verifies the receipt and fresh OS identity, persists identity and authorization, then sends GO. No adapter starts before GO. EOF/STOP leads to bounded group cleanup. On STOP the parent drains authenticated STARTED observations and waits for the genuine matching RESULT within one four-second absolute control/guardian-exit deadline. Timeout or cancellation remains the winning outcome, and the actual direct-child reap attestation is required if guardian cleanup is incomplete. A missing or malformed RESULT remains cleanup_pending after parent cleanup instead of inventing an attestation. Parent and guardian enumerate the full process table by PGID, verify creation identity before signaling, escalate TERM to KILL, and reap direct children. A missing or ambiguous identity leaves `cleanup_pending` rather than authorizing another attempt.
- The only executable adapter in this release is `backend/mw/jobs/lifecycle_fixture.py`, injected through an internal Python constructor for tests. It produces a `job_lifecycle@1` fixture object, never an energy table. Production HTTP input cannot choose a module, executable, environment, path, fixture or command. `rosetta_worker.py` is an inert no-protocol sentinel; it cannot accept arbitrary JSON work.
- `backend/mw/tools/energetic.py` reports four protocols individually: relax, Cartesian ddG, interface analyzer and residue energies. Engine discovery, implementation and validation are separate fields. The checked backend interpreter has no PyRosetta, and no protocol is implemented or scientifically validated. `rosetta_scripts` discovery is separate. Known protocols return a typed unavailable/precondition response with a reason code; unknown protocols and unsafe parameters are input-invalid. Dry-run returns plan-only data with no energy handle. No scientific energy protocol has been tested.
- `backend/mw/api/app.py` exposes `GET /capabilities`, `GET /runs/{rid}/jobs`, `GET /runs/{rid}/jobs/{job_id}`, `POST /runs/{rid}/jobs`, and `POST /runs/{rid}/jobs/{job_id}/cancel`. The existing capability inspector displays each unavailable protocol. The job API returns status and links without the private launch nonce, owner token or process identity. No public route dispatches a fixture or a production energy job in this release.
- `backend/pyproject.toml` declares `psutil>=7.2.2` directly.

## M4-6 ownership and harness invocation correction (2026-09-24)

`JobQueue._cleanup_owned` now retains an immutable PID/create-time/UID cohort admitted only when the original guardian identity matches immediately before and after a process-group scan. Every TERM/KILL request for an admitted member passes through `_signal_member`, which freshly checks its identity and group. The parent signals known descendants before the guardian, leaving the anchor alive during descendant cleanup when possible. Once the anchor is lost, later PGID occupants are not admitted; an unverified remaining member makes cleanup return false and leaves the job pending. The parent fallback no longer uses `killpg`, so it cannot bypass cohort authorization after a race. The guardian's own group cleanup remains a separate path while it is the live owner.

Four new deterministic, no-OS-signal cases cover a new stranger after anchor loss, TERM then KILL of an authenticated survivor, anchor loss during enumeration with a known survivor plus a stranger, and reuse of a known member's PID with a different creation time. The preexisting real timeout, cancellation and parent-death tests remain in the suite. The independent Astra probe at `/tmp/protview-qa/m4-astra-identity-probe.py` was neither changed nor claimed as run by this worker; root will run it and the actual host process checks after this correction.

`scripts/execute.py` now invokes `codex exec --json` while retaining the pinned Sol/Astra models, sandbox choices, `--enable hooks`, trusted hook hash/config preflight, and review report path. It checks ANSI-normalized runtime stderr for hook trust diagnostics, requires a valid JSONL thread with a completed turn, and rejects nonzero exit status, top-level `error`, and `turn.failed`. It does not inspect nested `item.*` agent or tool text for trust. Runner tests cover quoted hook/test prose in those items and the genuine failure paths. ## M4-7 cross-job admission correction (2026-09-24)

`Run.reserve_attempt` now rechecks the shared `_check_jobs_clear` invariant inside its short transition lock, immediately before any new physical-attempt reservation. The long run owner already serializes execution. A prior job with a durable dispatch intent and no terminal state blocks another claimed job, including after a new `Run` and `JobQueue` rebuild from events. `execute_claim` persists `job_blocked` with `job_cleanup_pending` and raises the typed precondition; the blocked job remains claimed with its owner token and no attempt ID, ordinal increment, budget debit, dispatch intent, launch or wall-time charge. Repeated blocked calls do not append duplicate blocked events. Verified cleanup plus a terminal event for the prior job permits the claimed job to resume and make one normally charged attempt. Job and run cancellation still use the short transition lock without waiting for the long owner.
