# 0027. M19 후보 일괄 도킹은 한 작업이 새로 계산하는 행마다 1단위를 쓰고, 행 결과는 단독 M18 결과와 같은 객체이며, 예산 부족은 사람이 승인한 증액으로만 푼다

- 상태: 채택 (사용자 결정 2026-10-03, M19 명세 확정 때 사용자가 추천안을 골랐다. 아래 "조율 세션이 정한 것"은 사용자가 최종 확인에서 바꿀 수 있다)

## 배경
M19의 여는 시나리오는 "building block 교체 설계, 여러 리간드 비교"(로드맵 M19)다. M17 후보 집합의 후보 여러 개를 같은 수용체·상자·seed·방식·값으로 도킹해 후보별 qvina 점수를 한 표에서 나란히 보고 보고서로 남긴다. M18 도킹은 한 번에 리간드 하나이고 결과를 서로 묶지 않았다. 위험은 네 가지였다: 후보마다 설정이 달라져 "같은 설정끼리만 나란히 볼 수 있다"(M18 한계 문장 2)는 전제가 깨지는 것, 한도·시간이 조용히 넘거나 잘리는 것, 일부만 끝난 일괄이 전부 끝난 것처럼 보이는 것, 계산하지 않은 행이 0점으로 보이거나 정렬에서 0으로 취급되는 것. 또 후보 50개·2시간짜리 일괄은 run 기본 예산(비싼 계산 8회, 활동 시간 1800초)에 걸리는데, 기존 규칙은 "한도를 바꾸려면 따로 기록된 변경"만 말하고 그 변경을 사람이 HTTP로 할 경로가 없었다(`Run.update_limits`는 테스트에서만 불림).

## 결정 (사용자, 2026-10-03)
- **일괄 = 작업 하나, 새로 계산하는 행마다 비싼 계산 1단위**: 프로토콜 `qvina_batch_dock_v1`(도구 `qvina_dock_batch`) 작업 하나가 행을 차례로 도킹한다.
- **방식은 일괄마다 하나**: `free` 또는 `core_fixed`. 수용체·인스턴스·상자·seed·값도 일괄 전체에서 하나이고 상자는 한 번 계산한다.
- **부모 기준 행은 선택 사항(기본 끔)**: 자유 방식에서만 쓸 수 있고 코어 고정에서는 비활성이며 이유(`batch_parent_not_allowed`)를 보여 준다. 부모에는 고정할 코어가 없으므로 새 방법을 만들지 않는다.
- **후보는 M17 후보 집합에서 고른다**: 서버가 저장값에 평가한 M17 필터 결과 위에서 체크박스로 고른다. 일괄에는 후보 id 목록만 남기고 필터 조건은 남기지 않는다.
- **결과는 후보별 `docking_result@1` + 일괄 요약 `docking_batch_result@1`**: 행 결과는 M18 객체 그대로이며 같은 입력의 단독 M18 도킹과 같은 handle이다.
- **상한**: 후보 50개(+ 부모 행 1), 행당 300초, 일괄 전체 2시간(7200초). 꽉 찬 일괄은 설계상 2시간 안에 끝나지 않을 수 있으므로 시작 전에 안내한다.
- **부분 완료는 끝낸 행을 보관한다**: 취소·전체 시간 소진·작업 중단 모두 끝난 행 결과는 남고 일괄은 `partial`로 보인다.
- **표는 후보별 점수 + 열 정렬만**: 부모 대비 차이 열, 접촉 잔기 비교 표, 순위 열은 없다. 행에서 기존 M18 상세(모드·접촉 표·포즈 SDF)로 이동한다.
- **한도 증액은 사람의 명시적 승인으로, 일괄 시작 때**: 부족한 만큼만 올리고, run 끝까지 유지하며(되돌리지 않음), 이벤트로 기록하고, 사람만 화면에서 부를 수 있다.
- **저장된 결과 자동 재사용, 과금 없음**: 같은 정규화 입력의 결과가 run에 있으면 새로 계산하지 않는다. 이어 하기는 같은 설정으로 새 일괄을 만드는 것이다.
- **활동 시간은 실제 경과만 과금한다.**
- **보고서는 일괄 보고서 하나**(`ligand_docking_batch`). 후보별 M18 보고서는 자동으로 만들지 않고 기존 경로 그대로 쓴다.

## 조율 세션이 정한 것 (사용자가 최종 확인에서 바꿀 수 있음)
- 일괄 고정 문장 B1–B3의 문구(`backend/mw/docking_batch_constants.py` `BATCH_STATEMENTS`).
- 점수 열 = 각 행 결과의 첫 행(자유 "모드 1(엔진 출력 순서)", 코어 고정 "샘플 1(점수 오름차순 나열)")이며 "best"라 부르지 않는다.
- 작업 시간 한도 7800초(작업 안 전체 시계 7200초 + 마무리 여유, 이 프로토콜에만).
- 출력 총량 상한 128 MiB(행 결과 파일 합, 조정 가능한 기본값).
- 시작 때 새 계산 행 수 N단위를 한 번에 예약하고 환불하지 않는다.
- 시도 1회, 자동 재시도 없음: 작업 프로세스 크래시는 `partial`·`worker_failed`로 끝난다.
- 요약은 서버가 만든다(작업 프로세스가 죽어도 만들 수 있게). 재사용 여부·시간·작업 ID는 요약에 넣지 않는다(같은 입력·같은 결과면 같은 handle).
- 닫힌 이유 추가: 입장 `batch_empty`, `batch_too_large`, `batch_parent_not_allowed`, `batch_limit_raise_required`, 행 `candidate_timeout`, `time_exhausted`, `cancelled`, `worker_failed`.
- **착수 확인(T1)이 바꾼 설계**: 사용자는 "행이 끝날 때마다 저장"을 원했다. 그러나 큐의 게시 순서(예약 → 정리 확인 → 결과 후보 → 종료)에서 정리 확인은 작업 프로세스 그룹이 끝난 뒤에만 기록되므로, 작업이 도는 동안 행 결과를 M18과 같은 검증으로 게시할 수 없었다. 그래서 작업 프로세스가 행마다 스테이징 파일을 끝나는 즉시 내구적으로 쓰고, 작업이 어떤 종료 상태(완료·취소·시간 소진·작업 중단·서버 재시작 복구)에 닿든 서버가 그 파일에서 검증 가능한 행을 모두 게시한 뒤 요약을 마지막에 게시한다. 결과적으로 끝난 행은 작업이 끝나기 전에는 객체로 보이지 않지만 작업이 어떻게 끝나든 남는다.
- 한도 증액 규칙: 부족분만 올리고, 증가분은 한 일괄의 필요량(51단위·7800초) 이하이며, 활동 시간 축에는 증액 직후 청구되는 런타임 오버헤드 때문에 다시 부족해지지 않도록 60초 여유를 더한다(조정 가능). 절대 한도에는 상한이 없다. 그래서 사용량이 이미 한도를 60초 넘게 넘은 run은 한 번의 승인으로 부족분이 0이 되지 않을 수 있다(또 한 번 명시적 승인이 필요).
- 재사용 키 = M18 호출 키 전체(작업 모듈 해시 등 pin 포함). M19가 `docking_worker.py`에서 행 계산 함수를 동작 변경 없이 추출해 작업 모듈 해시가 바뀌었으므로, 그 전에 만든 M18 결과는 재사용되지 않고 새로 계산된다(같은 입력의 결과 handle은 같다).
- 새로 계산할 행이 0개(N = 0)여도 run의 첫 비싼 계산 승인은 필요하다. 예약은 0단위 예약 이벤트로 남기고 작업 프로세스와 qvina는 띄우지 않는다. 필요 활동 시간은 60초다.

## 검토한 대안
- 후보마다 M18 작업 하나(일괄 = 작업 여러 개): 작업마다 수용체를 다시 준비하고, 일괄 단위의 상태(`partial`·`stop_reason`)와 한 번의 승인·예약을 표현할 곳이 없다. 사용자가 작업 하나를 골랐다.
- 작업이 도는 동안 행마다 즉시 게시: 정리 확인 전에 저장한 객체를 "검증된 게시"로 인정하는 새 규칙과 `_terminal`·`producer()` 의미 변경이 필요했다. 실행 중 수백 KB 객체 이벤트가 0.05초 감독 폴링의 이벤트 로그 재파싱 비용도 키운다. 위 대체 설계로 대신했다.
- 일괄 전용 결과 스키마(행 결과를 요약 안에 담기): 행 결과가 단독 M18과 다른 객체가 되어 M18 상세·보고서·재사용을 다시 만들어야 한다. 기존 `docking_result@1`을 그대로 쓰고 요약은 handle과 첫 행 점수 사본만 담는다.
- 증액 없이 기본 예산 안에서만 일괄: 비싼 계산 8회 한도에 걸려 후보 8개를 넘는 일괄이 불가능하다.
- 자동 증액·무인 증액, 또는 증액 상한 고정: 무인 증액은 "사람 승인 없는 무인 자율 실행은 하지 않는다"(로드맵)에 어긋난다. 절대 한도 상한을 두면 사용량이 많은 run이 일괄을 못 하게 된다. 증가분만 한 일괄의 필요량으로 묶었다.
- 재사용을 `input_sha256` + 엔진·준비 pin만으로 판단: 작업 모듈 해시가 바뀐 결과까지 재사용하면 "같은 호출 키 = 같은 계산"이라는 M18 캐시 규칙이 약해진다. M18 호출 키 전체를 썼다.
- 점수 열에 행 결과의 최솟값: "best"로 읽히므로 첫 행 사본으로 했다.
- 부모 대비 차이 열·순위 열·접촉 잔기 비교 표·뷰어 표시: 사용자가 뺐다.

## 결과
- 착수 확인(`docs/qa/m19-batch-20261003/preflight.txt`): 수용체 PDBQT를 한 번만 준비해 7행(부모 자유 1, 후보 자유 3, 후보 코어 고정 3)에 써도 모든 행의 작업 출력·`docking_result@1` 내용·handle·`input_sha256`·점수·포즈가 단독 M18과 바이트 동일했다. 행당 시간(exhaustiveness 8)은 자유 32–41초, 코어 고정 5.5–6.2초였다. 결과 하나 239,389–312,672 B, 객체 이벤트 줄 320,327–418,189 B로 51행이면 결과 약 16 MB·이벤트 약 21 MB다. 작업 시간 한도는 `JobQueue.submit`과 API `JobSubmit.timeout_s` 두 곳에 900초 상한이 있어 이 프로토콜만 7800초로 올렸다.
- 이제 run 한도를 HTTP로 바꾸는 경로가 하나 생겼다(`POST /runs/{id}/docking/batches/limit_approval`). 이 경로 밖(도구, M13 분석 흐름 단계, M8 모델 명령, 자율 루프)에서는 한도를 올릴 수 없다. 승인은 첫 비싼 계산 승인을 대신하거나 소진된 사용량을 되돌리지 않는다.
- 일괄이 도는 동안(최대 약 2시간) 그 run의 실행 잠금과 전역 작업 슬롯을 쥐므로 같은 run의 다른 계산·보고서 생성과 다른 run의 비싼 작업이 기다린다. 화면이 시작 전에 이를 안내한다.
- 하지 않게 된 것: 일괄 안에서 방식·상자·seed 섞기, 여러 후보 집합 섞기, 임의 3D SDF 목록 일괄, 코어 고정 부모 행, 포켓 후보 상자, 점수 차이·순위 표시, Mol* 포즈 표시, 작업 실행 중 행 객체 게시.
- 조율 세션이 정한 항목은 사용자의 최종 확인(M19 완료 승인) 때 함께 확인받는다. 변경 요청이 있으면 이 결정을 고친다.
- 규칙 전체: `docs/business-rules.md` "리간드 일괄 도킹 (M19, `qvina_batch_dock_v1`)". API: `docs/contracts.md` "M19 리간드 일괄 도킹". 완료 기록: `docs/tracking/m19-acceptance.md`.
