# 0026. M18 단일 리간드 도킹은 격리된 qvina(QuickVina 2.1) 하나로 하고, 점수는 엔진 이름으로만 부르며, 코어 고정은 구속 형태 샘플에 점수만 매긴다

- 상태: 채택 (사용자 결정 2026-10-02, M18 명세 확정 때. 아래 "조율 세션이 정한 것"은 사용자가 최종 확인에서 바꿀 수 있다)

## 배경
M18의 여는 시나리오는 "리간드 배치와 점수"(로드맵 M18)다. 로컬 수용체 하나와 리간드 하나(사용자가 준비한 3D SDF 또는 M17 후보)를 도킹해 포즈·점수·접촉 표를 만든다. 목적은 M17 후보와 3D 리간드를 정직한 이름의 점수로 배치해 보는 것이며 점수의 "좋음"을 말하지 않는다. 위험은 점수가 친화도·순위로 읽히는 것, 수용체를 조용히 고치는 것(물·금속·altloc 제거, 수소 추가), 서버 프로세스에 RDKit·Meeko가 들어오는 것, 같은 입력이 실행마다 다른 결과를 내는 것이다. 로드맵의 권장 엔진은 Vina였고, 사용자는 엔진을 직접 골랐으며 나머지 질문은 추천안을 골랐다. 구현 중 판단이 갈리면 "틀린 값을 보여 주느니 없음·거부를 이유와 함께 보여 준다"와 "범위를 작게" 쪽을 따른다.

## 결정 (사용자)
- **엔진은 qvina 하나**: QuickVina 2.1(`qvina2`, conda-forge `qvina 2.1.0`, build `h4a521e9_8`, osx-arm64). 일반 Vina·smina·gnina는 쓰지 않는다. 같은 패키지에 든 `vina`(AutoDock Vina 1.1.2) 실행 파일은 설치 기록에 해시만 남기고 호출하지 않는다. 엔진은 코드가 정한 실행 파일 하나이며 요청으로 고를 수 없다.
- **점수 문구**: "qvina 점수(kcal/mol, Vina 계열 스코어링 함수 값. 친화도가 아님)"(표 열 머리는 "qvina 점수(kcal/mol)"). 자유 도킹의 행은 "모드 n(엔진 출력 순서)", 코어 고정의 행은 "샘플 n(점수 오름차순 나열)"이다. "순위·최고·best·최적·개선·결합 강도"는 쓰지 않는다.
- **리간드 출처 둘**: 사용자가 준비한 3D V2000 SDF(`sdf`)와 M17 후보(`candidate`, 후보 집합·후보 id·부모 3D SDF). 후보의 3D 좌표와 수소는 RDKit이 만든 것으로 표시한다.
- **상자 출처 셋**: 입력 리간드 중원자 범위 + 여백(`ligand_range`), 수용체 안에서 뺀 리간드 인스턴스 범위 + 여백(`instance_range`), 직접 입력(`manual`). 사용자가 명시적으로 고른다. M12 포켓 후보로 상자를 만드는 길은 이번에 하지 않는다.
- **상호작용 표는 기하 접촉만**: 4.0 Å 이하 중원자 쌍, M2 원소 규칙(`polar_contact`·`hydrophobic_contact`·`contact`). ProLIF 화학 상호작용 판정은 하지 않는다.
- **뷰어 표시 없음**: 포즈는 표와 SDF 내려받기(모드별·전체)로만 보여 준다. Mol* 표시·저장된 보기·그림 저장은 없다.
- **수용체는 M11 입력 규칙 재사용**: 명시적 수소와 완전한 연결 정보(PDB CONECT 또는 `receptor_bonds@1`), 모델 명시 선택, 수소·양성자화·토토머 그대로. 복합체 파일은 허용하되 비표준 잔기 인스턴스 **하나**를 잔기 7필드로 지정해 뺄 수 있고(일치가 정확히 하나여야 함), 나머지 물·금속·보조인자·다른 리간드·변형 잔기·altloc은 조용히 지우지 않고 목록과 함께 거부한다.
- **코어 고정 = 구속 형태 샘플 + 점수만**: 후보의 코어(부모 중원자 `retained_parent_atoms`) 좌표를 부모 SDF 좌표 그대로 둔 RDKit 구속 형태(coordMap ETKDG, seed 고정, 힘장 최소화 없음)를 만들고, 각 형태에 `qvina2 --score_only`만 매긴다. 구조를 최적화하거나 충돌을 풀지 않는다. 구현은 구속 임베딩 뒤 코어로 강체 맞춤하고 코어 중원자 좌표를 부모 좌표로 **덮어쓴다**. 그래서 저장되는 `core_max_deviation_A`(포즈의 코어 중원자와 부모 좌표의 최대 거리)는 정의상 0에 가깝고, 덮어쓰기 전 구속 임베딩 잔차(착수 확인에서 0.118–0.125 Å)는 기록하지 않는다. 이 값을 "임베딩이 코어를 얼마나 지켰는가"로 읽으면 안 된다.
- **재현성**: seed는 사용자가 직접 넣는 정수(필수, 0–2147483647), `--cpu 1` 고정. 같은 정규화 입력·값·seed는 같은 호출 키·같은 handle이다.
- **설치는 새 격리 환경 둘**: qvina conda 환경(`.deps/qvina/env`)과 파이썬 작업 환경(`.deps/docking/venv-locked`: RDKit 2026.3.6, Meeko 0.8.0, MDAnalysis 2.10.0, gemmi 0.7.5와 의존). MDAnalysis는 수용체 화학 추론을 M11과 같은 방식(`MDAnalysisInferrer`)으로 하려고 넣었다. 기존 `.deps/prolif`·`.deps/fpocket`은 건드리지 않는다.
- **최소 보고서 포함**: `analysis_type: "ligand_docking"`, 도킹 결과 하나당 보고서 하나. 비교·일괄은 M19다.

## 조율 세션이 정한 것 (사용자가 최종 확인에서 바꿀 수 있음)
- 제출 전 확인 세 항목(M11 방식): 입력 양성자화·수소를 그대로 쓴다, AutoDock4 원자 유형·부분 전하는 Meeko가 정한다, 수용체는 강체이며 양성자화·최적화를 하지 않는다. 하나라도 빠지면 `acknowledgement_missing`.
- 후보 출처 표시: 자유 도킹은 RDKit 형태 하나를 시작점으로 썼다는 한계 문장 10, 미지정 입체 중심의 입체를 RDKit이 임의로 정했다는 한계 문장 11(`unspecified_stereo_centers` > 0일 때).
- 상자 밖 중원자 수(`atoms_outside_box`)와 포즈–수용체 최소 중원자 거리(`min_heavy_atom_distance_A`)는 기록·표시만 하고 모드를 거르거나 점수를 보정하지 않는다.
- 도킹 1회 = 비싼 계산 1단위(기존 `JobQueue` 경로, run 단위 첫 비싼 계산 승인).
- 고정 한계 문장 11개(`backend/mw/docking_constants.py` `LIMITATIONS`, 조건별로 순서대로 포함).
- 보고서 금지어 검사의 예외: 고정 한계 문장과 문자 그대로 같은 줄은 건너뛰고, 그 밖의 줄은 고정 점수 문구(`SCORE_LABEL`, "친화도가 아님"을 포함)를 지운 뒤 나머지를 검사한다. 명세 9절의 "고정 한계 문장과 같은 줄만 제외"보다 한 가지 넓다(점수 문구 자체가 금지어 "친화"를 담고 있기 때문).
- 수용체 PDBQT 경로: Meeko 수용체 준비(`Polymer`)가 아니라 M11 화학 추론(MDAnalysis 2.10.0 `MDAnalysisInferrer(max_iter=200, sanitize=True)`)으로 만든 RDKit 그래프를 공유 결합 조각마다 Meeko `MoleculePreparation`에 넘겨 AD4 유형·Gasteiger 전하를 받고, 입력 순서·입력 좌표로 ATOM 줄을 쓴다. 리간드는 Meeko 리간드 준비(`MoleculePreparation(rigid_macrocycles=True)`, 고리 형태는 입력 그대로)를 쓴다.

## 검토한 대안
- 일반 AutoDock Vina, smina, gnina: 사용자가 qvina만 골랐다. smina를 쓰지 않으므로 openbabel(GPL) 의존이 설치되지 않는다. 두 엔진 비교는 범위 밖이다.
- Meeko 수용체 준비(`Polymer.from_pdb_string`): 공개 준비 예제에서 모르는 잔기 이름(HSD/HSE)의 템플릿을 files.rcsb.org에서 내려받으려 했고(착수 확인에서 차단기가 막음), 템플릿을 지정해도 합쳐진 말단 캡 잔기 4개가 불일치했다. `allow_bad_res=True`는 그 잔기를 조용히 지우고, 출력이 원자 이름을 템플릿 이름으로 바꿔 식별자 규칙과도 맞지 않는다. 그래서 쓰지 않는다.
- MDAnalysis 없이 화학 추론을 새로 구현: M11과의 동등성을 다시 검증해야 한다. MDAnalysis를 작업 환경에 넣고 M11 인자를 그대로 썼다(ProLIF 잠금과 같은 wheel).
- 코어 원자를 엔진이 고정: Vina 계열은 원자를 고정하지 못하므로 구속 샘플 + 점수만으로 정했다. 맞춤만 하고 이탈(약 0.12 Å)을 기록하는 방법 대신 덮어쓰기를 골랐다(명세 "코어 중원자는 부모 좌표 그대로").
- 포즈 ProLIF 상호작용, 포켓 후보 상자, Mol* 포즈 표시: 사용자가 이번 범위에서 뺐다.
- 기존 `.deps/prolif/venv-locked`에 Meeko 추가: 잠긴 환경을 바꾸면 M11·M17 검증을 다시 해야 해서 새 환경 둘로 했다.

## 결과
- 착수 확인(`docs/qa/m18-docking-20261002/preflight.txt`, 공개 준비 도킹 예제이며 실험 검증 아님): 수용체 PDBQT를 위 경로로 만들 수 있었다(Meeko 자체 수용체 경로와 원자 2,894개에서 AD4 유형 불일치 0, 전하 차 ≤ 0.004). 같은 seed·`--cpu 1` 두 번의 출력 PDBQT가 바이트 동일했다(stdout은 검색 시간 줄만 다름). 공개 예제 재도킹에서 모드 1 중원자 RMSD 1.300 Å, 기준 포즈 `--score_only` −12.21087(kcal/mol, 상자 인자 없이도 같은 값). 이벤트·객체 크기 한도는 코드에 없고, 모드 8개 접촉 포함 결과 형태 JSON은 239,478 B였다. 결과 객체 한도 4 MiB 안에 들도록 모드당 접촉 상한을 500행으로 두었다(`MAX_CONTACTS_PER_MODE`, 넘으면 `resource_exceeded`).
- 조율 세션이 정한 항목(확인 세 항목, 입체 임의 선택 표시, 한계 문장 11개 등)은 사용자의 최종 확인(M18 완료 승인) 때 함께 확인받는다. 변경 요청이 있으면 이 결정을 고친다.
