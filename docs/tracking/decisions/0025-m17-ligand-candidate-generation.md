# 0025. M17 리간드 후보는 한 부위를 고정 교체·사용자 반응 규칙으로 바꾼 2D 그래프이며, 모두 보관하고 필터는 저장값에 적용한다

- 상태: 채택 (사용자 결정 2026-10-01, M17 명세 확정 때)

## 배경
M17의 여는 시나리오는 "부분 교체 후보 만들기"다. 부모 리간드 SDF에서 사용자가 고른 부위를 building block이나 반응 규칙으로 바꿔 후보를 만들고, 후보마다 RDKit 속성과 PAINS 구조 경고를 붙여 표와 보고서로 남긴다. 후보를 M18 도킹(코어 고정/자유)으로 넘기는 것이 목적이며, 후보의 "좋음"을 말하지 않는다. 위험은 속성·필터 결과가 약물 유사성·활성 판정으로 읽히는 것, 원자 번호가 RDKit 내부 인덱스와 섞이는 것, 서버 프로세스에 RDKit이 들어오는 것, 필터를 바꿀 때마다 후보를 다시 만들어 기록이 늘어나는 것이다. 사용자는 모든 질문에서 추천안을 골랐다. 구현 중 판단이 갈리면 "틀린 값을 보여 주느니 없음·거부를 이유와 함께 보여 준다"와 "범위를 작게" 쪽을 따른다.

## 결정
- **생성 방법 두 가지**: 고정 교체 `replace_single_bond_v1`(부위와 그 수소를 떼고, 교차 결합의 코어 쪽 원자와 block 표시 원자의 이웃을 단일 결합으로 잇는다)과 사용자가 직접 쓴 반응 SMARTS `user_reaction_smarts_v1`(반응물 템플릿 정확히 2개(부모 쪽 첫째, block 쪽 둘째)·생성물 1개, 첫째 템플릿이 맞춘 부모 원자가 모두 부위 안일 때만 적용). 요청당 규칙 0–10개, 규칙 텍스트 4 KiB 이하, `rule_id`는 요청 순서의 `user_<n>`. 고정 교체만, 규칙만, 둘 다 쓸 수 있고 둘 다 끄면 거절한다. 반응 규칙·building block 출처는 사용자 정의·사용자 파일뿐이다(자동 다운로드·벤더 카탈로그 없음).
- **부위 모양**: 부모 중원자의 비어 있지 않은 집합이며 코어도 비어 있지 않고, 부위와 코어를 잇는 결합이 정확히 1개이며 단일 결합이다. 연결이 2개 이상인 링커 교체, 부위 자동 제안은 하지 않는다. 서버가 RDKit 없이 점검 객체의 결합 목록으로 검사한다(이유 `site_empty`, `core_empty`, `crossing_bond_count`, `crossing_bond_not_single`, `site_atom_unknown`).
- **부모 입력**: V2000 SDF 레코드 1개(기존 `ligand_sdf` 가져오기, 레코드 수는 점검이 `record_count`로 검사), 연결된 단일 분자, 중원자 ≤ 256, 허용 원소 H C N O S P F Cl Br I. 수소·양성자화·토토머는 입력 그대로이며 검사·추가하지 않는다. 원자 번호는 SDF 원자 블록 1-기반 순번(수소 포함)이다.
- **building block**: 여러 레코드 V2000 SDF(`building_blocks_sdf`)와 `SMILES 이름` 줄 목록(`building_blocks_smiles`) 둘 다. 표시 원자(원자번호 0: SMILES `*`, SDF `*`/`R#`)가 정확히 1개이고 그 이웃이 단일 결합 중원자 1개인 block은 고정 교체 전용, 표시 원자가 없는 block은 규칙 전용이다. 쓸 수 없는 조합은 오류가 아니라 규칙별 `not_applicable` 개수다.
- **후보는 모두 보관, 필터는 저장값에 적용**: 후보 집합은 필터와 무관하게 한 번 만들어 저장한다. 속성 8개(`mol_weight`, `crippen_logp`, `hbd`, `hba`, `tpsa`, `rotatable_bonds`, `heavy_atoms`, `formal_charge`)와 PAINS A·B·C 일치를 후보·부모 모두 항상 계산한다. 필터(속성별 선택적 min·max, `pains_exclude`)는 화면 읽기와 보고서 시점에 서버 순수 함수가 저장값으로 평가한다. 기본 범위는 없다(미리 채우지 않음).
- **작업 두 개, 각 승인·예산 1단위**: 점검 `rdkit_inspect_v1` → `ligand_inspection@1`, 생성 `rdkit_enumerate_v1` → `ligand_candidate_set@1`. 번호 붙은 2D 그림이 RDKit을 요구하므로 점검도 작업이다. 둘 다 기존 `JobQueue` 비싼 작업 경로(run 단위 첫 비싼 계산 승인, 예산, 취소, guardian)이고, RDKit은 `.deps/prolif/venv-locked` 인터프리터의 `mw/jobs/ligand_worker.py`에서만 import한다. 생성 작업은 규칙 텍스트를 받지 않고 서버가 점검 객체에서 `valid` 규칙만 꺼낸다.
- **입체**: 부모 코어의 입체는 유지하고 새로 생긴 입체 중심은 미지정이다. 입체이성질체는 열거하지 않는다. 사라지거나 모호해진 입체는 `stereo_flag`(`none | parent_stereo_lost | new_unspecified_center`)로 표시한다. 중복 판정은 입체 포함 정규 SMILES 기준이고, 후보 id는 그 SMILES의 SHA-256 앞 16 hex(`c_…`)다.
- **상한**: block 1,000개(두 라이브러리 합산, 가져온 순서대로, `block_limit_reached` 표시), 저장 후보 2,000개, 원시 생성물 시도 20,000개, 입력 파일 10 MiB. 후보·시도 상한 도달만 결정적 순서에서 멈춘 부분 결과를 저장한다(`limit_reached`, `stop_reason`). 시간 초과·취소·크래시는 결과를 저장하지 않는다.
- **2D 전용**: 후보는 SMILES이며 3D 좌표·도킹·점수·합성 가능성은 없다(M18 이후). 구조 뷰어(Mol*)에 후보를 표시하지 않는다.
- **보고서**: 새 `analysis_type: "ligand_candidates"`. 증거는 계산값(`computed`) 요약뿐이다: 부모 속성, 개수·거부 이유별 개수·상한, 부위, 규칙 텍스트, 필터별 통과 개수 등 `count_where` 파생값(저장 행에 조건을 적용해 검증할 때마다 다시 셈). 후보를 행 단위로 증거에 묶지 않는다(후보 전체는 화면 표).
- **화면**: 리간드 설계·탐색 탭의 "사용할 수 없음" 안내를 새 화면으로 바꾼다(단백질 공학 탭 안내는 그대로). run 선택은 계속 구조 분석 탭에만 있다.

## 검토한 대안
- 반응 규칙만 또는 고정 교체만: 사용자가 둘 다를 골랐다.
- 그림 클릭으로 부위 지정: 원자 표 체크로 정했다(그림은 `<img>` 표시만).
- 필터를 생성 입력으로 받기: 필터를 바꿀 때마다 다시 생성·저장해야 하고 같은 후보가 중복 저장된다.
- 서버에서 2D 그림·규칙 검증: 서버 프로세스에 RDKit이 들어온다(금지).
- 점검을 무료 동기 도구로: RDKit 작업 프로세스가 필요하므로 작업 경로·예산 1단위로 했다. 부모를 올리거나 규칙을 고칠 때마다 점검 1단위가 든다(사용자 승인한 비용, `docs/tracking/findings.md`).
- 링커(연결 2개 이상) 교체, 후보 입체이성질체 열거, 수소 추가·토토머 변경, SA 점수: 범위 밖으로 남겼다.

## 결과
- 착수 확인에서 SMILES `*`, SDF `*`·`R#`가 모두 원자번호 0으로 읽히고 반응·PAINS·SVG가 동작했다. 후보 2,000행 크기는 0.77–3.24 MiB로 이벤트·객체 한도(코드에 없음)와 결과 한도에 걸리지 않았다(`docs/qa/m17-ligand-20261001/preflight.txt`).
