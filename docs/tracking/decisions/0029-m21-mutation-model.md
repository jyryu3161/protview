# 0029. M21 변이 구조 모델링은 M20 후보 하나마다 PDBFixer 곁사슬 + M7과 같은 OpenMM 최소화로 야생형 기준과 변이형을 한 작업에서 만들고, 각 구조의 값만 나란히 두며, 같은 조건 도킹은 단독 M18의 새 수용체 출처로 한다

- 상태: 채택 (사용자 결정 2026-10-04, M21 명세 확정과 착수 확인 뒤 명세 수정 때)

## 배경
M21은 단백질 공학 탭의 둘째 기능이고 여는 시나리오는 "기질 결합을 위한 서열 변경(로컬)"이다(로드맵 M21: 변이 구조 모델링과 전후 비교, 에너지는 엔진 이름 그대로). M20은 후보 목록까지이며 후보 구조·에너지·히스티딘 상태를 정하지 않았다. 위험은 다섯 가지였다: 엔진 값이 ΔΔG·안정성·개선처럼 읽히는 것(서열이 다른 두 구조의 전위 차이), PDBFixer가 변이 잔기 밖을 조용히 고치는 것, 두 구조의 양성자 상태가 달라 "변이 하나의 차이"가 아닌데 그렇게 보이는 것, OpenMM 위상으로 만든 수용체가 M18 화학 추론을 통과하지 못하는 것, M18 확장이 기존 M18·M19 동작과 저장 결과를 바꾸는 것.

## 결정 (사용자, 2026-10-04)
- **모델링 경로**: PDBFixer 곁사슬 재구성 + M7과 같은 OpenMM 최소화(Amber14-all + GBn2, CPU 1스레드, `NoCutoff`, pH 7 수소, 허용 오차 10 kJ/mol/nm, 최대 50회, 단백질만). 새 격리 환경 없이 프로젝트 `.venv`에 `pdbfixer==1.12.0`을 `backend/pyproject.toml`에 고정했다(PyPI 배포는 sdist 하나, SHA-256 `82e54074b33eb00270e9a439c8633fcf82cd3ab7a36561b01425a260c0fc4143`, 665,893 B, `--no-deps --require-hashes`로 설치해 numpy·openmm을 건드리지 않음).
- **FoldX·ProteinMPNN·ESM 등 모델 가중치는 허용하지 않는다.** 회전이성질체 탐색·곁사슬 최적화도 없다(곁사슬 한 가지 형태).
- **에너지는 각 구조의 OpenMM 전위만**("OpenMM Amber14-all + GBn2 전위(kJ/mol)"): 야생형–변이형 차이, 구조 안 최소화 전후 변화량, SASA·접촉 수의 차이를 어떤 필드·화면·보고서에도 만들지 않는다.
- **히스티딘·Cys 양성자 상태**: 두 구조에서 각각 OpenMM이 pH 7로 자동 지정하고(사용자 지정 없음, HIS가 들어간 변이도 거절하지 않음), 모든 HIS·CYS의 변형 이름을 잔기 7필드와 함께 기록한다. 변이 잔기 밖에서 두 구조의 상태가 다르면 그 목록(`protonation_differences`)과 고정 문장 L5를 남긴다. 한쪽에 맞춰 복사하거나 작업을 실패시키지 않는다.
- **PDBFixer는 변이 잔기에만**: M7 사전 검사를 먼저 통과해야 하고(M7 규칙을 완화하거나 입력을 복구하지 않음), 변이 잔기 밖에 원자를 더하려 하거나 좌표가 바뀌면 `unexpected_atoms_added`·`coordinates_changed`로 실패한다.
- **새 이황화 결합은 막지 않고 기록한다**(거리 기준 `createDisulfideBonds`, 변이형에만 있으면 L6).
- **작업 하나 = 후보 하나**: 야생형 기준 구조를 같은 작업 안에서 같은 절차로 만든다(기존 M7 결과를 재사용하지 않음). 비싼 계산 1단위, M7과 같은 승인·예산·guardian 경로(`openmm_mutation_model_v1`).
- **비교 항목 넷**: 변이 위치 잔기 하나의 SASA(FreeSASA, M6 파라미터, 리간드 없음), 변이 잔기 중원자와 다른 잔기 중원자의 거리 접촉(저장된 결합 위상에서 1–3결합 이내 쌍 제외), 각 구조의 OpenMM 전위, **같은 조건 도킹**("재채점"이 아님: 같은 리간드·상자·seed·방식으로 M18 자유 도킹을 두 구조에 각각).
- **뷰어 표시 없음**: 변이 구조를 Mol*에 올리지 않고 저장된 보기·브리지를 바꾸지 않는다. 표와 mmCIF 내려받기만.
- **M18 확장은 최소**: 단독 M18만 새 최상위 키 `receptor_source`(`{kind: "mutation_model", mutation_model, side}`)를 받는다. M19는 코드·이유 집합을 바꾸지 않으며 이 키를 알 수 없는 키로 거절한다. 이 출처일 때만 M18 한계 문장 열두째 "수용체는 변이 모델링으로 최소화한 구조이며 리간드 자세는 이 수용체에 맞춰 조정하지 않았다(리간드 좌표는 사용자가 준 SDF 그대로)."를 맨 뒤에 붙이고, 입장 전용 이유 `mutation_model_invalid` 하나를 더한다. 기존 11문장·순서·이유 집합·가져온 수용체의 입력·결과 모양은 그대로다.
- **명세 수정(착수 확인 D1, 사용자 승인)**: M7 구조는 C 말단마다 OXT가 있어 M11 화학 추론이 이중결합을 `OXT`에 붙이는 일이 있고, M18 `_protein_chemistry`가 그것을 `receptor_prep_failed`로 거부했다(T1: 1UBQ 야생형·I44W·K6H와 합성 Cys 파생 두 구조, 수용체 5개 모두 거부). `receptor_source`가 `mutation_model`일 때만 말단 카르복실의 이중결합이 `O`·`OXT` 어느 쪽이어도(다른 쪽은 단일결합·형식 전하 −1) 받는다. 가져온 수용체의 검사는 그대로이고, 수용체 원자 순서는 저장 mmCIF 순서 그대로다(OXT를 앞으로 옮기지 않음).
- **명세 수정(독립 코드 검토 R2, 사용자 승인)**: `receptor_source`가 `mutation_model`이면 리간드는 `sdf` 출처만 받는다. M17 후보 출처는 기존 입장 이유 `mode_source_mismatch`로 작업 전에 거절한다(열두째 문장의 "리간드 좌표는 사용자가 준 SDF 그대로"가 RDKit이 만든 후보 좌표에는 맞지 않음). 같은 조건 도킹 화면도 후보 출처를 막는다.
- **수용한 대가**: M18 작업 모듈(`docking_worker.py`)·상수(`docking_constants.py`)를 바꿔 호출 키가 묶는 `worker_sha256`·`constants_sha256`이 달라졌다. M21 전에 만든 M18 결과와 M19 행 결과는 같은 입력으로 다시 요청해도 자동 재사용되지 않고 새로 계산된다(과금됨). 저장된 객체·읽기·보고서는 그대로다.
- **M21 보고서에 도킹 점수를 인용하지 않는다**(각 M18 보고서에 둔다).
- **변이 잔기 행**은 원래 7필드와 변이 후 이름(`mutant_resname`)을 따로 저장한다. 구조 mmCIF와 M18 수용체는 표준 이름(HIS·CYS)으로 쓰고 OpenMM 변형 이름(HID·HIE·HIP·CYX)은 `protonation_variants` 기록에만 둔다.

## 착수 확인 뒤 명세에 반영한 설계 선택 (`docs/qa/m21-mutations-20261004/preflight.txt` B1·B2)
- **B1 같은 이름 원자(변형 A)**: PDBFixer `applyMutations`를 공개 API 그대로 쓰므로, 새 잔기 템플릿에 같은 이름이 있는 원래 곁사슬 원자(예: ILE→TRP의 CD1, PRO→TRP의 CG)를 PDBFixer가 남긴다. 그 원자는 입력 좌표를 쓴다. T1에서 같은 이름 원자가 남은 경우 최소화 전 전위가 크게 높을 수 있었다(P38W 변형 A 209,742,676 kJ/mol, 변형 B 58,015 kJ/mol). 두 변형 모두 37경우 모두 최소화가 끝났다. 어느 쪽이 나은 모델인지 주장하지 않는다.
- **B2 좌표 이식**: PDBFixer는 좌표를 nm로 옮겨 담아 마지막 비트가 달라진다(최대 7.1e-15 Å). 변이 잔기 밖은 이름·원소·순서가 같고 차이가 `GRAFT_TOLERANCE_A` 1e-9 Å 이하일 때만 받고 입력 좌표를 그대로 쓴다. 변이 잔기 안에서도 입력에 있던 원자는 입력 좌표다(C 말단 변이에서 PDBFixer가 지웠다 다시 놓는 OXT 포함, 다시 놓은 위치는 0.35–0.69 Å 달랐음). 새로 놓은 원자만 PDBFixer 좌표다.

## 조율 세션이 정한 조절 가능한 값 (사용자가 바꿀 수 있음)
- 접촉 cutoff 기본 4.0 Å(2.5–6.0, 양끝 포함), 구조당 접촉 행 상한 2,000(넘으면 자르지 않고 `resource_exceeded` `too_many_contacts`).
- 작업 시간: `JobSubmit` 최상위 `timeout_s`(작업 인자가 아니고 호출 키에 들어가지 않음), 이 프로토콜 기본 120초·최대 240초(큐가 프로토콜별로 적용, 범위 밖은 `argument_invalid`). T1에서 1UBQ 작업 하나는 단독 약 23초였다.
- 작업 출력·결과 객체 64,000,000 B, 스테이징 4,000,000 B(M7과 같은 투영), 읽기 페이지(목록 1–100 기본 50, 접촉 1–200 기본 100).
- **호출 키의 의존 파일 해시(독립 코드 검토 R1)**: 호출 키와 시작 때 재확인에 작업 모듈 SHA-256과 함께 작업 모듈이 import하는 프로젝트 모듈 다섯 개(`mutation_model_math.py`, `mutation_model_constants.py`, `jobs/openmm_worker.py`, `tools/openmm_method.py`, `mutation_candidates.py`)의 SHA-256을 넣는다. 이 파일이 바뀌면 기존 결과의 자동 재사용이 끝나고, 대기 중 작업은 시작 때 `worker_version_invalid`로 막힌다.

## 검토한 대안
- FoldX·ProteinMPNN·ESM 가중치: 라이선스·재현성·"점수" 해석 위험. 사용자가 허용하지 않았다.
- 두 구조 전위 차이를 "변이 효과"로 표시: 서열(원자 수)이 달라 비교할 수 없는 값이며 ΔΔG가 아니다. 차이 필드를 만들지 않는다.
- 양성자 상태를 야생형 기준에 맞춰 변이형에 복사: 조용한 가공이다. 각각 자동 지정하고 다르면 기록·L5.
- 기존 M7 결과를 야생형 기준으로 재사용: 같은 작업·같은 설정·같은 seed가 아니면 같은 조건이 아니다.
- 착수 확인 D1의 다른 선택지: 저장 mmCIF에서 OXT를 O 앞에 쓰기(추론기의 원자 순서 의존, 내려받기 파일 순서가 바뀜), 결합 차수를 OpenMM 위상에서 가져오는 새 경로(M18 작업 모듈 변경이 큼), 같은 조건 도킹 제외(시나리오 손실). 사용자가 이 출처에서만 완화를 골랐다.
- 변형 B(변이 잔기를 N·CA·C·O·CB(·OXT)만 남겨 넘김): 명세의 "PDBFixer 공개 API를 그대로, 같은 이름 원자는 PDBFixer가 유지"와 다르다.
- 도킹 결과를 M21 보고서에 인용: 도킹은 M18 보고서 규칙(점수 문구·접촉)을 따르므로 섞지 않는다.

## 결과
- 착수 확인(`docs/qa/m21-mutations-20261004/preflight.txt`): 1UBQ 37경우 × 변형 2 + 합성 Cys 파생 8경우 × 2 = 90회 모두 변이 잔기 밖 원자 추가·좌표 변경 없음, `mutation_modeling_failed` 0건, 같은 입력·seed 두 번 바이트 동일, 결과 JSON 약 0.6 MB(1UBQ). 리간드가 있고 M7 사전 검사를 통과하는 공개 구조는 로컬에 없어 같은 조건 도킹은 1UBQ + 합성 표시 페놀 SDF로 기계적으로 검증했다.
- M18 원자 수 한도(10,000, 수소 포함)는 그대로다. 1UBQ 비율(수소/중원자 1.045)로 보면 중원자 약 4,890개를 넘는 단백질 모델은 M7 한도(중원자 6,000) 안이어도 M18이 `receptor_invalid`로 거부한다.
- 하지 않게 된 것: 여러 후보 일괄, 두 곳 이상 변이, 회전이성질체 탐색, 모델 가중치, 복합체 OpenMM·MD·자유 에너지, 구조 간·구조 안 차이 표시, 뷰어 표시, M19 일괄의 변이 구조 출처, M13 흐름 연동, 야생형 도킹 결과의 후보 간 재사용.
