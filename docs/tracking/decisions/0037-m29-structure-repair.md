# 0037. M29 구조 보완은 사용자가 명시적으로 요청한 전처리 구조 하나에서 승인된 결손 다섯 종류(체인 조각 합치기·곁사슬 원자·C 말단 OXT·내부 틈 1–20잔기·MSE→MET)만 PDBFixer 작업으로 채운 새 `prepared_structure@1`과 보완 기록 `structure_repair@1`을 게시 전 검증을 모두 통과할 때만 만들고, 그 구조는 모델링 경로(M20 → M21·M23·M24·M25, M21 수용체 출처 M18)에서만 받고 나머지는 기본 거절하며, 하류 결과에는 "보완 구조 기준"을 화면·읽기·보고서로 드러내고, M21 시간 상한(120/240초)과 호출 키 해시 파일은 그대로 둔다

- 상태: 채택 (사용자 결정 2026-10-12~13. 명세 확정 전 질문에서 모두 추천안을 골랐고(자유 입력·메모 없음), T1 착수 확인 뒤 M21 시간 상한·명세 정정 둘·RCSB 구조 넷을 따로 정했다. 아래 "조율 세션이 정한 것"은 사용자 선택이 아니며 최종 보고(T20)에서 이의를 받는다). 결정 0029(PDBFixer는 작업 모듈에서만, 관측 좌표 이식 원칙)를 새 작업 하나로 넓힌다. 외부 요청 규칙(결정 0005·0015·0034·0035)과 실호출 할당 규칙(결정 0012)은 바뀌지 않는다.

## 배경
M28 판정 뒤 사용자가 "이 플랫폼은 범용 플랫폼인데, 특정 단백질만을 대상으로 하는게 아니야."라고 했다. 변이 구조 모델링(M21), 서열 GA(M23), 단백질 JEV 루프(M25), M21 수용체 출처 도킹(M18)은 모두 M7 OpenMM 사전 검사를 입구로 쓰고, M7은 표준 단백질 중원자 템플릿과 정확히 같은 구조만 받는다. 로컬 공개 구조 8개 중 1UBQ만 통과했고(M28 범위 표의 알려진 한계), 사용자가 요청해 받은 STK33 8VF6도 곁사슬 결손 잔기 23개(A 10·B 13), 사슬 안 틈(저자 번호 A 273–285·B 274–284), 두 C 말단 OXT 결손, 그리고 그것을 모두 고쳐도 남는 "같은 저자 체인 이름의 조각 분리"(`A,B,A,B,A,B`) 때문에 막혔다. 1FIN의 "저자 체인 중복" 거절도 같은 조각 분리 때문이었다(진짜 단백질 체인 중복이 아님).

위험은 일곱 가지였다: 보완 구조가 실험 좌표처럼 쓰이는 경로가 하나라도 새는 것, 호출 키 해시 파일·`also_hashed_files`를 "작은 수정"으로 건드리는 것, M20 인계가 원본 구조의 보호(KLIFS 주요 부위 등)를 조용히 잃는 것, 틈 잔기 식별자를 추측하는 것, 관측 원자가 바뀌거나 실패한 작업이 고아 객체를 남기는 것, M21이 보완 구조에서 시간 상한이나 M18 원자 상한에 걸리는 것, 간헐 실패를 숨기는 것.

## 결정 (사용자, 2026-10-12~13)
- ① **플랫폼 일반화 요청 → 구조 보완**(2026-10-12~13): M28 확인·병합 뒤 일반화 요청, 8VF6 한 파일로 점검, "구조보완으로 해."로 정했다. 목적은 특정 단백질이 아니라 일반적인 결정구조가 변이 모델링 경로에 들어가게 하되 어떤 원자가 실험 좌표이고 어떤 것이 모델링 좌표인지 어디서도 흐려지지 않게 하는 것이다. 질문에서 고른 것(모두 추천안): 틈은 메운다(내부 틈만, 말단 꼬리는 만들지 않음, 20잔기 초과는 거절) / 비표준 잔기는 MSE→MET만 / 보완 구조는 모델링 경로에서만 쓴다 / 충돌은 기록만 한다(거절하지 않음) / 하류 결과·보고서에 "보완 구조 기준"(화면과 보고서 모두) / 뷰어에는 올리지 않는다(표·내려받기만) / 검증 구조는 로컬 + RCSB 최대 4개 / 같은 저자 체인의 조각은 이름을 바꾸지 않고 한 체인으로 합친다(처음 고른 "체인 중복 → 거절 유지"는 독립 검토가 조각 분리라는 전제 오류를 찾아 다시 물어 바꿨다) / M20은 원본 구조 기준 참조 결과를 받고 모델링 원자 기준을 표시한다 / M20 저장 형식이 잔기별 "검사 안 함"을 담지 못하므로 저장값은 그대로 두고 읽기 계층이 덮어 보인다 / JEV 전송은 허용하되 경고한다 / M23 보고서는 바꾸지 않고 화면에만 표시한다.
- ② **M21 시간 상한 유지**(2026-10-13): T1 측정에서 보완한 8VF6(단백질 중원자 4,538)의 M21 작업 하나가 1,035초로 상한 240초를 넘었다. 사용자는 상한(`mutation_model_constants.py`의 `TIMEOUT_DEFAULT_S = 120`·`TIMEOUT_MAX_S = 240`, 해시 파일)을 유지하고 한계로 기록하는 쪽을 골랐다(고르지 않은 대안: 상한을 올림(M29에 포함), M29 중단). 상한을 올리는 일은 별도 후속 사용자 결정이다(해시 파일 변경이라 호출 키·골든 재기록이 따르고, 8VF6은 작업 하나에 17분 이상, 서열 GA는 개체마다 그 시간이 든다).
- ③ **명세 정정 둘**(2026-10-13 승인): (a) 새 원자 좌표는 소수 넷째 자리로 반올림해 구조와 보완 기록에 같은 값으로 넣는다(M21이 단백질을 PDBx 텍스트로 옮길 때 `%.4f`로 쓰고 변이 잔기 밖 좌표를 1e-9 Å로 대조하므로 원정밀도는 `coordinates_changed`로 실패한다. T1 측정 4.6e-5 Å). (b) PDB 형식 입력의 틈 잔기 `chain_label`은 보완 구조를 gemmi가 다시 읽을 때 정하는 값이다(SEQRES가 있으면 합성 subchain 이름, 없으면 null).
- ④ **RCSB 내려받기**: 8VF6은 STK33 점검 때 사용자 요청으로 GET 1회(2026-10-13, HTTP 200, 888,122 B). 추가 구조는 T1이 고른 후보 넷 `1RNH`·`4INS`·`1AY7`·`1CLL`을 사용자가 승인해(2026-10-13) 구조마다 `https://files.rcsb.org/download/<ID>.cif` GET 1회로 받았고 넷 모두 HTTP 200이었다(재시도·검색·헤더·키 없음). 실제 JEV 호출은 0이다.

## 조율 세션이 정한 것 (사용자 선택이 아님, 최종 보고에서 이의를 받는다)
1. **사용자 목록 밖의 기본 거절 소비자**: 사용자의 "모델링 경로에서만"을 "목록 밖은 모두 거절"로 읽어 계산 도구(`compute_interactions`·`compute_interface_sasa`·`measure_distance`·`align_structures`·`compile_state`), `POST /inspect_complex`, M7 단독 최소화(제출·사전 검사 읽기), M11 화학, M12 포켓(사전 검사 읽기 포함, M12 닫힌 이유 집합에 코드를 더하지 않음), M13 계획 라우트 입구, M15 번호 대응·M16 참조 주석, M26·M27 연결, 뷰어 세션·의도·보기·그림, 일반 보고서 생성이 422 `input_invalid`·`repaired_structure_not_accepted`로 거절한다. `Run._validated_bound`의 허용 목록 `REPAIRED_STRUCTURE_TOOLS`는 `generate_mutation_candidates` 하나다. 이유: 받는 곳을 열거하고 나머지를 닫아야 새 소비 지점이 생겨도 보완 구조가 실험 구조처럼 새지 않는다(인벤토리 시험이 완전성을 증명).
2. **`repair_policy` 리터럴 `complete_missing_atoms_v1`**(필수 인자): 이유: 모델링 좌표가 들어간 구조가 만들어진다는 것을 사람이 명시적으로 확인하게 한다.
3. **고정 seed(`REPAIR_SEED = 1`, 인자 아님)와 구조당 보완 한 번**: 같은 전처리 구조 = 같은 호출 키 = 같은 보완 구조·기록 handle. 이유: seed를 바꿔 마음에 드는 결과를 고르는 길을 막는다.
4. **뼈대 부분 결손 거절**(`backbone_atoms_missing`): 이유: N·CA·C·O가 빠진 잔기는 관측 뼈대가 아니라 모델링 뼈대가 되어 "관측 원자는 그대로" 원칙을 지킬 수 없다.
5. **manifest의 `repair` 키와 `missing_residues` 새 값 `modeled_internal_gaps`**(틈을 메웠을 때만): 이유: M7 사전 검사와 해시 파일이 `prepared_structure@1`을 요구해 새 스키마를 만들 수 없으므로, 기존 형식 안에서 보완 구조를 판별할 유일한 표지와 사실대로의 전처리 기록이 필요하다(도구 입력 `prepare_structure`의 `leave_gaps` 전용 집합은 그대로).
6. **MSE→MET 예외와 틈 안 MSE 거절**: MSE→MET는 잔기 7필드 보존 규칙의 명시적 예외이며(원래 7필드 ↔ 새 7필드·원자 이름 대응표·레코드 종류 HETATM → ATOM을 기록) SE 좌표를 그대로 SD로 바꾸려고 PDBFixer 호출 전에 작업 모듈이 이름·원소만 바꾼다. 미관측 목록의 틈 잔기가 표준 20종이 아니면(MSE 포함) 틈을 메우지 않고 `unsupported_residue`(`detail.in_gap: true`)로 거절한다. 이유: 관측되지 않은 MSE를 MET로 지어 넣으면 이름 대응의 근거가 되는 관측 원자가 없다.
7. **새 코드 셋**: 입장 거절 `m7_condition_unsupported`(위 거절 코드가 덮지 않고 보완으로 풀리지 않는 M7 거절, `detail.m7_reason`에 M7 코드나 메시지 원문), 작업 실패 `repair_identity_mismatch`(새 잔기 7필드가 목록·서열과 다름)·`repair_record_mismatch`(다시 만든 기록과 저장 바이트가 다름). 이유: 닫힌 거절 집합이 M7 입구 조건을 모두 덮어야 하고, 게시 전 검증의 각 검사가 자기 코드로 끝나야 한다.
8. **보완 화면 위치**: 단백질 공학 탭 맨 위(변이 후보 화면 위) "구조 보완" 영역. 이유: 보완 구조를 쓰는 곳이 그 탭의 모델링 경로뿐이고, 구조 분석 탭·뷰어·저장된 보기·브리지는 건드리지 않는다.
9. **새 보고서 종류 `structure_repair_markdown@1`**(`analysis_type: "structure_repair"`, 보고서 목록 이름 "구조 보완 보고서", 입력은 보완 기록 handle 하나, 주장은 모두 `computed`): 이유: 무엇을 더하고 바꿨는지를 하류 보고서와 별도로 인용할 근거 문서가 필요하다.
10. **고정 문장 문구**: RP1–RP6(보완 기록 `limitations`·화면·보고서, 조건별), SO1–SO3(하류 화면·보고서), JW1(JEV 미리보기·승인). 이유: 모델링 좌표라는 사실을 서버가 정한 같은 문장으로만 말하게 한다(브라우저는 그대로 보임).
11. **결정 번호 0037.**
12. **`chain_ends`의 null 의미**: `first_is_sequence_start`·`last_is_sequence_end`는 파일의 서열·미관측 목록으로 정할 수 없으면 null이며 "판정 불가"이지 "같음"이 아니다(RP4는 값이 거짓일 때만, 화면은 "—(판정 불가)"). 이유: 모르는 것을 참·거짓으로 채우지 않는다.
13. **충돌 기록의 `min_pair`는 분류별**(`protein`·`ligand`·`metal`·`water`·`other`, 상대가 없으면 null, 전체 최솟값은 분류별 값 중 가장 작은 것). 이유: 분류마다 가장 가까운 쌍을 그대로 보여야 기록만 하는 충돌이 한 숫자로 뭉개지지 않는다. 상대가 없는 분류는 개수 0과 `min_distance_A: null`이며 "충돌 없음"으로 읽지 않는다.
14. **기록 키 추가**: `counts.protein_heavy_atoms`(보완 뒤 단백질 중원자 수), `unchanged.input_calc_flag_cleared`, `new_atom_rounding{decimals, max_abs_delta_A}`(PDBFixer 원값과의 차이, 검증기는 0 이상 0.5e-4 이하 범위만 확인), `parameters.new_atom_coordinate_decimals: 4`. 이유: M21 크기 한계와 ③의 반올림·표지 정규화가 기록에서 읽혀야 한다.
15. **새 원자 표지 `_atom_site.calc_flag = c`와 정규화**: 점유율 0은 쓰지 않는다(입력에 점유율 0 단백질 원자가 실제로 있다: 1M17 37개, 1A4I 20개). 입력에 이미 있던 `calc_flag` 값은 `.`로 바꾸고 개수를 남기며, 검증기는 "`c`인 원자 = `added_atoms`"를 양방향으로 확인한다. 이유: T1 측정에서 이 열은 제품 gemmi 읽기·OpenMM `PDBxFile`·PDBFixer·M7 사전 검사가 모두 받고 다시 써도 남는다.
16. **게시 직전 환경 상실은 닫힌 실패 집합 밖으로 기록**: 게시 전 검사 중 설치 템플릿·M7 엔진·프로세스 신원이 없어지면 작업 실패가 `error: precondition`과 `reason_code` `openmm_unavailable`·`process_identity_unavailable`로 남는다(명세 §4.4 집합 밖, 예약 1단위 환불 없음, 객체 저장 없음). 이유: 환경이 없다는 사실을 "증거 무효"로 보이지 않는다(T12 검토가 지적했고 고치지 않고 예외로 적음).
17. **M20 `@3`의 새 `computed` 주장과 새 줄 셋**: statement id `repair_modeled_residue_position_count`(모델링 잔기 위치 수, 읽기와 같은 판정 `mutation_handoff.modeled_residue_view`, subject 키 `reference_not_checked`)와 줄 셋(보호 검사 절의 "모델링 잔기 위치의 … 검사: 검사 안 함(모델링 잔기). 위 표의 상태와 개수는 저장값이며 이 위치를 검사했다는 뜻이 아니다.", 번호 대응 절의 같은 취지 줄, 구조 출처 절의 모델링 잔기 위치 수 줄). 이유: 명세 §5.3이 "검사 안 함(모델링 잔기)"을 보고서에도 요구하는데 저장 집합(해시 파일)은 "해당 없음"으로 담기 때문이다(T12 검토 지적).
18. **R4a/R4b 재정의**: R4a는 `completes` 구간 구조 1HSG를 화면에서 M21 작업 완료(`timeout_s` 240)·M21 보고서 `@2`까지 보이고 합성 표시 페놀 SDF로 같은 조건 도킹 경로를 기계적으로 확인한다. R4b는 8VF6 M21 작업 하나를 `timeout_s` 240으로 돌려 시간 상한 결과(실패·결과 없음·모델 0·1단위 환불 없음·프로세스 정리)를 한 번 관측한다(모델 없음으로 도킹은 `not_observed` `no_model_time_limit`). 이유: ②의 결정 뒤 8VF6로는 M21 완료를 보일 수 없다.

## 이유
- **PDBFixer를 작업 모듈에만 둔다**: 결정 0029와 같은 경계다. 서버 프로세스는 PDBFixer를 import하지 않고(버전은 `importlib.metadata`만) 작업 모듈은 PDBFixer가 **더한 원자만** 돌려준다. 서버가 그 원자를 전처리 구조에 접합하므로 관측 원자는 하나도 작업 프로세스에서 오지 않고, 관측 원자 불변(1e-9 Å)을 서버의 순수 검증기가 확인할 수 있다. `prepare_structure` 정책에 보완을 넣어 서버가 PDBFixer를 import하는 대안은 이 경계를 깬다.
- **기존 형식의 새 `prepared_structure@1`로 둔다**: M7 사전 검사와 호출 키 해시 파일(`mutation_candidates.py`·`sequence_ga_worker.py` 등)이 이 종류·스키마를 요구하므로 새 종류·`prepared_structure@2`는 해시 파일 변경 없이는 모델링 경로에 들어가지 못한다. 표지는 manifest의 `repair` 키 하나이고, handle이 내용 해시이므로 보완 좌표 → 보완 기록 → manifest → 보완 구조 순으로 만들고 기록은 구조 handle을 담지 않아 순환이 없다. 기록에서 구조로는 게시 이벤트 `structure_repair_published`로 간다.
- **게시 전 검증 + 한 잠금 구간**: 관측 원자 불변·추가 원자 목록 일치·새 잔기 식별자·M7 사전 검사(저장하지 않는 읽기 전용 겹침 보기)·기록 재생성 일치를 모두 통과해야 네 객체와 게시 이벤트를 저장하고, 저장과 작업 종료 기록은 취소를 다시 확인한 같은 전이 잠금 구간에서 한다. 실패·취소·시간 초과는 run 저장소에 새 객체를 남기지 않는다.
- **기본 거절**: 받는 곳을 열거하고 나머지를 닫으면 보완 구조 단백질 좌표로 접촉·SASA·포켓 값이 나오지 않고, 인벤토리 시험이 새 소비 지점을 선언하거나 거절하도록 강제한다.
- **M20 인계는 읽기 계층에서**: 원본 구조 기준 참조 결과를 잔기 7필드 정확 일치로 이어 관측 잔기의 보호(8VF6 `klifs_key_site` 일곱 자리 K145·M192·E193·L194·C195·T264·D265)를 그대로 지키고, 저장 집합(해시 파일 형식)은 바꾸지 않은 채 모델링 잔기를 "검사 안 함(모델링 잔기)"으로 덮어 보인다.
- **보고서 형식 버전은 해당할 때만 올린다**: M28 M20 `@2` 선례대로 보완 구조일 때만 새 버전이 만들어지고 저장된 이전 버전은 같은 바이트로 다시 열리며, 보완 구조가 아닌 결과의 보고서·읽기 응답 바이트는 그대로다(골든 불변). M23 보고서·읽기는 해시 파일이라 화면 표시만 한다.

- JEV 전송 본문은 보완 사실을 담지 않고(JW1 경고만), M23 보고서 바이트에도 없다(화면과 같은 후보 집합의 M20 `@3`·보완 보고서에 있음).
- 메운 틈 구간은 단순한 기하로 놓은 가상 좌표이고 충돌은 기록만 한다(예: 1MQ4 보완 곁사슬이 리간드와 1.24 Å, 2.0 Å 미만 5개).
- 작업 경로: `timeout_s` 범위 오류는 API 모델 단계에서 먼저 나와 입장 순서보다 앞설 수 있다(M21과 같음). 시간 초과 실패에는 `detail.reason_code`가 없다(`resource_exceeded`, 메시지 "job timeout"). 취소된 작업은 재시도 대상이 아니라 그 run에서 그 전처리 구조를 다시 보완할 수 없다. 입력 좌표가 소수 5자리 이상이면 PDBx 텍스트(`%10.4f`) 왕복 때문에 `coordinates_changed`로 실패하고 1단위가 과금된다(로컬 구조는 3자리). 네 객체를 저장하는 도중 I/O가 실패하면 추가 전용 로그에 일부 객체가 남고(읽기는 `valid: false`) 재시도가 완성한다.
- 표시 경로: 망가진 보완 기록일 때 루프 만들기·계산 시작·도킹 포기·끝내기 라우트가 이벤트를 기록한 뒤 422/412로 답할 수 있다. 화면은 게시 이벤트로, 서버는 manifest `repair` 키로 판별하므로 게시 이벤트 없이 부분 저장된 객체가 화면 목록에 보일 수 있다(고르면 서버가 422). 내려받은 보완 mmCIF를 다시 올리면 `calc_flag = c`가 남아도 일반 구조로 다룬다(M21 모델 내려받기와 같음).
- M27 `link_kinase_precedents`에는 M16처럼 지도의 구조를 직접 거절하는 방어선이 없다(상위의 번호 대응에서 막혀 닿지 않음). 서버가 설치 템플릿을 읽은 뒤 파일이 바뀌면 캐시 때문에 서버를 다시 시작하기 전까지 412가 나지 않는다(검증 결과는 틀리지 않음).
- 긴 동기 작업 시작(M21 약 2분, 8VF6 보완 약 25–35초)은 Next 프록시가 연결을 끊어 브라우저에 500이 보일 수 있다(작업은 계속되고 화면은 저장된 작업을 읽어 복구한다. M29 이전부터의 동작).
- 검증은 macOS arm64 CPython 3.11에서만 했다. 그 밖의 남은 문제는 `docs/tracking/findings.md`.

## 변경하려면 사용자 결정이 필요한 것
보완 종류 다섯과 순서(`REPAIR_CLASSES`), 거절 이유 아홉과 순서(`REFUSAL_REASONS`), 입장·사용할 수 없음·작업 실패 코드 집합, `repaired_structure_not_accepted`와 받는 곳 목록(`REPAIRED_STRUCTURE_TOOLS`), `repair_policy` 리터럴, `REPAIR_SEED`·구조당 보완 하나, `MAX_GAP_RESIDUES = 20`(조절 가능한 상수이나 바꾸면 분류가 바뀜), 새 원자 소수 자릿수 4와 `calc_flag` 표지, 보완 기록 키 집합·`missing_residues` 값 `modeled_internal_gaps`·manifest `repair` 키, MSE→MET 예외, 충돌 분류·기준 거리, 고정 문장 RP1–RP6·SO1–SO3·JW1, 보고서 statement id(보완 보고서 열하나, 하류 `repair_added_residue_count`·`repair_added_atom_count`, M20 `@3` `repair_modeled_residue_position_count`)와 형식 버전 규칙(보완 구조일 때만 새 버전), 상한(스테이징 입력·결과 기록 4,000,000 B, M7 중원자 6,000), M21 시간 상한(120/240초, 해시 파일), 새 외부 요청. 작업 `timeout_s`(기본 120, 0 초과 240 이하)·추가 원자 쪽 크기(기본 100, 1–200)·화면 폴링 1초는 조정 가능한 기본값이다.
