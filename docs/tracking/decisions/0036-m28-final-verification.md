# 0036. M28 종단 검증은 로컬 공개 실데이터와 실제 JEV 호출 2회로 완성 정의 여섯 항목을 세 분기에서 끝까지 돌리고, 새 기능 없이 간헐 실패 시험과 M20 보고서 출처표만 고치며, 판정은 사용자 확인 전까지 `검증 통과, 사용자 확인 대기`로 둔다

- 상태: 채택 (사용자 결정 2026-10-11, M28 명세 확정 전 질문에서 모두 추천안을 골랐다(자유 입력·메모 없음). 아래 "조율 세션이 정한 것"은 사용자 선택이 아니며 최종 확인에서 이의를 받는다). 이 결정의 판정 절차에 따라 M28의 판정은 사용자가 확인하기 전까지 `검증 통과, 사용자 확인 대기`다(기록 `docs/tracking/m28-acceptance.md`). 외부 요청 규칙(결정 0005·0015·0034·0035)과 실호출 할당 규칙(결정 0012: 할당은 사용자만 정함)은 바뀌지 않는다.

## 배경
로드맵 M28은 종단 검증과 마감 단계다(선행 M13–M27 전부). 완성의 정의(`docs/tracking/roadmap.md`) 여섯 항목은 "실제 데이터로 한 번 끝까지 돌아가 검토를 통과"하는 것을 요구하지만 M13–M27은 단계마다 따로 수락했고, 로컬 공개 자료만으로는 한 구조에서 끝까지 이어지지 않는 사슬이 있다(M7 사전 검사를 통과하는 로컬 공개 구조는 1UBQ뿐이고 1UBQ는 효소도 아니고 리간드도 없다). 미해결 문제는 128절이 쌓였고 README는 M12까지만 설명했다.

위험은 여섯 가지였다: 로컬 자료로 안 이어지는 사례를 합성값으로 메우는 것, 간헐 실패를 코드 문제로 단정하거나 가리는 것, 호출 키 해시 파일·닫힌 집합·고정 문장을 "작은 수정"으로 건드리는 것, 실호출이 계획 밖으로 나가는 것, 문서가 코드와 어긋난 채 마감되는 것, 감사·판정 코드가 거짓 통과를 내는 것.

## 결정 (사용자, 2026-10-11)
- ① **실데이터는 로컬 공개 자료만**이다: 저장소의 공개 구조(`public_{1m17,1fin,1mq4,1s9i,1a30,1a4i,1ubq,1hsg}.cif`), ProLIF 공개 예제 준비 수용체·포즈, 공개 파생 부모 SDF와 "합성 표시" block·반응 규칙 fixture, 보관된 M26 실세트(`.deps/reaction_qa/import2`, 읽기 전용), 로컬 `../kbase_kinase`와 M15 활성 세트. 새 외부 요청은 0건이다(구조 새로 받기·M26 다시 가져오기 없음).
- ② **실제 JEV 호출은 2회**다: 리간드 루프 한 바퀴 + 단백질 루프 한 바퀴.
- ③ **새 기능 없음**: Linux·Intel Mac 작업 환경 잠금, 다른 탭 알림, run 전체 작업 목록, GPCR 계열 지식은 범위 밖으로 기록한다.
- ④ **미해결 문제는 선별 수정 + 최종 분류**다: 모든 절에 닫힌 집합 넷(`해결`·`수용`·`사용자 결정 필요`·`범위 밖`) 중 하나를 붙인다.
- ⑤ **판정 문구는 범위를 명시한 완성 문구**이며 사용자가 확인한 뒤에만 쓴다.
- ⑥ **문서는 최신화 + 빈틈 메우기**다(`CLAUDE.md`·`AGENTS.md` 구조는 그대로, 머리말과 M28 항만).
- ⑦ **설치 시험은 핵심 설치를 새로 시험**하고 선택 작업 환경은 정적으로만 확인한다.
- ⑧ **통과 규칙**: 항목마다 분기 하나에서 사례 사슬이 끝까지 돌아야 하고, 완성 문구는 사용자 확인 뒤에만 기록한다(독립 검토 통과만으로는 쓰지 않는다).
- ⑨ **코드 수정은 둘뿐**이다: M20 보고서의 참조 출처표(보고서 형식 버전 @2)와 간헐 실패 시험. POST JSON 형식 검사와 M20 v2의 "0 저장 → null" 변경은 하지 않는다.
- ⑩ **QA는 fixture 회귀 전량 + M28 실데이터 단계**다: M13–M27 수락 실행기를 최종 소스에서 fixture 단계로 다시 돌리고(M26·M27은 자기 real 단계도), 실데이터 종단 검증은 새 실행기가 맡는다.

## 조율 세션이 정한 것 (사용자 선택이 아님, 최종 확인에서 이의를 받는다)
- **명세 작성 때**: 실호출 대상은 리간드 바퀴 = 활용형, 단백질 바퀴 = 탐색형이고 나머지 목표는 fixture 서버로 같은 코드 경로를 지난다. 실패하거나 완료되지 않은 호출도 할당에서 세고 재시도·보정 호출이 없으며 첫 호출이 완료되지 않으면 계획을 끝낸다. 바퀴 결과는 닫힌 집합 `completed`·`provider_failed`·`product_failed`·`not_sent`이고 하나라도 `completed`가 아니면 판정은 `보류`다(면제는 `provider_failed`에 한해 사용자만). 판정 값은 셋(`검증 통과, 사용자 확인 대기`·`보류`·사용자 확인 뒤의 완성 문구)이고 확인 전에는 Git 추적 문서 어디에도 확인 전 금지 표현(명세 §3.3의 정규식)이 없어야 한다. 설치 시험은 README 개정 뒤 고정 커밋의 로컬 클론에서 하고, 선택 기능이 숫자 없이 "사용할 수 없음 + 이유"로 보이는 것을 통과 조건에 넣으며, 핀·잠금 변경이 필요하면 멈춘다. 지원 환경 문구는 "서버" 전제를 두고 과학 기능은 macOS arm64 CPython 3.11에서만 검증됐다고 적는다. 실데이터 산출물은 지우지 않고 공유 제외 폴더 목록만 문서에 적는다. 역추적 감사는 보고서 증거 항목을 검사하고 Markdown 서술 속 숫자는 파싱하지 않는다. 분기 하네스는 기존 흐름 함수를 복사해 쓰되 기대값은 입력 파일에서 독립으로 계산한다. 소스 고정 뒤 변경은 문서·증거와 회귀 사슬이 요구하는 옛 하네스·실행기 기대 수정뿐이고 실제 live 단계 뒤에는 문서·증거만이다.
- **착수 확인 뒤(T1, 2026-10-11)**: 실행 순서는 루프를 GA·일괄보다 먼저 돈다(B: B1, B2, B3(+같은 인자 재제출), B6, B7(탐색형 → 활용형), B4, B5(설정 1 → 2), B8 / C: C1, C2, C3, C5, C6(탐색형 → 활용형), C4(설정 1 → 2), C7). 명세 표 순서대로 한 run에서 돌리면 루프에는 증액 경로가 없고 M19·M22·M23 증액은 부족분만 올려 B7·C6이 예산에 막히기 때문이다. live는 B와 C를 다른 run으로 한다. M20 보고서 @2는 참조값(번호 대응·주석 handle, 또는 M-CSA 항목 ID 주장)을 인용하는 새 보고서에만 쓰고, 인용 없는 새 보고서와 저장된 @1은 그대로다("새 보고서 전부 @2"는 수정 금지 기준선 비교 시험을 깸). 반응 표는 M-CSA 항목 ID 주장이 있을 때만 싣고 "가공 행 수" 열과 활성 세트 줄은 싣지 않는다. B2 입력은 기존 합성 표시 파일 조합(`ligand_ga/synthetic-ga-small-blocks.smi` + `ligand/synthetic-blocks.sdf` + `ligand_ga/synthetic-ga-pool2000-rules.json`의 `user_2`·`user_3`)이다. A1 "기본 정책"은 화면 기본값(물 `strip_all`)이다. 점검 보고서와 `interface_sasa` 보고서는 제품이 다시 열 때 다시 만들지 않으므로 감사에 `partialProductRecheck`로 표시하고 A2·A3의 독립 기대값으로 보완한다. README의 가상환경 명령은 `python3.11 -m venv`로 바로잡는다. PDBFixer는 플랫폼 잠금이 아니라 `pyproject.toml` 핀이므로 범위 표에 사실대로 적는다.
- **구현·검토 중**: X4 금지 표현 예외는 세 방식(줄 일치·숫자 정규화 템플릿 일치·`label` 일치) 19개이고 예외마다 종류·사례·소스 위치·이유를 증거에 남기며 원문 줄은 Git 제외다(`label` 일치는 포켓 보고서 공동 번호 머리 부분만, 명세의 "줄 단위 예외"를 약간 넓힌 해석). 실제 live는 `--live-calls 2`와 분기 전체(b·c)만 받고(부분집합·1회는 대장을 건드리기 전에 거절), 첫 입장에서 빈 대장과 잠금을 함께 만들며, 단백질 바퀴는 리간드 바퀴가 dispatch 이벤트 정확히 1건으로 `completed`일 때만 보내고, `completed`·`provider_failed`는 dispatch가 정확히 1건일 때만 인정한다(보냈는지는 하네스 자기 보고가 아니라 분기 앞뒤의 dispatch 이벤트 수로 정함). 송신 전 예산 부족은 할당을 쓰지 않는 `product_failed`다. 역추적 감사 검사는 다섯(명세 §7의 근거 구조 검사를 근거 객체 존재·주장 필드로 나눔)이고 어댑터는 보고서 종류 20종이다. 명세 §8.2 (a)의 "AGENTS.md"는 `scripts/AGENTS.md`·`frontend/AGENTS.md`를 포함한 문서로 읽는다. live 단백질 바퀴 탐색형의 "본문에 점수 없음" 확인이 비는 것은 선행 상태에 도킹을 더하는 계획 변경 없이 범위 표에 적는다. Stop 훅 pytest 그룹은 더하지 않고 M28 시험 넷을 `SCRIPT_TESTS`에 넣는다.
- **기록 때(T18, 2026-10-12)**: 미해결 문제 절 11(fpocket 네트워크 차단)·108(SSL CA 환경변수)은 명세 §11.3이 수용 예시로 지정했으므로 `수용`, 절 98(낡은 문장)은 문서를 고친 뒤 `해결`이다. `사용자 결정 필요` 84개(본문 근거 24·기본값 60)는 완성 정의의 사례 사슬을 막지 않는 이월·관찰이므로 `보류` (b)의 "이번 단계의 결함"으로 읽지 않는다(사용자가 다르게 읽으면 `보류`).

## 이유
- 세 분기를 실제 Electron 오프스크린 클릭으로 끝까지 돌리고 기대값을 입력 파일·저장 객체의 다른 필드·기존 oracle에서 독립으로 계산하면, 제품이 자기 값을 맞다고 하는 순환 없이 "실제 데이터로 끝까지"를 보일 수 있다. 로컬 자료로 이어지지 않는 곳(촉매 보호와 변이 모델링이 다른 구조, 1UBQ의 합성 표시 리간드)은 합성값으로 메우지 않고 범위 표에 적는다.
- 실호출을 두 바퀴로 묶고 대장·dispatch 이벤트·실행 상한으로 강제하면 되돌릴 수 없는 외부 비용이 계획 밖으로 나가지 않는다. 다른 목표는 fixture 서버가 같은 코드 경로로 덮는다.
- 코드 수정을 시험 쪽 간헐 실패와 M20 보고서 형식 버전으로 한정하면 호출 키 해시 파일·닫힌 집합·고정 문장·결과 객체가 그대로여서 기존 결과의 자동 재사용과 골든 셋이 유지된다.
- 판정 문구를 사용자 확인 뒤로 미루고 기계 검사(금지 표현 정규식)로 지키면 조율 세션이나 검토만으로 완성이 선언되지 않는다.

## 검토한 대안 (기각, 되돌리지 말 것)
새 공개 복합체를 받아 실제 결합 맥락에서 변이 도킹을 시험하기, 옛 실행기의 real 단계 일괄 재실행, 조건부 완성 문구, 독립 검토만으로 완성 기록, `CLAUDE.md`/`AGENTS.md` 재구성, README만 갱신, 정적 확인만 하는 설치 시험 또는 선택 환경까지 전부 새로 설치, 해시 파일·닫힌 집합을 바꾸는 "전부 수정", 코드 수정 없이 분류만, POST JSON 형식 검사와 "0 저장 → null" 변경, Linux 잠금·탭 알림·작업 목록·GPCR 추가.

## 수용한 대가
- M20 보고서에 형식 버전이 둘 생겼다(`mutation_candidates_markdown@1`·`@2`). 저장된 @1 보고서는 같은 바이트로 다시 열리고 출처표가 필요하면 새로 만든다.
- 완성 정의의 항목 2는 키나아제·효소로만, 항목 4는 서로 다른 두 구조(1A30·1UBQ)로, 리간드·변이 도킹은 합성 표시 자료를 섞어 보였다. GPCR은 범위 밖이다.
- 실제 모델 호출은 바퀴 한 번씩이고 나머지 목표는 fixture 서버 응답이다. live 단백질 바퀴 탐색형의 "본문에 점수 없음" 확인은 비어 있다.
- 실호출 대장은 대장과 잠금 파일을 함께 지우면 상한이 되돌려지고(대장 밖 기준점 없음), 단백질 바퀴만 다시 보낼 수 없다.
- 미해결 문제 84개가 `사용자 결정 필요`로 남는다.
