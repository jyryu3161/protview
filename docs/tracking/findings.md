# 미해결 문제

## 과거 단계 재검증이 대부분 오래된 검토로 판정된다
- **현상**: `scripts/execute.py <phase> --verify`를 실행하면 공유 파일(README.md, AGENTS.md, `docs/ARCHITECTURE.md` 등) 해시가 검토 당시와 달라 M0–M10 단계 대부분이 오래된 검토로 판정된다. M11이 공유 소스(app.py, queue.py, guardian.py, MolstarViewer.tsx, page.tsx 등)를 더 바꿨으므로 이 상태는 계속된다.
- **영향**: 끝난 단계를 "과거 검토 해시 기준으로 검증됨"이라고 주장할 수 없다.
- **지금 해결하지 못하는 이유**: 검토 해시를 고치면 과거 증거를 위조하는 것이다.
- **현재 상태**: 각 단계 완료 검토가 바뀐 공유 소스와 회귀를 현재 기준으로 다시 확인한다. 가장 최근은 M16(`docs/tracking/m16-acceptance.md`의 "대체한 과거 검증 범위": M15·M14 수락 실행기, M13 수락 실행기 전체와 그 안의 M11·M12 실행기)이며, 다시 돌리지 않은 범위는 M13 완료 기록에 적었다. 과거 기록은 그대로 둔다.

## :3000에 Host 헤더가 두 개면 검사를 지나간다
- **현상**: `Host: 127.0.0.1:3000` 다음에 외부 Host를 보내면 200이 나오고 `/api` 요청이 백엔드까지 간다.
- **영향**: Host를 두 개 보낼 수 있는 로컬 프로그램은 프런트엔드 Host 검사를 피할 수 있다. 브라우저는 Host를 하나만 보내므로 DNS 리바인딩 방어에는 영향이 없다.
- **지금 해결하지 못하는 이유**: 사용자 결정(2026-09-28)으로 알려진 한계로 둔다. 막으려면 Next를 자체 Node 서버로 띄워 원시 헤더를 검사해야 한다.
- **방향**: 공유 사용이나 외부 공개를 검토할 때 함께 다룬다. 증거: `docs/qa/m11-chemical-20260928/host-check.json`, 결정 0013.

## 이벤트 로그를 읽을 때마다 전체를 다시 파싱한다
- **현상**: 작업 상태 읽기와 이벤트 추가가 run의 `events.jsonl` 전체를 다시 파싱한다. M11 작업 기록이 커서(작업당 수 MB) 한 번에 약 0.3초 CPU가 든다.
- **영향**: 정확성 문제는 아니지만, 화학 작업이 많은 run에서 폴링과 작업 시작이 느려진다.
- **지금 해결하지 못하는 이유**: `core/events.py`의 읽기 구조를 바꾸는 일로 M11 범위 밖이다. 이벤트 형식은 바꾸지 않아야 한다.
- **방향**: 추가 전용 로그의 오프셋 기반 증분 읽기를 설계하고 events-only 복구 테스트로 확인한다.

## GO 전에 guardian이 끝나면 작업이 running으로 남는다
- **현상**: guardian이 GO를 받기 전에 끝나면(상한 초과 등) 작업은 `guardian_result_missing`과 함께 running으로 보이다가, 백엔드를 다시 시작해야 interrupted로 정리된다.
- **영향**: GO 대기 상한을 작업 시간에 맞춘 뒤로는 드물지만, 생기면 사용자가 재시작해야 한다.
- **지금 해결하지 못하는 이유**: 부모 쪽 즉시 정리 경로는 작업 수명 주기 전체를 다시 검증해야 하는 변경이다.
- **방향**: guardian 종료를 부모가 감지하면 과학 작업 없이 끝난 시도를 typed 실패로 기록하는 경로를 추가하고 실제 프로세스 테스트로 확인한다.

## 긴 작업 시작 응답 복구가 브라우저로 검증되지 않았다
- **현상**: 시작 요청이 Next 프록시의 30초를 넘겨 500을 받은 뒤 실제 작업 상태를 다시 읽어 보여 주는 경로(`chemicalStartProgressed`)는 단위 테스트로만 확인했다. 수락 QA의 시작 요청은 모두 30초 안에 끝났다.
- **영향**: 큰 수용체에서 실제로 이 경로를 탈 때의 화면은 관찰하지 않았다.
- **방향**: 표시된 지연 fixture로 30초를 넘기는 오프스크린 사례를 추가한다.

## M11 사례 대장의 증거 형식이 고르지 않다
- **현상**: 회귀 행 5개에 offscreen·WebGL 요약과 fixture 출처가 행 안에 없고(흐름 jsonl에만 있다), 모든 단계의 `paint-first.png`가 0바이트다(실제 paint 증거는 `baseline.paint.png`와 이후 프레임). attach-setup 행에는 파일별 출처 라벨이 없다.
- **영향**: 증거 자체는 유효하지만(독립 증거 검토 승인), 대장만 읽는 사람이 오해할 수 있다.
- **현재 상태**: 첫 paint 저장은 M12에서 고쳤다(첫 번째로 비어 있지 않은 프레임을 저장하고 크기·해시를 기록, 0바이트면 실패). 고정된 2026-09-28 증거는 바꾸지 않는다. 행 안의 offscreen 요약·파일별 출처 라벨은 M11 대장 형식 그대로다.

## 공유 서버 사용을 막는 장치가 없다
- **현상**: 백엔드는 인증 없이 `127.0.0.1:8000`에서 열린다. 여러 사람이 계정을 가진 서버에서 실행하면, 다른 계정도 모든 run의 구조·보고서를 읽고 계산을 실행할 수 있다.
- **영향**: 미공개 구조가 같은 서버의 다른 사용자에게 노출될 수 있다.
- **지금 해결하지 못하는 이유**: 현재 사용 방식은 인스턴스당 한 사람(서버도 혼자 사용)으로 정했다. 인증과 run 소유권은 설계되지 않았다.
- **방향**: 공유 서버나 외부 공개가 필요해지면 인증, 사용자별 runs 루트, 포트 격리를 설계한다.

## ProLIF·fpocket 작업 환경이 macOS arm64 전용이다
- **현상**: `config/chemical/`의 잠금 파일과 `setup_prolif_worker.py`가 CPython 3.11 macOS arm64만 허용한다.
- **영향**: Linux 서버에 설치한 인스턴스에서는 M11 화학 기능을 쓸 수 없다.
- **지금 해결하지 못하는 이유**: 다른 플랫폼 wheel 조합을 조사하고 해시 잠금·검증을 새로 해야 한다.
- **방향**: Linux x86_64용 잠금 파일과 설치 경로를 따로 만들고, 같은 네이티브 테스트로 검증한다.


## M12 수락 QA에서 실제 화면으로 확인하지 못한 영역
- **현상**: (1) 최소화 구조의 포켓을 골랐을 때 원래 복합체 접촉 행이 숨는지는 확인하지 못했다. 최소화 가능한 공개 fixture(1UBQ)에 리간드가 없고, 1HSG는 OpenMM이 거부한다(말단 OXT 누락). 범례·초점·직전 보기 복귀는 확인했다. (2) M11 회귀는 7개 모드와 m11-create만 다시 돌렸다(연결 두 모드, restrictions, faults, 잘못된 입력, M11 replay, 작업 프로세스 없음·버전 불일치, 화학 구조 중 M9 보기 복원은 제외). (3) 화면 취소는 승인 대기 작업으로만 확인했다(실행 중 취소는 백엔드 테스트). (4) M8–M10 회귀 행에 WebGL 렌더러 문자열이 없다.
- **갱신(M13, 2026-09-29)**: (2)는 해결. M13 수락 QA가 M11 수락 실행기 전체(모든 모드, 17/17, 29행)를 다시 돌렸다. (1)은 그대로다. (3)은 M12 포켓 화면 기준으로는 그대로이며, M13 흐름에서는 소유 OpenMM 작업 실행 중 중지를 실제 화면으로 확인했다(S-stop-running). (4)는 M13 회귀 행에도 그대로다.
- **영향**: 해당 경로는 코드·단위 테스트로만 뒷받침된다.
- **방향**: 리간드가 있고 OpenMM으로 최소화할 수 있는 공개 fixture를 마련해 접촉 행 확인을 추가한다. 회귀 행에 렌더러 문자열을 기록한다. 증거: `docs/qa/m12-pockets-20260929/README.md`, `docs/qa/m13-workflows-20260929/README.md`.

- **현상**: 보고서 Markdown에 `fpocket&#x27;s`처럼 HTML 이스케이프 뒤 Markdown 이스케이프가 겹친 문자열이 나온다.

## fpocket 작업 프로세스의 네트워크 차단은 운영체제 수준이 아니다
- **현상**: fpocket은 허용 목록 환경변수(비밀·프록시 없음)로, 시스템 라이브러리만 링크한 고정 실행 파일을 실행한다. 네트워크 자체를 막는 샌드박스는 없다.
- **영향**: 고정 실행 파일에는 네트워크 코드 경로가 없지만, 운영체제가 강제하는 보장은 아니다.
- **방향**: 필요해지면 `sandbox-exec` 같은 방식으로 네트워크를 거부하고 같은 테스트로 확인한다(argv는 바꾸지 않는다).

## 게시되지 않은 포켓 원본 출력이 이벤트 기록에 남을 수 있다
- **현상**: 결과 쓰기와 종료 이벤트 사이의 짧은 틈에 취소·재시작이 끼면, 게시되지 않은 원본 출력 객체가 이벤트 기록에 남는다. run당 보관 한도에는 계산하지 않는다.
- **영향**: 디스크만 쓴다. 게시 전 현재 시도 확인이 있어 드물고, 시도마다 비싼 계산 1단위가 들어 개수가 제한된다.
- **방향**: 이벤트 로그 증분 읽기 설계 때 함께 본다. 읽을 때마다 원본 출력을 다시 파싱하는 비용도 30 MiB 한도 근처에서 재 보지 않았다.

## 실패한 공유 작업은 흐름에서 다시 돌릴 수 없다
- **현상**: 흐름 단계가 같은 호출 키의 기존 작업을 관찰(`observed_shared`)했는데 그 작업이 실패·취소로 끝나면, 단계는 재시도 불가 `failed`(`shared_job_failed`)다. 새 계획·실행도 같은 호출 키라 같은 작업을 다시 관찰한다.
- **영향**: 사용자가 `/jobs`에서 원래 작업을 직접 재시도해야 흐름을 다시 진행할 수 있다. 원래 작업이 다른 흐름 실행의 소유 작업이면, 그 소유 실행이 종료 상태가 된 뒤에만 수동 재시도가 된다(실행이 진행 중이면 412 `job_owned_by_analysis_execution`). 소유 실행이 한 번의 재시도까지 쓰고 실패로 끝난 작업도 이렇게 기존 수동 재시도 규칙(시도 4회까지)으로 다시 돌릴 수 있다.
- **지금 해결하지 못하는 이유**: 흐름은 다른 사람이 만든 작업을 시작·재시도·취소하지 않는다는 규칙(M13 명세)과, 같은 호출 키는 기존 작업을 돌려주는 작업 큐 동작을 유지했다.
- **방향**: 화면에 원래 작업 화면으로 가는 안내를 더 분명히 하거나, 흐름 쪽 재시도 규칙을 사용자와 다시 정한다.

## ATR 5YZ0:A의 KLIFS `linker.49`가 한 칸 어긋나 보인다
- **현상**: KLIFS 측정에서 5YZ0:A의 불일치 1개(`linker.49`)는 포켓 서열 앞뒤에 같은 글자 N이 겹쳐 생긴 한 칸 차이로 보인다. 증거 검토자는 다른 대량 불일치 5개 구조(7TYM:A, 6TLJ:S, 8E06:A, 6CD6:D, 8U7L:A)는 KLIFS 쪽 산물로 판단했지만 이것은 판단하지 않았다.
- **영향**: ATR에서 `linker.49` 번호 하나가 KLIFS 구조별 표와 한 칸 다를 수 있다. 우리 번호는 유일 배치 규칙대로 붙은 것이다.
- **방향**: M16에서 linker·hinge 주석을 표시하기 전에 ATR 포켓과 UniProt 서열을 손으로 대조하고, 규칙을 바꿔야 하면 사용자와 정한다. 증거: `docs/qa/m15-numbering-20260930/klifs_measurement.txt`.
- **M16 손 대조(2026-10-01, `docs/qa/m16-annotations-20261001/preflight.txt`)**: 5YZ0:A의 GK.45(2377)·hinge.46–48(2378–2380)은 손 대조, 제품 규칙, KLIFS 구조별 표가 모두 같다. 어긋남은 `linker.49`(KLIFS 표 2381, 제품 2382, 두 자리 모두 N)뿐이다. 포켓 linker `NTAG`는 UniProt 2382–2385에만 연속 일치하고 KLIFS 표는 2382를 건너뛴다. `linker.49`는 M16 부위 목록 밖이라 표시에 영향이 없고 규칙은 바꾸지 않았다. 어느 쪽이 맞는지는 여전히 정하지 않았다.

- **방향**: 화면 체인 목록을 도구 규칙으로 계산한 읽기 API에서 받도록 바꿀지 M16 착수 때 정한다. 지금은 `lib/numbering.ts`에 코드 주석으로 차이를 적어 두었다.
- **M16에서 다시 미룸(2026-09-30 사용자 결정)**: 틀린 대응이 생기는 문제가 아니므로 그대로 두었다. M16은 지식 탭을 바꾸지 않았다(결정 0024).

## 뷰어 쪽 `viewer_scene@2` 복원 거부 경로가 실제 화면에서 지나가지 않았다
- **현상**: `restoreScene`이 주석을 그리지 못해 `siteAnnotation: {status: "rejected"}`를 돌려주는 경로(페이지가 요청을 거두고, 뷰어가 그 의도 revision을 다시 그리지 않음, 코드 검토 수정 `cc3da8e`)는 실제 화면에서 일어난 적이 없다. M16 수락 QA의 복원 거절 사례(A-blocked-pocket, A-blocked-comparison)는 페이지가 복원 전에 거절하는 경로다.
- **영향**: 뷰어 거부 뒤 화면 표시(적용·거부를 나눠 보여 주기, 주석 꺼짐)는 코드와 코드 검토로만 뒷받침된다.
- **방향**: 원자 카탈로그와 맞지 않는 주석(표시된 fixture)으로 거부를 일으키는 오프스크린 사례를 추가한다. 증거: `docs/tracking/m16-acceptance.md`.

## 부위 이름표가 선택 가능한 Mol* 도형으로 남는다
- **현상**: 극성 접촉 점선과 거리 이름표는 `pickable: false`로 그리지만, 부위 이름표(`addLabel`)는 Mol* 측정 도형 기본값대로 선택 가능하다.
- **영향**: 이름표를 누르면 잔기 선택이 아니라 Mol* 도형이 잡힐 수 있다. 과학 값이나 저장된 기록에는 영향이 없다.
- **방향**: 다음 뷰어 변경 때 이름표도 선택 불가로 두고, 이름표 위 클릭이 기존 잔기 선택과 같은지 오프스크린으로 확인한다.

## 다른 접촉 잔기는 회색 막대 모형으로 겹쳐 그린다
- **현상**: `other_contact_residues`는 주 모델의 잔기 색을 바꾸지 않고, 그 잔기 원자를 얇은 회색(`site-other-contact`) 막대 모형 구성 요소로 따로 그린다.
- **영향**: 명세의 "잔기 색으로만 강조"와 보이는 모양이 조금 다르다(점선은 없음, 값에는 영향 없음). 표현 모드에 따라 주 모델과 겹쳐 보인다.
- **방향**: 그림 용도로 부족하다는 의견이 나오면 주 모델 색 덮어쓰기 방식을 검토한다.

## 비교를 끝내면 참조 주석 패널의 선택이 지워진다
- **현상**: M10 비교를 시작하면 주석이 꺼지는 것(명세)에 더해, 비교를 끝낸 뒤 패널에서 골라 두었던 주석 선택도 지워져 있다(M16 수락 QA 관찰, 판정 대상 아님). 저장된 보기 복원 뒤 "현재 구조로 돌아가기"를 누를 때도 주석이 꺼진다.
- **영향**: 사용자가 주석을 다시 골라 켜야 한다. 잘못된 표시는 아니다.
- **방향**: 사용 중 불편하다는 의견이 나오면 비교 종료 뒤 같은 소스면 선택을 유지할지 정한다.

## 참조 스냅샷을 가져올 때마다 세트 해시가 달라 수락 QA 실행마다 해시가 다르다
- **현상**: M16 수락 시도 1 `67e062ad…`, 시도 2 `96abf6e4…`, M15 회귀 `7de2dd22…`는 같은 kbase 파일을 격리 폴더로 가져온 세트인데 해시가 모두 다르다(매니페스트의 `imported_at`, `docs/engineering-notes.md`).
- **영향**: 실행 사이에 세트 해시로 같은 자료인지 비교할 수 없다. 같은 사용자 폴더에서 다시 가져오면 기존 주석·대응이 "이전 스냅샷 기준"으로 보인다.
- **방향**: 설계대로다. 파일 같음은 매니페스트의 파일별 SHA-256으로 비교한다. 다시 가져오기를 "변경 없음"으로 다루려면 별도 결정이 필요하다.
