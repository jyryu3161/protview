# 미해결 문제

## 과거 단계 재검증이 대부분 오래된 검토로 판정된다
- **현상**: `scripts/execute.py <phase> --verify`를 실행하면 공유 파일(README.md, AGENTS.md, `docs/ARCHITECTURE.md` 등) 해시가 검토 당시와 달라 M0–M10 단계 대부분이 오래된 검토로 판정된다. M11이 공유 소스(app.py, queue.py, guardian.py, MolstarViewer.tsx, page.tsx 등)를 더 바꿨으므로 이 상태는 계속된다.
- **영향**: 끝난 단계를 "과거 검토 해시 기준으로 검증됨"이라고 주장할 수 없다.
- **지금 해결하지 못하는 이유**: 검토 해시를 고치면 과거 증거를 위조하는 것이다.
- **현재 상태**: 각 단계 완료 검토가 바뀐 공유 소스와 회귀를 현재 기준으로 다시 확인한다. 가장 최근은 M19(`docs/tracking/m19-acceptance.md`의 "대체한 과거 검증 범위": M18·M17·M16·M15·M14 수락 실행기, M13 수락 실행기 전체와 그 안의 M11·M12 실행기)이며, 다시 돌리지 않은 범위는 M13 완료 기록에 적었다. 과거 기록은 그대로 둔다.

## :3000에 Host 헤더가 두 개면 검사를 지나간다
- **현상**: `Host: 127.0.0.1:3000` 다음에 외부 Host를 보내면 200이 나오고 `/api` 요청이 백엔드까지 간다.
- **영향**: Host를 두 개 보낼 수 있는 로컬 프로그램은 프런트엔드 Host 검사를 피할 수 있다. 브라우저는 Host를 하나만 보내므로 DNS 리바인딩 방어에는 영향이 없다.
- **지금 해결하지 못하는 이유**: 사용자 결정(2026-09-28)으로 알려진 한계로 둔다. 막으려면 Next를 자체 Node 서버로 띄워 원시 헤더를 검사해야 한다.
- **방향**: 공유 사용이나 외부 공개를 검토할 때 함께 다룬다. 증거: `docs/qa/m11-chemical-20260928/host-check.json`, 결정 0013.

## 이벤트 로그를 읽을 때마다 전체를 다시 파싱한다
- **현상**: 작업 상태 읽기와 이벤트 추가가 run의 `events.jsonl` 전체를 다시 파싱한다. M11 작업 기록이 커서(작업당 수 MB) 한 번에 약 0.3초 CPU가 든다.
- **영향**: 정확성 문제는 아니지만, 화학 작업이 많은 run에서 폴링과 작업 시작이 느려진다.
- **지금 해결하지 못하는 이유**: `core/events.py`의 읽기 구조를 바꾸는 일로 M11 범위 밖이다. 이벤트 형식은 바꾸지 않아야 한다.
- **방향**: 추가 전용 로그의 오프셋 기반 증분 읽기를 설계하고 events-only 복구 테스트로 확인한다.

## GO 전에 guardian이 끝나면 작업이 running으로 남는다
- **현상**: guardian이 GO를 받기 전에 끝나면(상한 초과 등) 작업은 `guardian_result_missing`과 함께 running으로 보이다가, 백엔드를 다시 시작해야 interrupted로 정리된다.
- **영향**: GO 대기 상한을 작업 시간에 맞춘 뒤로는 드물지만, 생기면 사용자가 재시작해야 한다.
- **지금 해결하지 못하는 이유**: 부모 쪽 즉시 정리 경로는 작업 수명 주기 전체를 다시 검증해야 하는 변경이다.
- **방향**: guardian 종료를 부모가 감지하면 과학 작업 없이 끝난 시도를 typed 실패로 기록하는 경로를 추가하고 실제 프로세스 테스트로 확인한다.

## 긴 작업 시작 응답 복구가 브라우저로 검증되지 않았다
- **현상**: 시작 요청이 Next 프록시의 30초를 넘겨 500을 받은 뒤 실제 작업 상태를 다시 읽어 보여 주는 경로(`chemicalStartProgressed`)는 단위 테스트로만 확인했다. 수락 QA의 시작 요청은 모두 30초 안에 끝났다.
- **영향**: 큰 수용체에서 실제로 이 경로를 탈 때의 화면은 관찰하지 않았다.
- **방향**: 표시된 지연 fixture로 30초를 넘기는 오프스크린 사례를 추가한다.
- **M18 갱신(2026-10-02)**: 서버는 도킹 작업 시작 요청도 작업이 끝날 때까지 붙잡는다. 공개 예제 자유 도킹 한 번이 약 28–29초였으므로(착수 확인), exhaustiveness·모드 수를 올리거나 코어 고정 샘플이 많으면 30초를 넘겨 시작 응답이 실패로 끝날 수 있다. 도킹 영역은 같은 다시 읽기 경로(`ligandStartProgressed`)를 쓰고, 독립 코드 검토 수정(`283cc72`)으로 취소를 시작 요청과 분리해 제출 응답의 job id로 바로 보낼 수 있게 했다(수락 `D-cancel`은 실행 중 취소를 실제 화면으로 확인). 30초를 넘긴 시작 응답의 화면 복구는 여전히 실제 화면으로 관찰하지 않았다.

## M11 사례 대장의 증거 형식이 고르지 않다
- **현상**: 회귀 행 5개에 offscreen·WebGL 요약과 fixture 출처가 행 안에 없고(흐름 jsonl에만 있다), 모든 단계의 `paint-first.png`가 0바이트다(실제 paint 증거는 `baseline.paint.png`와 이후 프레임). attach-setup 행에는 파일별 출처 라벨이 없다.
- **영향**: 증거 자체는 유효하지만(독립 증거 검토 승인), 대장만 읽는 사람이 오해할 수 있다.
- **현재 상태**: 첫 paint 저장은 M12에서 고쳤다(첫 번째로 비어 있지 않은 프레임을 저장하고 크기·해시를 기록, 0바이트면 실패). 고정된 2026-09-28 증거는 바꾸지 않는다. 행 안의 offscreen 요약·파일별 출처 라벨은 M11 대장 형식 그대로다.

## 공유 서버 사용을 막는 장치가 없다
- **현상**: 백엔드는 인증 없이 `127.0.0.1:8000`에서 열린다. 여러 사람이 계정을 가진 서버에서 실행하면, 다른 계정도 모든 run의 구조·보고서를 읽고 계산을 실행할 수 있다.
- **영향**: 미공개 구조가 같은 서버의 다른 사용자에게 노출될 수 있다.
- **지금 해결하지 못하는 이유**: 현재 사용 방식은 인스턴스당 한 사람(서버도 혼자 사용)으로 정했다. 인증과 run 소유권은 설계되지 않았다.
- **방향**: 공유 서버나 외부 공개가 필요해지면 인증, 사용자별 runs 루트, 포트 격리를 설계한다.

## ProLIF·fpocket·qvina·도킹 작업 환경이 macOS arm64 전용이다
- **현상**: `config/chemical/`의 잠금 파일과 `setup_prolif_worker.py`가 CPython 3.11 macOS arm64만 허용한다. M18의 `config/docking/` 잠금도 같다: `setup_qvina.py`는 conda-forge osx-arm64 패키지(macOS ≥ 11.0 arm64), `setup_docking_worker.py`는 CPython 3.11 macOS arm64 wheel만 받는다. Linux·Intel Mac 잠금은 없다.
- **영향**: Linux 서버나 Intel Mac에 설치한 인스턴스에서는 M11 화학 기능, M17 리간드 후보, M18 도킹을 쓸 수 없다(이유만 표시).
- **지금 해결하지 못하는 이유**: 다른 플랫폼 wheel 조합을 조사하고 해시 잠금·검증을 새로 해야 한다.
- **방향**: Linux x86_64용 잠금 파일과 설치 경로를 따로 만들고, 같은 네이티브 테스트로 검증한다.


## M12 수락 QA에서 실제 화면으로 확인하지 못한 영역
- **현상**: (1) 최소화 구조의 포켓을 골랐을 때 원래 복합체 접촉 행이 숨는지는 확인하지 못했다. 최소화 가능한 공개 fixture(1UBQ)에 리간드가 없고, 1HSG는 OpenMM이 거부한다(말단 OXT 누락). 범례·초점·직전 보기 복귀는 확인했다. (2) M11 회귀는 7개 모드와 m11-create만 다시 돌렸다(연결 두 모드, restrictions, faults, 잘못된 입력, M11 replay, 작업 프로세스 없음·버전 불일치, 화학 구조 중 M9 보기 복원은 제외). (3) 화면 취소는 승인 대기 작업으로만 확인했다(실행 중 취소는 백엔드 테스트). (4) M8–M10 회귀 행에 WebGL 렌더러 문자열이 없다.
- **갱신(M13, 2026-09-29)**: (2)는 해결. M13 수락 QA가 M11 수락 실행기 전체(모든 모드, 17/17, 29행)를 다시 돌렸다. (1)은 그대로다. (3)은 M12 포켓 화면 기준으로는 그대로이며, M13 흐름에서는 소유 OpenMM 작업 실행 중 중지를 실제 화면으로 확인했다(S-stop-running). (4)는 M13 회귀 행에도 그대로다.
- **영향**: 해당 경로는 코드·단위 테스트로만 뒷받침된다.
- **방향**: 리간드가 있고 OpenMM으로 최소화할 수 있는 공개 fixture를 마련해 접촉 행 확인을 추가한다. 회귀 행에 렌더러 문자열을 기록한다. 증거: `docs/qa/m12-pockets-20260929/README.md`, `docs/qa/m13-workflows-20260929/README.md`.

## 포켓 보고서 Markdown의 작은따옴표가 이중 이스케이프된다
- **현상**: 보고서 Markdown에 `fpocket&#x27;s`처럼 HTML 이스케이프 뒤 Markdown 이스케이프가 겹친 문자열이 나온다.

## fpocket 작업 프로세스의 네트워크 차단은 운영체제 수준이 아니다
- **현상**: fpocket은 허용 목록 환경변수(비밀·프록시 없음)로, 시스템 라이브러리만 링크한 고정 실행 파일을 실행한다. 네트워크 자체를 막는 샌드박스는 없다.
- **영향**: 고정 실행 파일에는 네트워크 코드 경로가 없지만, 운영체제가 강제하는 보장은 아니다.
- **방향**: 필요해지면 `sandbox-exec` 같은 방식으로 네트워크를 거부하고 같은 테스트로 확인한다(argv는 바꾸지 않는다).

## 게시되지 않은 포켓 원본 출력이 이벤트 기록에 남을 수 있다
- **현상**: 결과 쓰기와 종료 이벤트 사이의 짧은 틈에 취소·재시작이 끼면, 게시되지 않은 원본 출력 객체가 이벤트 기록에 남는다. run당 보관 한도에는 계산하지 않는다.
- **영향**: 디스크만 쓴다. 게시 전 현재 시도 확인이 있어 드물고, 시도마다 비싼 계산 1단위가 들어 개수가 제한된다.
- **방향**: 이벤트 로그 증분 읽기 설계 때 함께 본다. 읽을 때마다 원본 출력을 다시 파싱하는 비용도 30 MiB 한도 근처에서 재 보지 않았다.

## 실패한 공유 작업은 흐름에서 다시 돌릴 수 없다

- **지금 해결하지 못하는 이유**: 흐름은 다른 사람이 만든 작업을 시작·재시도·취소하지 않는다는 규칙(M13 명세)과, 같은 호출 키는 기존 작업을 돌려주는 작업 큐 동작을 유지했다.

## ATR 5YZ0:A의 KLIFS `linker.49`가 한 칸 어긋나 보인다
- **현상**: KLIFS 측정에서 5YZ0:A의 불일치 1개(`linker.49`)는 포켓 서열 앞뒤에 같은 글자 N이 겹쳐 생긴 한 칸 차이로 보인다. 증거 검토자는 다른 대량 불일치 5개 구조(7TYM:A, 6TLJ:S, 8E06:A, 6CD6:D, 8U7L:A)는 KLIFS 쪽 산물로 판단했지만 이것은 판단하지 않았다.
- **영향**: ATR에서 `linker.49` 번호 하나가 KLIFS 구조별 표와 한 칸 다를 수 있다. 우리 번호는 유일 배치 규칙대로 붙은 것이다.
- **방향**: M16에서 linker·hinge 주석을 표시하기 전에 ATR 포켓과 UniProt 서열을 손으로 대조하고, 규칙을 바꿔야 하면 사용자와 정한다. 증거: `docs/qa/m15-numbering-20260930/klifs_measurement.txt`.
- **M16 손 대조(2026-10-01, `docs/qa/m16-annotations-20261001/preflight.txt`)**: 5YZ0:A의 GK.45(2377)·hinge.46–48(2378–2380)은 손 대조, 제품 규칙, KLIFS 구조별 표가 모두 같다. 어긋남은 `linker.49`(KLIFS 표 2381, 제품 2382, 두 자리 모두 N)뿐이다. 포켓 linker `NTAG`는 UniProt 2382–2385에만 연속 일치하고 KLIFS 표는 2382를 건너뛴다. `linker.49`는 M16 부위 목록 밖이라 표시에 영향이 없고 규칙은 바꾸지 않았다. 어느 쪽이 맞는지는 여전히 정하지 않았다.

- **방향**: 문장을 바꿀 때 두 곳을 함께 고치고, 같음을 확인하는 테스트(예: 프런트 테스트가 백엔드 파일 문자열을 읽어 비교)를 추가한다.

## 화면의 체인 목록과 번호 대응 도구의 사슬 잔기 규칙이 다르다
- **현상**: 화면은 `structure_residues`의 `category`가 polymer인 잔기가 있는 체인만 고를 수 있게 보여 준다(`polymerChains`). 도구는 gemmi 엔티티 설정의 polymer 엔티티이거나 ATOM 레코드인 잔기를 사슬 잔기로 본다(`gemmi_polymer_entity_or_atom_record@1`).
- **영향**: 흔한 파일에서는 같지만, 사슬 잔기가 HETATM(MSE 등 변형 잔기)뿐인 체인은 도구로는 대응할 수 있어도 화면에 나오지 않는다. 반대로 화면에 나오지만 도구 규칙으로 사슬 잔기가 없는 체인을 보내면 `input_invalid`(`chain_not_found`)가 된다. 틀린 대응이 생기지는 않는다.
- **방향**: 화면 체인 목록을 도구 규칙으로 계산한 읽기 API에서 받도록 바꿀지 M16 착수 때 정한다. 지금은 `lib/numbering.ts`에 코드 주석으로 차이를 적어 두었다.
- **M16에서 다시 미룸(2026-09-30 사용자 결정)**: 틀린 대응이 생기는 문제가 아니므로 그대로 두었다. M16은 지식 탭을 바꾸지 않았다(결정 0024).

## 뷰어 쪽 `viewer_scene@2` 복원 거부 경로가 실제 화면에서 지나가지 않았다
- **현상**: `restoreScene`이 주석을 그리지 못해 `siteAnnotation: {status: "rejected"}`를 돌려주는 경로(페이지가 요청을 거두고, 뷰어가 그 의도 revision을 다시 그리지 않음, 코드 검토 수정 `cc3da8e`)는 실제 화면에서 일어난 적이 없다. M16 수락 QA의 복원 거절 사례(A-blocked-pocket, A-blocked-comparison)는 페이지가 복원 전에 거절하는 경로다.
- **영향**: 뷰어 거부 뒤 화면 표시(적용·거부를 나눠 보여 주기, 주석 꺼짐)는 코드와 코드 검토로만 뒷받침된다.
- **방향**: 원자 카탈로그와 맞지 않는 주석(표시된 fixture)으로 거부를 일으키는 오프스크린 사례를 추가한다. 증거: `docs/tracking/m16-acceptance.md`.

## 부위 이름표가 선택 가능한 Mol* 도형으로 남는다
- **현상**: 극성 접촉 점선과 거리 이름표는 `pickable: false`로 그리지만, 부위 이름표(`addLabel`)는 Mol* 측정 도형 기본값대로 선택 가능하다.
- **영향**: 이름표를 누르면 잔기 선택이 아니라 Mol* 도형이 잡힐 수 있다. 과학 값이나 저장된 기록에는 영향이 없다.
- **방향**: 다음 뷰어 변경 때 이름표도 선택 불가로 두고, 이름표 위 클릭이 기존 잔기 선택과 같은지 오프스크린으로 확인한다.

## 다른 접촉 잔기는 회색 막대 모형으로 겹쳐 그린다
- **현상**: `other_contact_residues`는 주 모델의 잔기 색을 바꾸지 않고, 그 잔기 원자를 얇은 회색(`site-other-contact`) 막대 모형 구성 요소로 따로 그린다.
- **영향**: 명세의 "잔기 색으로만 강조"와 보이는 모양이 조금 다르다(점선은 없음, 값에는 영향 없음). 표현 모드에 따라 주 모델과 겹쳐 보인다.
- **방향**: 그림 용도로 부족하다는 의견이 나오면 주 모델 색 덮어쓰기 방식을 검토한다.

## 비교를 끝내면 참조 주석 패널의 선택이 지워진다
- **현상**: M10 비교를 시작하면 주석이 꺼지는 것(명세)에 더해, 비교를 끝낸 뒤 패널에서 골라 두었던 주석 선택도 지워져 있다(M16 수락 QA 관찰, 판정 대상 아님). 저장된 보기 복원 뒤 "현재 구조로 돌아가기"를 누를 때도 주석이 꺼진다.
- **영향**: 사용자가 주석을 다시 골라 켜야 한다. 잘못된 표시는 아니다.
- **방향**: 사용 중 불편하다는 의견이 나오면 비교 종료 뒤 같은 소스면 선택을 유지할지 정한다.

## 참조 스냅샷을 가져올 때마다 세트 해시가 달라 수락 QA 실행마다 해시가 다르다
- **현상**: M16 수락 시도 1 `67e062ad…`, 시도 2 `96abf6e4…`, M15 회귀 `7de2dd22…`는 같은 kbase 파일을 격리 폴더로 가져온 세트인데 해시가 모두 다르다(매니페스트의 `imported_at`, `docs/engineering-notes.md`).
- **영향**: 실행 사이에 세트 해시로 같은 자료인지 비교할 수 없다. 같은 사용자 폴더에서 다시 가져오면 기존 주석·대응이 "이전 스냅샷 기준"으로 보인다.
- **방향**: 설계대로다. 파일 같음은 매니페스트의 파일별 SHA-256으로 비교한다. 다시 가져오기를 "변경 없음"으로 다루려면 별도 결정이 필요하다.

## 부위 주석의 없음 이유 한국어 이름이 화면과 보고서에서 다르다
- **현상**: 같은 이유 코드(`klifs_not_applied` 등)의 한국어 이름이 화면(`frontend/src/lib/site-annotation.ts`의 `SITE_REASON_LABEL`)과 보고서(`backend/mw/site_annotation_reports.py`의 `ABSENT_KO`·`GROUP_KO`)에 따로 있고 문구가 다르다(예: "KLIFS 번호를 적용하지 않은 그룹" / "KLIFS 번호 적용 안 됨").
- **영향**: 두 곳 모두 코드를 함께 보여 주므로 뜻이 섞이지는 않는다. 사용자가 화면과 보고서를 나란히 볼 때 표현이 다르게 보인다.
- **지금 해결하지 못하는 이유**: M16 최종 고정 뒤 기록 단계에서 발견했다. 보고서 문구를 바꾸면 렌더 결과와 보고서 테스트가 바뀌어 수락 QA를 다시 돌려야 한다.
- **방향**: 다음에 이 보고서나 패널을 고칠 때 한쪽을 기준으로 맞추고, M15 이유 코드 목록처럼 두 목록이 같은지 확인하는 테스트를 둔다.

## 반응 규칙 SMARTS 오류는 점검 작업을 돌린 뒤에야 알 수 있다
- **현상**: 서버는 RDKit을 import하지 않으므로 반응 SMARTS를 미리 검사할 수 없다. 규칙의 `valid`·오류 이유는 점검 작업(`rdkit_inspect_v1`, 비싼 계산 1단위)의 결과로만 나오고, 규칙을 고치면 점검을 다시 돌려야 한다(새 점검 객체, 1단위).
- **영향**: 규칙을 시행착오로 고칠수록 run 예산(기본 8회)이 빨리 준다. 부모만 바꿔도 점검 1단위가 든다.
- **지금 해결하지 못하는 이유**: 사용자가 승인한 비용이다(M17 명세 확정 때). 값싼 경로로 검사하려면 RDKit 작업 프로세스를 무료 동기 도구로 부르는 새 경로가 필요하고, 승인·예산 규칙에 예외를 두는 일이다.
- **방향**: 실제 사용에서 불편하면 규칙 검증만 하는 값싼 작업(예산 정책 포함)을 사용자와 정한다.

## (일부 해결, M18) M17 후보에는 3D 좌표·점수가 없다
- **현상**: 후보는 2D 그래프(SMILES)뿐이다. 3D 배치, 도킹 점수, 합성 가능성은 계산하지 않는다(고정 한계 문장 ③).
- **영향**: 후보를 구조와 함께 보거나 비교하려면 M18(단일 리간드 도킹, 코어 고정/자유)·M19(일괄 도킹)가 필요하다. 구조 뷰어(Mol*)에는 후보를 표시하지 않는다.
- **방향**: M18 착수 때 후보 SMILES에서 3D를 만드는 방법(코어 좌표 유지 여부 포함)을 사용자와 정한다.
- **M18 갱신(2026-10-02)**: 후보 하나를 도킹 작업 안에서 RDKit 3D 형태로 만들어 자유 도킹하거나 코어 고정 샘플에 점수만 매길 수 있게 했다(결정 0026). 후보 객체 자체는 여전히 2D이고, 여러 후보의 일괄 도킹·비교(M19)와 Mol* 표시는 없다.
- **M19 갱신(2026-10-03)**: 후보 집합의 후보 ≤ 50개를 한 설정으로 일괄 도킹해 첫 행 점수를 한 표에서 나란히 볼 수 있게 했다(결정 0027). 후보 객체는 여전히 2D이고 Mol* 표시·점수 차이·순위는 없다.

## 중원자 약 230개를 넘는 부모는 2D 그림 상한 때문에 점검할 수 없다
- **현상**: 번호 붙은 2D SVG는 256 KiB 이하여야 하고(넘으면 점검 `resource_exceeded`, `svg_limit`), `noFreetype` 출력으로도 중원자 약 230개부터 넘는다(착수 확인 실측 235개 266,494 B). 부모 중원자 한도는 256이다.
- **영향**: 중원자 약 230–256개 부모는 한도 안인데도 점검이 실패한다(과금됨).
- **지금 해결하지 못하는 이유**: SVG 상한·부모 한도는 명세 값이고, 바꾸려면 사용자 결정이 필요하다.
- **방향**: 실제 사례가 나오면 SVG 상한을 올리거나, 그림 없이 원자 표만 내는 경로를 정한다. 증거: `docs/qa/m17-ligand-20261001/preflight.txt` 3절.

## 미리보기와 후보 집합의 `retained_parent_atoms`가 같은 이름으로 다른 것을 뜻한다
- **현상**: 부위 미리보기 응답의 `site_check.retained_parent_atoms`는 코어 중원자 + 코어에 붙은 명시적 수소 번호이고, 후보 집합·후보 행의 같은 이름 필드는 코어 중원자만이다(명세 4.4).
- **영향**: 두 응답을 나란히 쓰는 코드가 수소 명시 부모에서 다른 목록을 얻는다. 화면은 후보 집합 쪽만 표시하므로 지금 틀린 표시는 없다.
- **지금 해결하지 못하는 이유**: 고정 뒤 기록 단계에서 정리했다. 이름을 바꾸면 API 계약·저장 객체 검증·화면을 함께 바꿔야 한다.
- **방향**: 다음에 미리보기 응답을 바꿀 때 필드 이름을 나누거나(예: 수소 포함 목록을 따로) 문서와 테스트로 뜻을 고정한다.

## 일반 객체 읽기는 리간드·도킹 객체를 검증하지 않고 내보낸다
- **현상**: `GET /runs/{id}/objects`·`/objects/meta`는 `ligand_inspection@1`·`ligand_candidate_set@1`·M18 `docking_result@1`을 각자의 검증(완료된 게시·입력 대조) 없이 그대로 읽어 준다. M12 `pocket_set@1`과 같은 관례다.
- **영향**: 검증된 읽기는 `/ligand/*`·`/docking/*`뿐이다. 화면은 이 경로만 쓰므로 지금 경로는 없지만, 다른 클라이언트가 일반 읽기를 쓰면 변조된 객체를 알아채지 못할 수 있다.
- **방향**: 일반 객체 읽기에 종류별 검증 훅을 둘지 방법 결과 종류 전체(포켓 포함)에 대해 함께 정한다.

## 리간드 탭에서 작업을 끝내도 전역 예산 줄은 탭을 바꿀 때까지 그대로다
- **현상**: M14 규칙대로 전역 예산 줄(`.mw-app-budget`)은 새 폴링 없이 탭 전환과 화학 화면 객체 변경 때만 `/budget`을 읽는다. 리간드 탭의 점검·생성 작업이 끝나도 전역 줄은 갱신되지 않는다. 리간드 패널 안의 예산 표시는 작업이 끝나면 다시 읽는다.
- **영향**: 같은 화면에서 두 예산 표시가 잠시 다르다. 과금·예산 기록은 맞다. M17 수락 `L-structure-kept`는 탭을 돌아온 뒤 전역 예산이 백엔드와 같음을 확인했다.
- **방향**: 리간드 패널의 작업 종료를 페이지에 알려 전역 줄을 한 번 읽게 할지 정한다(M14 전역 예산 읽기 실패 항목과 함께 본다).

## 리간드 패널의 늦은 응답 버림은 abort 층만 실제 화면으로 확인했다
- **현상**: 패널은 run·점검 선택이 바뀌면 요청을 abort하고, 영역별 요청 순번(stamp)이 맞지 않는 응답도 버린다. M17 수락 `L-run-switch-late`는 붙잡아 둔 run A 목록 응답이 버려지는 것을 abort 층에서 관찰했다. abort가 늦어 응답이 도착한 뒤 stamp 층이 버리는 경로는 `frontend/tests/ligand.test.cjs` 단위 테스트로만 확인했다.
- **영향**: stamp 층의 실제 화면 동작은 단위 테스트와 코드 검토로만 뒷받침된다.
- **방향**: 응답 본문을 받은 뒤 상태 반영 전에 run을 바꾸는 오프스크린 사례를 추가한다.

## 리간드 필터 경계는 서버에서 float로 바뀐다
- **현상**: 화면은 입력한 경계 문자열을 그대로 보내지만 서버 파서(`ligand_reads._number`)는 정수 모양이 아니면 float로 바꾼다. `1.0000000000000001` 같은 경계는 서버에서 1.0이 된다. 보고서 요청 본문의 `filters`도 JSON 숫자(float)다.
- **영향**: float로 구분할 수 없는 자리까지 쓴 경계는 사용자가 쓴 값과 다르게 비교된다. 저장 속성값도 float라 실제 판정이 달라지는 경우는 드물다.
- **방향**: 필요해지면 경계를 10진 문자열로 저장하고 `Decimal`로 비교하는 필터 버전을 둔다(보고서 manifest의 `filter_spec` 형식이 바뀌므로 렌더 버전을 올린다).

## 도킹 리간드가 수용체와 같은 좌표계인지 도구가 검증하지 못한다
- **현상**: M18 도킹은 입력 리간드(또는 후보의 부모) 좌표가 수용체와 같은 좌표계라고 가정한다. 도구가 하는 검사는 상자 안에 수용체 중원자가 하나도 없으면 거부하는 것(`box_no_receptor_atoms`)뿐이다.
- **영향**: 다른 구조에서 가져온 리간드처럼 좌표계가 조금 어긋난 입력은 상자 안에 수용체 원자가 있으면 그대로 도킹되고, `ligand_range` 상자가 엉뚱한 곳에 놓일 수 있다. 화면은 이 가정을 항상 적는다(`BOX_FRAME_NOTE`).
- **지금 해결하지 못하는 이유**: 좌표계 일치는 입력 파일만으로 판정할 수 없고, 정렬·변환을 하면 사용자 입력을 조용히 바꾸게 된다(명세 범위 밖).
- **방향**: 필요하면 상자 중심과 수용체 포켓·인스턴스의 거리 같은 경고를 사용자와 정한다.

## 도킹 포즈를 뷰어에서 볼 수 없다
- **현상**: M18 포즈는 모드 표·접촉 표와 포즈 SDF 내려받기로만 보인다. Mol* 표시·저장된 보기·그림 저장은 없다.
- **영향**: 포즈를 구조와 함께 보려면 SDF를 내려받아 다른 프로그램에서 열어야 한다.
- **지금 해결하지 못하는 이유**: 사용자 결정(결정 0026)으로 범위에서 뺐다. 표시하려면 MolstarViewer 브리지·식별자 대응·저장된 보기 형식을 함께 설계해야 한다.
- **방향**: M19 일괄 비교 화면도 사용자 결정으로 뷰어 표시를 뺐다(결정 0027, 행 상세는 M18 표·SDF). 포즈 표시는 별도 결정으로 다시 정한다.

## 실제 결정구조 수용체는 사용자가 손질해야 도킹할 수 있다
- **현상**: 수용체에 지정한 인스턴스 하나 말고 물·금속 이온·보조인자·다른 리간드·변형 잔기·H C N O S 밖 원소·altloc이 남으면 `receptor_unsupported_residue`·`receptor_altloc_present`로 거부한다(목록 최대 20개). 명시적 수소와 완전한 연결 정보도 필요하다(M11 규칙).
- **영향**: PDB에서 받은 결정구조는 대부분 그대로는 쓸 수 없고, 사용자가 외부 도구로 손질해 다시 가져와야 한다.
- **지금 해결하지 못하는 이유**: 수용체를 조용히 고치지 않는다는 규칙과 사용자 결정(물·금속·보조인자 처리, 수소 추가는 범위 밖)이다.
- **방향**: 실제 사용에서 반복되는 손질이 있으면, 명시적 확인을 받는 전처리 단계(예: 물만 빼기)를 사용자와 정한다.

## 코어 고정의 `core_max_deviation_A`는 덮어쓰기 때문에 사실상 0이고, 코어 수소는 고정하지 않는다
- **현상**: 코어 고정은 구속 임베딩 뒤 코어 중원자 좌표를 부모 좌표로 덮어쓰므로 저장되는 `core_max_deviation_A`는 정의상 0에 가깝다. 덮어쓰기 전 구속 임베딩 잔차(착수 확인 0.118–0.125 Å)는 기록하지 않는다. 코어에 붙은 수소는 RDKit이 만든 위치이며 고정 대상이 아니다.
- **영향**: 이 값을 "임베딩이 코어를 얼마나 지켰는가"로 읽으면 틀린다. 덮어쓰기로 생긴 연결부 결합 길이 변형도 따로 보이지 않는다.
- **지금 해결하지 못하는 이유**: 명세("코어 중원자는 부모 좌표 그대로")를 덮어쓰기로 구현했고(결정 0026), 잔차 필드를 더하면 결과 스키마가 바뀐다.
- **방향**: 필요하면 `docking_result@2`에서 덮어쓰기 전 잔차를 따로 기록할지 사용자와 정한다.

## 수용체 수소가 일부만 없으면 하전 종으로 추론되어 통과할 수 있다
- **현상**: M18 수용체 검사는 명시적 수소가 하나도 없을 때만 `receptor_hydrogens_missing`으로 거부한다. 일부 원자의 수소가 빠진 경우는 M11과 같은 MDAnalysis 추론이 형식 전하·결합 차수를 정하므로, 화학적으로 의도하지 않은 하전 종으로 통과할 수 있다(M11 단백질 그래프 검사에 걸리는 경우는 `receptor_prep_failed`).
- **영향**: 도킹 점수와 Meeko 부분 전하가 사용자가 의도하지 않은 양성자화 상태로 계산될 수 있다.
- **지금 해결하지 못하는 이유**: M11과 같은 규칙을 재사용하기로 했다(결정 0026). 바꾸면 M11 화학 결과와 규칙이 달라진다.
- **방향**: M11·M18을 함께 다룰 때 잔기별 수소 수 검사를 둘지 정한다.

## 모드 0개와 코어 고정 재현은 오프스크린에서 관찰하지 못했다
- **현상**: M18 수락 QA에서 실제 qvina가 유효 입력에 모드 0개를 낸 적이 없어 `D-zero-modes`는 "관찰하지 않음"이다(입력을 위조하지 않음). 재현 검사(`D-reproducible`)는 자유 도킹만 새 run 두 개에서 했다.
- **영향**: 모드 0개 화면은 `frontend/tests/docking.test.cjs`와 백엔드 테스트로만, 코어 고정의 같은 seed 재현은 백엔드 테스트로만 뒷받침된다.
- **방향**: 모드 0개를 실제로 내는 표시된 입력을 찾으면 오프스크린 사례를 추가한다. 코어 고정 재현을 수락 실행기의 재현 검사에 더한다.

## 도킹 결과 목록 읽기는 행마다 결과 전체를 다시 검증한다
- **현상**: `GET /docking/results`는 페이지의 행마다 `validated_result`(객체 읽기, 게시 이벤트 대조)를 부르고, 그때마다 run 이벤트 로그를 다시 읽는다.
- **영향**: 정확성 문제는 아니지만 도킹 결과가 많은 run에서 목록 읽기가 느려진다(이벤트 로그 재파싱 항목과 같은 원인).
- **지금 해결하지 못하는 이유**: 이벤트 읽기 구조를 바꾸는 일이라 M18 범위 밖이다.
- **방향**: 이벤트 로그 증분 읽기 설계 때 게시 대조 결과를 한 번에 계산하도록 함께 바꾼다.

## 비싼 계산 승인은 run의 가장 최근 승인 요청을 승인한다
- **현상**: `POST /jobs/approve`는 요청 본문에 작업을 지정하지 않고 run의 마지막 승인 요청 하나를 승인한다(그 도구의 queued 작업이 있어야 함). 도킹 영역도 같은 경로(`approveOpenmm`)를 쓴다.
- **영향**: 리간드 후보 작업과 도킹 작업이 같은 run에서 함께 승인을 기다리면, 어느 쪽 요청이 승인되는지는 요청 순서로 정해진다. 승인은 run 단위라 과금·결과가 틀리지는 않는다.
- **지금 해결하지 못하는 이유**: 기존 공용 작업 API이며 M11·M12·M17 화면이 같은 규칙을 쓴다. 바꾸려면 승인 계약을 바꿔야 한다.
- **방향**: 승인 요청에 작업·도구를 지정하는 계약을 둘지 다음 공용 작업 변경 때 정한다.

## (해결됨, 결정 0027) 일괄 증액의 상한·여유 해석이 명세에서 모호했다
- **현상**: 명세는 "증가분은 한 일괄의 필요량 이하"와 "활동 시간 부족분에 60초 여유"를 함께 적어, 필요량이 7800초로 묶인 경우 여유를 더해도 되는지와 절대 한도 상한이 있는지가 모호했다(독립 코드 검토 권고).

## 일괄 상자 계산이 작업 모듈과 M18 `dock_row`에 두 번 있다
- **현상**: M19 일괄 작업 모듈의 `batch_box`가 `prepared.json`에 쓰는 상자는 `docking_worker.dock_row`의 상자 단계(`range_box`, `check_box`)를 다시 적은 것이다. 행 결과의 상자는 `dock_row`가 따로 계산한다.
- **영향**: 둘 중 하나만 바뀌면 요약 검증(행 결과 `box` = 요약 `box`)이 모든 행에서 실패해 요약이 게시되지 않는다(행 결과는 남고 작업은 실패). 조용히 틀린 값이 나가지는 않는다.
- **지금 해결하지 못하는 이유**: 상자 단계를 `dock_row` 밖으로 빼면 M18 작업 모듈을 다시 고쳐야 하고, 그러면 작업 모듈 해시가 또 바뀌어 저장된 결과의 재사용이 다시 끊긴다(독립 코드 검토 권고, 이번 범위에서 고치지 않음).
- **방향**: 다음에 `docking_worker.py`를 고칠 일이 있을 때 상자 함수를 하나로 합치고 일괄 테스트의 단독 M18 바이트 비교를 다시 돈다.

## 늦은 종료 신호가 끝난 행을 잃게 할 수 있고, 남은 `qvina_work` 폴더가 다음 행을 막는다
- **현상**: 일괄 작업 모듈은 파일을 쓰는 동안만 SIGTERM·SIGALRM을 막는다. 행 계산이 끝난 뒤 결과 파일을 쓰기 전, 또는 결과 파일과 상태 파일 사이에 신호가 오면 계산을 마친 행이 결과 없이 `cancelled`(또는 `.started`만)로 남을 수 있다. 행 작업 폴더 `qvina_work`는 행마다 `os.mkdir`로 만들고(행 `try` 밖) `finally`에서 `ignore_errors`로 지우므로, 지우기가 일부 실패해 폴더가 남으면 다음 행의 `os.mkdir`이 `OSError`를 내고 작업 모듈 전체가 멈춘다.
- **영향**: 드물게 계산을 마친 행 하나가 결과 없이 기록되거나, 일괄이 `worker_failed`로 `partial`이 될 수 있다. 숫자가 잘못 나가지는 않는다(실패·취소로 보임). 관찰한 적은 없다.
- **지금 해결하지 못하는 이유**: 독립 코드 검토 권고이며 고정 소스를 바꿔야 한다. 이 기록 작업은 문서만 바꾼다.
- **방향**: 결과 파일·상태 파일 쓰기를 한 신호 차단 구간으로 묶고, 행 폴더를 행 번호별 이름으로 만들거나 시작 전에 지운다. 신호 주입 테스트를 더한다.

## 일괄 활동 시간 예산은 제출 때만 확인한다
- **현상**: `batch_limit_raise_required` 검사는 `POST /jobs` 제출 때 한다. 제출과 시작 사이에 다른 작업·요청이 활동 시간을 쓰면 시작 때 잔여가 필요량보다 작아도 막지 않고, 작업 마감은 min(잔여, 7800초)이 된다(비싼 계산 축은 예약 때 `would_exceed`로 다시 확인함).
- **영향**: 일괄이 필요량보다 짧은 마감으로 `time_exhausted`가 되어 `partial`로 끝날 수 있다. 끝낸 행은 남고 숨지 않는다.
- **지금 해결하지 못하는 이유**: 독립 코드 검토 권고이며 시작 경로(`queue.py`)를 바꿔야 한다.
- **방향**: 시작 때 같은 필요량 검사를 한 번 더 하고 부족하면 시작 전에 거절한다(과금 없음).

## 멈춘 일괄에서도 재사용 행은 `scored`로 남는다
- **현상**: 재사용 행은 작업이 계산하지 않으므로 요약이 멈춤과 무관하게 저장된 결과로 채운다. 그래서 `partial` 요약에서 멈춘 지점 뒤의 재사용 행도 점수가 있다.
- **영향**: 명세 문장 "남은 행은 `not_run`"을 글자 그대로 읽으면 어긋나 보인다. 점수는 실제 저장 결과이고 같은 설정이라 비교 전제는 깨지지 않는다.
- **지금 해결하지 못하는 이유**: 명세 해석 문제이며 바꾸면 요약 규칙과 기존 요약 검증이 바뀐다(사용자 결정 필요, 독립 코드 검토 권고).
- **방향**: 사용자가 원하면 멈춘 뒤 행은 재사용이어도 `not_run`으로 둘지, 지금처럼 둘지 정해 결정 0027에 적는다.

## 51행 일괄의 읽기가 행마다 다시 검증해 느리다
- **현상**: 입장·시작 전 확인은 행마다 M18 입장 검사(수용체 가져오기 gemmi 파싱 포함)를 한다. 요약 목록·상세와 일괄 작업의 `GET /jobs`(진행 필드가 요약을 `validated_summary`로 읽음)는 읽을 때마다 단일 게시·선택 기록·모든 행 결과를 다시 검증하고, 행 결과 검증은 행마다 이벤트 로그를 다시 읽는다.
- **영향**: 정확성 문제는 아니지만 큰 일괄이 여러 개인 run에서 시작 전 확인·목록·2초 폴링이 느려진다(이벤트 로그 재파싱 항목과 같은 원인). 수락 QA 크기(행 4개, 50개 선택은 시작하지 않음)에서는 문제가 보이지 않았다.
- **지금 해결하지 못하는 이유**: 이벤트 읽기 구조를 바꾸는 일이라 M19 범위 밖이다(독립 코드 검토 권고).
- **방향**: 이벤트 로그 증분 읽기 설계 때 게시 대조·수용체 파싱 결과를 한 번만 계산하도록 함께 바꾼다. 진행 필드는 요약 상태를 게시 이벤트에 함께 기록하는 방법도 있다.

## 2시간 일괄 작업 모듈에도 stdout·stderr 1 MiB 상한이 그대로다
- **현상**: guardian은 감시 대상 작업 모듈의 stdout·stderr를 각 1 MiB로 제한한다. 일괄 작업 모듈은 최대 51행·2시간 동안 같은 프로세스로 돌므로, RDKit·Meeko 경고가 행마다 쌓이면 이 상한에 닿을 수 있다(qvina 출력은 작업 모듈이 받아 둠).

- **지금 해결하지 못하는 이유**: guardian 공용 상한을 바꾸는 일이며 독립 코드 검토 권고로 남겼다.
- **방향**: 일괄 어댑터만 상한을 행 수에 맞추거나, 작업 모듈이 화학 패키지 경고를 행별로 잘라 기록한다.

- **영향**: 이 경로들의 화면 표시(`partial`·이유·빈 점수 칸)와 작업 경로 게시는 실제 화면·실제 작업 경로로는 관찰하지 않았다.

- **방향**: 다음 흐름 변경 때 합성 파생 Cys 구조(`backend/tests/fixtures/mutation_model/`)로 L5·L6 사례를, 작은 cutoff로 접촉 0개 사례를 더한다. 짝 승인은 짝을 먼저 여는 별도 run이 필요하지만 모델이 먼저 있어야 하므로 지금 흐름으로는 닿지 않는다.

## 리간드가 있고 M7 사전 검사를 통과하는 공개 구조가 없어 같은 조건 도킹은 합성 리간드로만 검증했다
- **현상**: 로컬 fixture 중 M7 사전 검사를 통과하는 공개 구조는 1UBQ(리간드 없음) 하나다(1HSG·1MQ4와 그 파생 구조, 합성 도킹 수용체는 말단 OXT 누락·중원자 템플릿 불일치·변형 잔기·펩티드 기하로 거부됨, 착수 확인 (e)). 같은 조건 도킹은 1UBQ + 합성 표시 페놀 SDF로 실제 qvina를 돌려 기계적으로만 검증했다.
- **영향**: 실제 기질·리간드 결합 부위에서의 도킹 짝은 관찰하지 않았다. 생물학적으로 의미 있는 자세가 아니다.
- **지금 해결하지 못하는 이유**: M7 규칙(누락 원자를 만들지 않음)을 완화하지 않기로 했고, 사슬 끝 OXT까지 갖춘 공개 복합체 fixture를 새로 들여오는 일은 M21 범위 밖이다.
- **방향**: OXT가 있고 비표준 잔기가 없는 공개 단백질–리간드 구조를 출처·라이선스와 함께 fixture로 더하고, 단백질만 투영한 모델과 원래 리간드 SDF로 짝 흐름을 돌린다.

## M21 시간·크기는 1UBQ에서만 쟀고, M7을 통과해도 M18이 받지 않는 크기 구간이 있다
- **현상**: 작업 시간(단독 약 23초)과 결과 크기(약 0.6 MB)는 1UBQ(중원자 602)에서만 쟀다. `NoCutoff` GBn2라 큰 구조에서 시간이 원자 수에 비례 이상으로 늘 수 있고, 기본 120초·최대 240초에 걸리면 결과 없이 1단위가 청구된다. 또 M7 한도(중원자 6,000)와 M18 수용체 한도(수소 포함 10,000) 사이에, 1UBQ 비율로 중원자 약 4,890개를 넘는 모델은 같은 조건 도킹이 `receptor_invalid`로 거절된다.
- **영향**: 큰 단백질에서는 시간 초과나 도킹 거절이 날 수 있다. 조용히 잘리지는 않는다.

## 첫 비싼 계산 승인 뒤 `claimed` 작업에서 "작업 시작"이 사라지는 잠재 결함이 M17·M18·M19·M22 패널에 남아 있다

## M23 수락 QA에서 만들 수 없는 사례는 테스트로만 확인했다
- **현상**: 점수 없는 개체 화면(`SG-individual-without-score`), 4,890 경고(`SG-heavy-atom-warning`), `generations_complete`·`space_exhausted`·`time_exhausted`·`worker_failed`·`resource_exceeded`·`repeated_failure`(`SG-other-stop-reasons`), SL5·L6 문장(`SG-model-conditional-sentences`), dry-run(`SG-dry-run`)은 수락 QA에서 관찰하지 않았다. 덮는 테스트는 `docs/tracking/m23-acceptance.md`에 적었다(1UBQ는 중원자 602개·Cys 없음·모든 개체가 점수를 냄).
- **영향**: 이 경로들의 실제 화면 표시는 보지 않았다. 종료 이유·부분 게시·모델 한계 문장은 실제 엔진 작업 모듈 테스트와 순수 테스트로 확인했다.
- **지금 해결하지 못하는 이유**: 합성 표시 입력(1UBQ + 페놀 SDF)에서는 만들 수 없고 입력을 위조하지 않는다. 리간드가 있고 M7을 통과하는 공개 구조는 로컬에 없다(M21 선례).
- **방향**: Cys·HIS가 바뀌는 변이와 큰 구조 fixture가 생기면 흐름에 더한다.

## 서열 GA의 큰 구조 시간·이벤트 로그 크기는 재지 않았다
- **현상**: 모델링·도킹 시간은 1UBQ(중원자 602개, 평가 약 11초/건)에서만 쟀고 모델링 240초·도킹 300초 단계 상한에 닿는 입력, 중원자 4,890개 근처 구조, 개체 64개 연속 평가, 4시간 실행은 재지 않았다. 큰 구조의 크기·시간은 1UBQ 비율로 가늠했다(개체 하나 ≈ 11 MB, 65개 ≈ 700 MB로 출력 256 MiB가 개체 수보다 먼저 닿을 수 있고 이벤트 로그가 최대 ≈ 210 MB 늘 수 있음).
- **영향**: 큰 단백질 GA는 `resource_exceeded`로 일부만 평가되거나 읽기가 느릴 수 있다(상한에서 조용히 자르지 않고 부분 완료로 알림). 같은 run에서 GA를 여러 번 돌리면 이벤트 로그가 커진다.
- **지금 해결하지 못하는 이유**: M7을 통과하는 큰 공개 구조 fixture와 몇 시간의 실행 예산이 없다.
- **방향**: 실제 사용에서 큰 구조 GA를 처음 돌릴 때 시간·출력·이벤트 로그 크기를 기록하고 상한과 기본 규모를 사용자와 다시 정한다.

## 서열 GA 읽기·작업 목록 폴링이 요약을 다시 검증하는 비용과 검증 틈
- **현상**: 시작 전 확인 `preflight`는 이벤트 로그를 여러 번 읽는다(165 MB 규모에서 4.4초). `GET /jobs`의 `progress`는 요약이 게시된 뒤 폴링마다 `validated_summary`를 다시 부른다(M22와 같은 구조). 독립 코드 검토가 권고한 검증 틈: `evaluation` 라벨(`reused`·`computed`)을 게시 증거와 대조하지 않음, 세대 안 슬롯 순서(교차 → 편집 → 무작위)를 검증하지 않고 개수만 셈(점수·핸들은 저장된 값과 대조되므로 과학 값은 바뀌지 않음), M18 수용체 읽기 경로는 기준 모델과의 관계를 다시 보지 않음(요약 읽기가 전체 검증).
- **영향**: 정확성 문제는 아니지만 요약이 많은 run의 폴링이 느려질 수 있고, 변조로 재사용 수와 S3 표시를 꾸밀 수 있다(점수는 저장된 값이라 바뀌지 않음).
- **지금 해결하지 못하는 이유**: 이벤트 증분 읽기·검증 캐시 설계와 검증 대조 규칙 추가가 필요하며 명세 목록 밖이다(M19·M22 읽기 항목과 같은 원인).
- **방향**: 이벤트 로그 재파싱 항목과 함께 검증 결과 캐시를 정하고, 검증 목록에 라벨·슬롯 순서 대조를 더할지 정한다.

## M23이 M22에서 물려받은 복구·신호 경계와 사용성 한계
- **현상**: (1) 서버가 `sequence_ga_published` 이벤트 뒤 `job_terminal` 전에 죽으면 복구가 `worker_failed` 요약을 하나 더 게시할 수 있다(handle이 달라 같은 시도에 요약 이벤트가 둘, M22 `ligand_ga_jobs.finish`와 같음). (2) `dock_row`가 돌아온 직후 신호가 막히기 전의 한 바이트코드 구간이 남아 있다(M22와 같음). (3) 사용자 취소를 요청한 실행은 `finish`가 fatal을 내도 큐 `_terminal` 때문에 `cancelled`로 보이고 fatal 진단이 남지 않는다. (4) `finish`가 M7 `preflight`를 다시 불러 서버 재시작 복구 때 OpenMM을 쓸 수 없으면 요약 없이 `failed`가 된다. (5) 화면은 GA가 도는 동안(최대 4시간) 저장된 요약 열기를 막고, 같은 인자 재제출은 예산 부족이면 이미 끝난 GA를 다시 보이려고도 증액을 요구한다(서버는 기존 작업을 예산 검사 전에 돌려줌).
- **영향**: 드문 경계 상황의 진단·복구 한계와 사용성 불편이며 과학 값은 바뀌지 않는다.
- **지금 해결하지 못하는 이유**: M22 이월 구조이고 명세가 정한 동작(한 번에 한 GA, 같은 호출 키 기존 작업 반환)을 바꾸려면 사용자 결정이 필요하다.
- **방향**: 요약 중복 게시를 호출 키 단위로 막고, 화면의 요약 전환 차단을 요청 단계로 좁힐지와 기존 작업이 있으면 증액 요구를 건너뛸지 사용자와 정한다.

## `docs/system-architecture.md`가 M20–M23 구성 요소를 설명하지 않는다
- **현상**: 구성 요소·의존 방향·업로드→보고서 흐름 문서에 M20 변이 후보, M21 변이 구조 모델링, M22 리간드 GA, M23 서열 GA(두 인터프리터를 한 프로세스 그룹에서 쓰는 구조 포함)의 모듈과 흐름이 없다(M19 뒤부터 이어진 갱신 누락).

- **지금 해결하지 못하는 이유**: M23 단계의 갱신 범위(변경한 규칙·계약·운영·표준·주의점 문서) 밖이고 M20부터 이월된 문서 정리 작업이다.
- **방향**: M24 착수 전에 구성 요소·의존 방향·작업 경로 그림에 M20–M23을 더한다.
