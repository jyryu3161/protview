## 0. 먼저 짚어야 할 사실 세 가지

1. **JEV는 글을 쓰는 모델이 아니라 판정하는 모델이다.** 현재 게이트가 쓰는 엔드포인트는 `POST https://openrouter.ai/api/alpha/decisions`(`gate.py`)이고, 이 API의 질문 형식은 `choice`(미리 정한 선택지 중 하나), yes/no, `score`(미리 정한 구간 점수) 세 가지다([ai-sdk-provider schemas.ts](https://github.com/OpenRouterTeam/ai-sdk-provider/blob/main/src/evaluation/schemas.ts)). 따라서 JEV는 새 서열이나 새 SMILES를 **직접 써낼 수 없다.** "JEV가 제안한다"를 이루는 길은 두 가지다.
   - (권장) 로컬 엔진이 후보 목록을 만들고, JEV는 그중 무엇을 먼저 계산할지·어디서 멈출지 **고른다.**
   - (별도 결정 필요) 자유 텍스트를 내는 채팅 모델(원래 계획의 "Frontier")을 두 번째 목적지로 게이트에 추가한다. 현재 보안 정책은 목적지를 decisions 하나로 고정한다.
2. **결정 0015는 금지 규칙을 없앴을 뿐, 전송 경로를 만든 것이 아니다.** 게이트는 아직 `viewer_intent@1`, `inspection_state@1` 두 투영만 만든다. 새 데이터 종류를 보내려면 투영 스키마·UI 미리보기·예산·감사 기록을 새로 구현해야 하고, 실제 호출 검증은 결정 0012에 따라 매번 횟수 할당을 받아야 한다(M8 할당 4회는 소진).
3. **"좋아졌다"를 판정할 검증된 엔진이 아직 하나도 없다.** 결정 0006으로 Rosetta는 사용할 수 없고, ΔΔG·친화도·안정성 이름은 실제 검증된 엔진 없이 쓸 수 없다. 그래서 새 기능이 보고할 수 있는 값은 "엔진 이름 + 고유 단위"가 붙은 값(도킹 점수, 언어모델 로그우도, OpenMM 전위 kJ/mol, 접촉·SASA·RMSD 변화)뿐이다. 이 제약이 아래 모든 설계를 지배한다.

## B. 지식 베이스 설계: LLM wiki vs RAG vs 혼합

### B.1 이 제품의 제약

- 과학 주장은 필드 단위로 근거에 묶인다(source handle, 필드 경로, 단위, 정확한 값·렌더링 값).
- 계산하지 않은 수치를 만들지 않는다. 근거 없는 서술은 숫자가 맞아도 거부한다.
- 잔기는 7필드가 전부 같을 때만 같다. 표시 문자열을 파싱해 식별자를 만들지 않는다.
- 한 사람이 쓰는 로컬 도구. 외부 HTTP는 `EgressGate` 하나.
- 이벤트만으로 전부 복원 가능해야 한다.

### B.2 세 방식 비교

| 기준 | LLM wiki (LLM이 관리하는 마크다운) | RAG (문헌 검색 후 인용) | 혼합 (구조화 참조층 + 인용 검증 문헌층 + 파생 wiki) |
|---|---|---|---|
| 근거 추적 | 약하다. 문장이 어느 원문에서 왔는지 흐려지고 편집이 쌓이면 출처가 사라진다 | 중간. 조각 단위 출처는 남지만 잔기·필드 단위가 아니다 | 강하다. 참조 레코드는 필드 단위, 문헌은 원문 인용 구간 + 출처 ID |
| 없는 값이 생길 위험 | 높다. 요약·일반화 단계에서 수치와 인과가 새로 태어난다 | 중간. 검색이 맞아도 조각을 합치는 과정에서 생긴다 | 낮다. 수치는 구조화 레코드에서만, 문헌은 원문에 실제 존재하는 구간만 |
| 잔기 번호 연결 | 사실상 불가(산문 속 "Met793"은 식별자가 아니다) | 불가 | 가능. 번호 대응 객체를 따로 만든다 |
| 최신성 | 사람·모델이 다시 써야 한다 | 색인만 다시 만들면 된다 | 스냅샷 날짜·버전 명시 후 재빌드 |
| 비용 | 페이지 유지에 모델 호출이 계속 든다 | 임베딩 또는 BM25(BM25는 모델 불필요) | 참조층은 모델 불필요, 문헌층만 비용 |
| 재현성 | 낮다 | 임베딩 고정 시 중간, BM25는 높다 | 높다(해시 고정 스냅샷 + 결정적 빌드) |
| JEV 소비 | 페이지 전문을 넣어야 해서 크다 | 상위 조각을 넣는다 | ID 붙은 짧은 레코드만 넣는다 |

**권장: 혼합.** 정본은 구조화 참조 레코드 + 원문 인용이 검증된 문헌 레코드이고, wiki는 그 둘에서 **결정적으로 생성하는 파생 보기**로만 둔다. LLM이 wiki를 직접 편집하게 하지 않는다. 이 선택은 `kbase_kinase`가 이미 택한 설계(ADR-002 "wiki는 파생물이며 정본이 아니다", ADR-013 "규칙은 집계만, 산문 없음")와 같고, ProtView의 증거 규칙을 만족하는 유일한 방식이다.

- LLM wiki만으로는 보고서 증거 규칙(필드 경로·정확한 값)을 만족시킬 방법이 없다. 페이지 문장은 계산 결과도 원문 인용도 아니다.
- RAG만으로는 "이 구조의 A:793이 계열 공통 번호로 몇 번인가"에 답할 수 없다. 그 답은 텍스트 검색이 아니라 대응표에서 나온다.
- 구조 분석에 실제로 쓸모 있는 지식 대부분은 잔기 단위 표 데이터(포켓 잔기, 계열 공통 번호, 촉매 잔기, UniProt 주석)이고 LLM이 필요 없다.

### B.3 네 층 구조

1. **참조층**: 외부 DB 스냅샷을 날짜·파일 해시와 함께 로컬에 둔다. 서버는 런타임에 외부 조회를 하지 않는다. 갱신은 관리자 명령 한 번(`kbase_kinase`의 `sync-ref` 방식).
2. **번호 대응층**: 사용자 구조 잔기 7필드 ↔ UniProt 위치 ↔ 계열 공통 번호. 불변 객체(B.6).
3. **문헌층**: 재사용이 허용되는 오픈 액세스 원문만 로컬 색인. 결과는 "원문 인용 구간 + 출처 ID + 버전". 처음에는 BM25(SQLite FTS5)로 시작한다 — 가중치가 없어 결정적이고 재현된다. 임베딩 검색은 BM25로 부족하다는 증거가 생긴 뒤에 추가한다.
4. **파생 wiki**: 계열·단백질별 마크다운을 위 세 층에서 템플릿으로 생성한다. 스냅샷 버전과 소스 레코드 ID를 페이지에 박는다. 사람이 훑어보는 용도이며 보고서 증거가 아니다.

### B.5 인용이 보고서 증거가 되는 방법

계산 증거와 **섞지 않는** 새 증거 종류 두 개를 만든다.

- `reference_annotation@1`: `{source:"uniprot", source_version:"2026_03", snapshot_sha256, record_id:"P00533", field_path:"features[12].location", value, retrieved_date}`. 보고서에는 "UniProt 2026_03 주석"으로 표시하고 계산 결과가 아니라고 못 박는다.
- `literature_quote@1`: `{source_id:"PMID:…"|"PMCID:…", license_code, version_or_date, locator:{page, section, table_row}, quote(단어 수 제한), quote_verified, verification_method:"exact_substring@1"}`. `quote_verified`는 저장된 원문에 그 구간이 정확히 있는지 빌드 시 확인한 결과다. 인용 없는 요약 문장은 증거가 될 수 없다.
- 보고서 검증기는 **문헌 속 숫자를 ProtView 계산의 증거로 쓰지 않는다.** 필드 규칙에 "외부 보고값(측정 아님)" 표시를 추가한다.
- LLM이 추출한 미검수 레코드는 `review_status: unreviewed`를 그대로 보여 주고, 인용 검증 여부를 따로 표시한다.

### B.6 잔기 번호 대응 — 가장 중요한 부분

1. **공개 PDB 구조**: SIFTS가 `label_seq_id`(=`seq_label`) ↔ UniProt 위치를 준다. author 번호로 맞추지 않는다. `seq_label`이 null인 잔기는 대응 없음으로 둔다.
2. **미공개·사용자·모델 구조**: PDB ID가 없어 SIFTS를 못 쓴다. 구조에서 뽑은 서열을 **사용자가 명시적으로 고른** UniProt 서열에 로컬 전역 정렬하고(정렬기·행렬·gap 설정 고정), 정렬 결과와 동일성 %를 객체에 기록한다. "가장 비슷한 것"을 자동으로 고르지 않는다.
3. **공통 번호**: UniProt 위치 → KLIFS 포켓 번호(1–85) / GPCRdb 번호(예: 3.50x50) / M-CSA 촉매 잔기. 대응표는 참조층 스냅샷에서 온다.
4. **저장 형태**: 불변 `residue_numbering_map@1`. 행마다 `{residue: 7필드, uniprot_accession, uniprot_position|null, generic:{scheme,label}|null, method:"sifts@<snapshot>"|"local_alignment@1", status: mapped|unmapped|conflict}`. 삽입 코드·altloc·다중 모델은 7필드로 구분한다.
5. **충돌은 고르지 않는다.** SIFTS와 로컬 정렬이 다르거나 두 출처의 판정이 엇갈리면 `conflict`로 양쪽을 보존한다(`kbase_kinase` intend §7과 같은 원칙).
6. 검증: 1hsg(비 kinase), 공개 kinase 구조, 삽입 코드가 있는 구조, label 필드가 없는 PDB 입력으로 왕복 검사.

### B.7 `kbase_kinase`는 무엇이고 무엇을 쓸 수 있나

**정체**: kinase 구조 기반 lead optimization 지식 베이스. 원자 단위는 **Design Move** — 화합물 A→B 변형 한 건에 유발 구조 관찰, 측정 효과와 assay 조건, trade-off, 원문 표 행·그림 패널 포인터가 붙는다. 명시된 소비자는 "복합체를 보고 다음 화학 변형을 제안하는 LLM agent"다. 사용자 목표 (b)와 거의 그대로 맞는다.

**구조**:
- `src/kbase/`(도메인을 모르는 엔진: 레코드 IO, 스키마 검증, 스냅샷·캐시, PDF 파서 래퍼, LLM 클라이언트, 빌드, reader, wiki 렌더러) / `src/domains/kinase/`(kinase 지식, 폐쇄 어휘, 프롬프트, 소스 어댑터, 질의). 경계는 `tests/test_engine_isolation.py`가 import 그래프로 감시한다.
- 두 계층: reference(전체 kinome, KLIFS·KinCore·UniProt·SIFTS·RCSB·InterPro·KinHub 스냅샷에서 기계 생성) + knowledge(논문 PDF에서 `deepseek/deepseek-v4.1-flash`로 추출, MinerU·Docling 두 파서 교차, ChEMBL 3차 대조).
- 정본은 JSONL(`kb/`, `dist/`) + 해시가 든 `dist/manifest.json`(`kb_version: kbv1:ae11f41d19e5bef9`) + 소비 계약 `dist/CONTRACT.md`. `wiki/`(kinases 77, papers 253, tactics, families)는 결정적 파생물.
- 현재 규모: moves 891, moves_flagged 885, structures 13,415, references 555, figures 4,380, tactics 240, mutations 0.
- **임베딩·벡터 검색은 없다.** 질의는 KLIFS 모양의 구조 descriptor JSON(`target`, `site_features.occupied_subpockets`, `dfg_state`, `goal`)을 태그·필드 필터로 바꾼다. 읽기 전용 MCP 서버(`describe`, `ask`, `find_structures`; stdio·HTTP 127.0.0.1)가 있다.
- 모든 레코드는 `review_status: unreviewed`, 신뢰도 점수 없음, 인용 구간은 25단어 이하, 저장소 비공개(ADR-021).
- 수치 규칙이 엄격하다: 부등호가 있으면 배수 계산 금지, assay 조건 일치가 확인되지 않으면 배수 계산 금지, 방향과 크기 등급은 항상 채운다.

**재사용 후보**:
- (가치 가장 큼) 커밋된 `dist/`를 **읽기 전용 외부 참조**로 소비. 코드 import 없이 JSONL만 읽거나 MCP 서버를 별도 프로세스로 둔다. ProtView가 M11·M12 결과로 descriptor를 만들고 전례는 그쪽이 돌려준다 — 두 저장소의 설계 의도와 경계가 정확히 맞는다.
- 설계 패턴 차용: 스냅샷+해시+오프라인 빌드, 충돌 보존, 파생 wiki, 엔진/도메인 분리(GPCR·enzyme 도메인을 추가할 때 그대로 쓸 수 있는 골격).
- 하지 말 것: 레코드를 ProtView 계산 결과처럼 표시하는 것, `kbase_kinase` 코드를 서버 프로세스에 import하는 것.

**필요한 결정**: `docs/standards.md`의 "`../kbase_kinase`에서 과학 코드·데이터·결론을 가져오지 않는다"를 다음처럼 좁히는 결정 기록.
> 커밋된 `dist/`를 고정 커밋 SHA와 `kb_version`으로, **별도 증거 종류(미검수 외부 전례)** 로 읽는 것은 허용한다. 코드 import, 계산 결과로 표시하는 것, 미검수 표시를 지우는 것은 금지한다.

함께 확인할 것: KLIFS·KinCore 라이선스 불명, ChEMBL CC BY-SA 동일조건, 25단어 인용 제한이 ProtView 보고서 내보내기에도 걸리는지.

### B.8 원래 계획의 "Knowledge Pack SDK" 제외와의 관계

`agent_protein_viewer_plan_v05.md` §2는 "Knowledge Pack SDK, 플러그인 마켓"을 만들지 않는 목록에 넣었다. 권장안은 이를 뒤집지 않는다. 계열 지식을 **SDK가 아니라 코드에 고정된 내장 참조 스냅샷**(kinase, GPCR, enzyme 3종)으로 넣고, 사용자가 임의 팩을 설치하는 기능은 계속 만들지 않는다. 다만 "지식 연결 기능을 넣는다" 자체는 새 결정으로 기록해야 한다(F-4).

### B.9 JEV가 지식을 소비하는 방식

state에 들어가는 것은 긴 문서가 아니라 ID가 붙은 짧은 레코드다.

```
knowledge_context@1 = {
  numbering:   [{alias:"r0012", generic:"KLIFS:45", uniprot_pos:790}],
  annotations: [{id:"ann-3", source:"uniprot@2026_03", text:"…"}],
  precedents:  [{id:"kb:MOVE-0014", review:"unreviewed", direction:"worsened",
                 quote:"…", quote_verified:true}]
}
```

JEV는 선택지 이름만 돌려주므로 "어떤 ID를 근거로 봤는가"는 알 수 없다. 보고서에는 보낸 context 해시와 고른 선택지만 기록하고, 지식 레코드가 그 선택의 **이유였다고 주장하지 않는다.**

### B.10 먼저 만들 시제품

1. **kinase 번호 대응 하나**: 공개 kinase 구조 1개 + SIFTS + KLIFS 85잔기 → `residue_numbering_map@1` → Mol*에서 hinge·gatekeeper·DFG 잔기 강조 → 보고서에 `reference_annotation@1`. LLM 없음, 외부 요청 없음(스냅샷은 미리 받은 파일). 이것만으로 "지식이 잔기 단위로 구조 분석에 연결된다"가 증명된다.
2. 그 위에 `kbase_kinase` descriptor 질의(M12 포켓 + M11 상호작용 → occupied subpockets) → 전례 목록 표시.
3. 그다음 GPCR(GPCRdb 번호), enzyme(M-CSA 촉매 잔기). BM25 문헌층은 1·2가 쓸모 있다고 확인된 뒤에.

## C. JEV 에이전트 공학 두 갈래 — 무엇이 실제로 가능한가

여기서 다루는 것은 "어떻게 더 좋은 분자를 만드는가"가 아니라, **제품이 정직하게 표시·기록할 수 있는 범위**다. 두 갈래 모두 아래 세 가지가 먼저 있어야 성립한다.

1. 후보를 만드는 실제 로컬 엔진 (모델이 아니라 코드가 만든다)
2. 후보를 평가할 실제 엔진 + 그 엔진 고유 이름·단위
3. 게이트 투영·승인·예산 (JEV에 무엇을 보내고 무엇을 돌려받는지)

하나라도 없으면 그 기능은 "사용할 수 없음 + 이유"로 두어야 한다. 이것이 지금 M12·M13 이후에 남은 실제 작업량의 대부분이다.

### C.1 루프의 형태와 통제

```
사용자 목표·제약 선택
  → 로컬 후보 생성기(결정적, 상한 있는 목록)
  → JEV choice: 어느 후보를 먼저 계산할지 / 멈출지
  → 과학 계산 승인 → 실제 엔진 실행
  → 결과 표(엔진 이름·단위 그대로)
  → JEV choice: 계속 / 멈춤
  → (상한 내 반복) → 사람이 최종 선택 → 보고서
```

- 실행 기반은 M13을 그대로 쓴다(불변 계획, 한 단계씩 Advance, 범위 한정 Stop, 충돌 복구). 반복 한 번은 새 계획 버전이다.
- 판단 라벨은 원래 계획 §7.3대로 `rule` / `jev` / `human`. 임계값으로 잘리는 판단에는 JEV를 쓰지 않는다. 그래야 나중에 "JEV가 실제로 기여했는가"를 규칙 기준선과 비교해 측정할 수 있다.
- 가드: 기존 규칙(같은 호출 키 3번째 정지, 새 handle 없는 제안 4회 정지, 진동 정지) + 반복 상한(기본 5) + 후보 수 상한 + 반복당 JEV 호출 상한.
- 예산: 현재 run 한도(1800초, 비싼 계산 8회, 외부 토큰 120,000, USD 2.00)는 반복 루프에 작다. 루프 전용 한도는 별도로 기록된 변경으로만 올린다. 소진 시 `checkpoint_and_ask`.
- 최종 후보 선정은 항상 사람(원래 계획 §4.5). JEV `score` 응답 숫자는 **모델 판정값**이며 과학 값 칸이나 보고서 수치 증거에 넣지 않는다. 표시할 때 "JEV 판정"이라는 이름을 붙인다.
- 게이트로 나가는 새 투영(예: `engineering_state@1`): 후보 별칭 목록, 계산 결과 요약(엔진 이름·단위 포함), 번호 대응 요약, `knowledge_context@1`. 결정 0015로 좌표·서열 전송도 허용되지만 **권장은 필요한 최소한**이다(포켓 주변 잔기 요약 수준부터). API 키와 로컬 경로는 여전히 절대 나가지 않는다.
- 모델이 낸 선택·제안은 `proposal` 종류로 저장하고, 계산 객체와 같은 화면·같은 표에 섞지 않는다.

반드시 지킬 두 가지:
- **서열이 다른 두 구조의 OpenMM 전위를 비교하지 않는다.** 원자 수와 항이 달라 차이값에 의미가 없다. 차이를 보여 주면 사실상 가짜 ΔΔG가 된다. 변이 구조에서 OpenMM은 "이 모델 구조가 물리적으로 터지지 않았는지" 확인용이다.
- ESM·ProteinMPNN은 PyTorch가 필요하다. ProLIF처럼 **격리 작업 환경 + wheel 해시 잠금 + 가중치 파일 해시 고정**으로 둔다. 가중치 받기는 설치 스크립트에서 한 번만 하고, 새 외부 목적지가 생기는 일이므로 별도 허용 결정이 필요하다(결정 0015는 "보내는" 것에 대한 결정이다).

주의할 점:
- 도킹 점수는 순위용 근사값이다. 보고서에서 "친화도", "개선", "더 강한 결합"으로 바꿔 부르지 않는다. 같은 수용체·같은 상자·같은 seed·같은 exhaustiveness에서 나온 값끼리만 나란히 보여 준다(설정을 객체에 기록).
- 도킹은 seed에 따라 결과가 흔들린다. seed와 반복 횟수를 고정·기록하고, 재현 검사를 수락 조건에 넣는다.
- **리간드가 든 복합체 OpenMM은 별도 과학 프로젝트다**(결정 0006). 리간드 힘장 매개변수화 없이 복합체 에너지를 내지 않는다.
- 변형된 리간드는 M11 규칙상 "사용자가 준비한 SDF"의 지위를 갖지 못한다. 엔진이 만든 수소·tautomer는 **생성된 것**이라고 표시하고, M11의 "사용자가 준 protonation을 그대로 쓴다"는 계약과 분리한다. 이 구분을 흐리면 M11 증거 규칙이 깨진다.

## D. ODDT 평가

**무엇인가**: Open Drug Discovery Toolkit. 상호작용 지문(SIFt, PLEC), 재채점 함수(RF-Score 계열, NNScore), 도킹 래퍼(Vina 등), 가상 스크리닝 파이프라인, scikit-learn 연동을 한 패키지로 묶은 툴킷. BSD-3-Clause([github.com/oddt/oddt](https://github.com/oddt/oddt)).

**유지 상태 — 가장 중요한 사실**: master의 최근 커밋이 **2022-02-03(README 수정)**, 그 이전 실질 커밋은 **2021-04(0.8 릴리스)**다([커밋 목록](https://github.com/oddt/oddt/commits/master)). 즉 약 5년간 실질적 유지가 없다. 선언 의존성은 OpenBabel 3.0+ 또는 RDKit 2018.03+, Python 3.6+, NumPy/SciPy/scikit-learn/pandas/joblib다.

**ProtView 스택과의 호환 위험 (높음)**:
- 현재 M11 잠금은 RDKit 2026.3.6, numpy 2.4.6, pandas 3.0.6, scipy 1.17.1, Python 3.11이다. 2021년에 멈춘 패키지가 numpy 2.x / pandas 3.x와 맞을 가능성은 낮다(특히 `np.float`류 제거, pandas API 변경). 실제로 import·계산이 되는지는 **실행해 봐야만** 안다.
- scikit-learn 모델(RF-Score, NNScore)은 pickle로 배포되는 경우가 많아 버전이 다르면 로드가 깨지거나 조용히 다른 결과를 낸다. 이건 과학 결과에 직접 영향을 준다.
- OpenBabel 경로를 쓰면 GPL 의존이 생기고, 네이티브 빌드가 또 하나 늘어난다. RDKit 경로만 쓰도록 고정하는 편이 낫다.

**ProLIF(M11)와의 관계**: 겹치는 부분은 상호작용 판정이고, ODDT가 추가로 주는 것은 (1) 벡터화된 지문(PLEC/SIFt: 기계학습 입력이나 후보 간 비교에 쓰기 쉬움), (2) 도킹 포즈 재채점 함수다. 반대로 ProLIF는 최신 RDKit·MDAnalysis 기반이고 M11에서 이미 검증·잠금되어 있다. **ODDT는 ProLIF를 대체하지 않는다.**

**권장 역할**: 우선순위 낮음, 그리고 **조건부**다.
1. 먼저 30분짜리 조사: 별도 venv(Python 3.11)에서 `pip install oddt` + 현재 잠금 근처 버전으로 import·PLEC·RF-Score를 실제 실행. 깨지면 여기서 끝낸다.
2. 통과하면 M11과 같은 방식(격리 작업 환경, wheel 해시 잠금, 버전 고정, 실제 검증)으로만 넣는다. ProLIF와 **다른 방법 이름**으로 둔다.
3. 필요해지는 시점은 리간드 변형 후보를 여러 개 비교할 때(지문 기반 비교, 포즈 재채점)다. 그 전에는 넣지 않는다.
4. 대안: 지문만 필요하면 ProLIF도 비트벡터 출력을 낼 수 있어 새 의존성 없이 갈 수도 있다(현재 M11 구현이 무엇을 내는지 확인 필요).

### "완성"의 정의 (제안)

원래 계획에는 M13 이후 단계가 정의되어 있지 않고 M6 이후는 "(선택)"이었다. 그래서 완성선을 새로 정해야 한다. 제안하는 문장:

> **완성 = 한 사람이 자기 컴퓨터에서, 구조 하나를 열어 (1) 로컬 계산으로 부위·상호작용·표면·공동을 보고, (2) 그 부위가 계열 지식에서 무엇이라 불리는지 잔기 단위로 확인하고, (3) 서열 변경안과 리간드 변경안을 후보로 만들어 실제 엔진으로 계산하고, (4) JEV가 어느 후보를 먼저 볼지 골라 주는 반복을 예산·승인 안에서 돌린 뒤, (5) 모든 수치가 handle·필드·단위로 역추적되고 모든 인용이 출처·버전으로 역추적되는 보고서를 얻는다.** 이 다섯이 실제 데이터로 한 번 끝까지 돌아가고 검토를 통과하면 완성이다.

여기에 **포함하지 않는 것**을 같이 못 박는다: 다중 사용자·인증·공유, 외부 공개, 플러그인 SDK, MD 궤적, 자유 에너지, 복합체 OpenMM, 백그라운드 완전 자율 실행, GUI 파이프라인 편집.

- ProteinMPNN·PDBFixer·fair-esm 라이선스와 Vina 1.2 라이선스는 기억 기반이므로 착수 시 저장소에서 직접 확인해야 한다.

## G. 제품 구조 (정보 구조)

최상위를 작업 공간(탭) 4개로 나눈다. 기능을 탭으로 분리하는 것이 사용자 요구다.

| 탭 | 담는 것 | 현재 화면 대응 |
|---|---|---|
| **구조 분석** | M0–M12 전부: 불러오기·전처리, Mol* 보기, 기하 접촉, SASA, 원자 거리·정렬, 화학 상호작용(M11), 공동 후보(M12), 저장 보기·PNG, 보고서 | 현재 메인 페이지, `ChemicalWorkspace`, 포켓 패널이 그대로 이 탭 안으로 들어간다 |
| **단백질 공학** | 변이 후보 정의, 변이 구조 모델링, 변이 전후 분석, 설계 모드(JEV / GA), 파라미터 편집, 결과 표·순위 없는 비교 | 새 화면 |
| **리간드 설계·탐색** | 리간드 부위(슬롯) 지정, building block·reaction rule 열거, 필터, 도킹, 결과 표, 설계 모드(JEV / GA), 파라미터 편집 | 새 화면. M11 화학 입력 화면과는 **다른 화면**이며 입력 종류도 다르다 |
| **지식·보고서** | 참조 스냅샷 상태, 번호 대응, 계열 주석, 문헌 인용, 전례 조회, 생성한 보고서·그림 목록 | 현재 보고서 화면을 확장 |

**공용 구성 요소**(탭이 공유하지만 각 탭이 소유하지 않는다):

- **소스(source)**: structure / prepared_structure / chemical_structure handle. 어느 탭에서 만들어도 같은 불변 객체다.
- **보기(scene)**: M9 `viewer_scene@1`. 어느 탭에서든 저장·복원한다. 복원은 도구를 다시 실행하지 않는다.
- **작업(job)**: 기존 JobQueue 하나. 탭이 늘어도 큐는 하나이고 예약·잠금 규칙은 그대로다. 탭별 병렬 워커를 새로 만들지 않는다.
- **계획·실행(plan/execution)**: M13의 `analysis_plan@1` + 실행 기록. 공학·설계 루프도 같은 기반을 쓴다. 탭마다 다른 실행기를 만들지 않는다.
- **보고서·증거**: 기존 증거 검증기 하나. 새 값 종류가 생기면 필드·단위 규칙을 추가할 뿐, 검증기를 우회하는 경로를 만들지 않는다.
- **예산·승인**: run 단위 하나. 탭이 다르다고 별도 예산을 갖지 않는다.

**경계 규칙**:
- 탭은 화면 구분이지 권한 구분이 아니다. 뷰어 동의가 설계 실행 권한을 주지 않는다(기존 규칙 유지).
- 설계 탭에서 만든 제안(변이안·리간드 변형안)은 `proposal` 종류로, 계산 결과와 **다른 표·다른 색**으로 보여 준다.
- 사용할 수 없는 기능은 탭 안에서도 이유와 함께 "사용할 수 없음"으로 남긴다. 빈 탭이나 자리표시자 숫자를 두지 않는다.

## H. 시나리오 카탈로그

판정 기준: **가능**(기존·계획된 기능으로 정직하게 된다) / **조건부**(조건을 만족해야 한다) / **배제**(정직하게 주장할 수 없거나 범위 밖).

### H-1. (사용자 시나리오 1) 현재 결합 구조의 kinase hinge 상호작용을 논문용으로 시각화 — **조건부 가능**

- **입력**: 구조 파일(로컬), 모델 번호, 리간드 인스턴스 하나. 계열 지식 사용 시 사용자가 고른 UniProt accession.
- **hinge 잔기 식별**: 두 경로를 둔다.
  1. (권장, M15 필요) 번호 대응: 공개 PDB면 SIFTS로 `seq_label` ↔ UniProt 위치, 사용자 구조면 사용자가 고른 UniProt 서열에 로컬 정렬 → KLIFS 포켓 번호(1–85)로 hinge 구간(대략 45–48 부근, 스냅샷 정의를 그대로 따른다) 표시. 대응 결과는 `residue_numbering_map@1`에 `mapped/unmapped/conflict`로 남고, `unmapped`는 그대로 보여 준다.
  2. (폴백, 지금도 가능) 사용자가 잔기를 직접 고른다. 이 경우 화면·보고서에 "사용자 지정 잔기(계열 번호 대응 없음)"라고 표시한다. **자동으로 "이게 hinge다"라고 단정하지 않는다.**
- **표시할 상호작용**: 두 종류를 **분리**해서 보여 준다.
  - M0/M5 기하 접촉: 중원자 거리(Å)만. `polar_contact`/`hydrophobic_contact`/`contact`는 원소 기준 분류이며 수소결합 판정이 아니다.
  - M11 ProLIF 화학 상호작용: 사용자가 준비한 수소·연결 정보를 쓴 범주 판정(D···A 거리 Å, D–H···A 각도 °). 이걸 쓰려면 명시적 수소 좌표와 완전한 CONECT 또는 `receptor_bonds@1`, V2000 SDF 리간드가 필요하다.
  - 둘 중 하나로 다른 하나를 덮어쓰지 않는다. 그림 범례에 어느 방법인지 적는다.
- **그림 내보내기**: M9 PNG + 출처 JSON(소스 handle, 보기 필드, 선택 잔기). 현재 한도는 64–2048 px, 400만 픽셀 이하, PNG 하나 8 MiB, run당 그림 100개다. **논문 그림은 보통 300 dpi에서 2048 px를 넘어가므로**(예: 단일 컬럼 90 mm × 300 dpi ≈ 1063 px는 통과, 두 컬럼 180 mm × 600 dpi ≈ 4250 px는 초과) 고해상도 내보내기가 필요하면 별도 작업으로 한도를 올리고 재검증해야 한다(F′-14). 지금은 2048 px 안에서 가능하다고만 말한다.
- **산출물**: 상호작용 표(방법 이름·단위 그대로), 강조된 보기, PNG + 출처, 증거 연결 보고서.
- **필요 단계**: 폴백 경로는 지금도 가능. 번호 대응 경로는 M15. 고해상도는 별도.
- **배제**: "이 hinge 수소결합이 결합력의 핵심"류 해석 문장, 상호작용 개수에서 친화도·안정성 추론.

### H-2. (사용자 시나리오 2) JEV 기반 설계로 hinge에 잘 결합하는 리간드 결합 구조 찾기 — **조건부 가능, 단 주장 범위를 크게 좁힘**

- **정직하게 할 수 있는 것**: 지정한 부위(hinge 잔기 집합 또는 M12 공동) 주변에서, 로컬로 만든 리간드 변형 후보들의 **도킹 포즈와 점수 표**를 만들고, 각 포즈가 지정 잔기와 어떤 상호작용을 이루는지 M11/기하 접촉으로 표시하는 것. JEV는 "다음에 어느 후보를 계산할지", "여기서 멈출지"를 고른다.
- **배제**: "이 리간드가 hinge에 잘 결합한다", "친화도가 높다", "가장 좋은 후보"라는 주장. 도킹 점수는 스코어링 함수 값이며 친화도가 아니고, 실험 검증 없이 순위를 결과로 제시하지 않는다.
- **배제**: JEV가 SMILES를 직접 만드는 경로. decisions API는 choice/yes-no/score만 받는다(§0).
- **필요 단계**: M16(변형·도킹) + M14(게이트 투영) + M18(루프). 부위를 계열 번호로 지정하려면 M15.

### H-3. (사용자 시나리오 3) 현재 기질과 잘 결합하도록 단백질 서열 변경 + 반응 지식 연결 — **조건부 가능, 활성 주장은 배제**

- 상세는 K절. 요점: 촉매 잔기 보호(M-CSA), 포켓 접촉 잔기에서 변이 후보 생성, PDBFixer+OpenMM 모델링, 기질 포즈 재채점·접촉·SASA 비교까지가 정직한 범위다.
- **배제**: kcat·kM·활성 향상·기질 특이성 개선 주장(동역학 엔진이 없다), ΔΔG·안정성 이름(결정 0006), 서열이 다른 두 구조의 OpenMM 전위 차이를 효과로 제시하는 것.
- **필요 단계**: M15(반응 지식·촉매 잔기) + M17(변이 모델링) + M14·M18(JEV 루프 쓸 경우).

### H-4. (사용자 시나리오 4) JEV 기반 설계와 GA 기반 설계를 각각, 파라미터·환경 편집 가능 — **가능(설계 필요)**

- 상세는 I절. 두 모드를 **별개 엔진**으로 두고 같은 후보 생성기·같은 평가 엔진을 공유한다. GA는 완전 로컬이므로 외부 요청 0건으로 돌 수 있고, 이것이 JEV 없이도 설계 탭이 동작하는 근거가 된다.

### H-5. (사용자 시나리오 5) building block + reaction rule로 특정 부위만 갈아끼우며 도킹 — **조건부 가능**

- 상세는 J절. 요점: 사용자가 리간드에서 바꿀 부위(슬롯)를 명시적으로 지정하고, reaction SMARTS로 열거하고, 필터로 줄이고, core 고정 도킹으로 포즈를 만들고, 점수·상호작용 표를 낸다.
- **배제**: 열거 규모를 사용자가 무제한으로 올리는 것(상한 필요), 합성 가능성 주장("합성 가능"), 점수를 친화도로 부르는 것.

### H-6. (추가 제안) 리간드 시리즈 비교 (SAR 표) — **가능**

- 입력: 같은 수용체 + 리간드 여러 개(사용자 SDF 또는 J절 열거 결과). 흐름: 각각 상호작용 판정·SASA·(도킹 시) 점수 → 공통 잔기 축으로 정렬한 비교 표. 산출: 잔기 × 리간드 행렬(값은 각 방법 이름·단위), 보고서.
- 배제: 표에서 "구조-활성 관계"라는 이름. 활성값이 없으면 SAR이 아니라 "계산 지표 비교 표"다. 외부 활성값을 붙이면 `literature_quote@1`로 인용 표시(M19).
- 필요 단계: M13(워크플로 반복 실행) + M16(도킹 쓸 경우).

### H-7. (추가 제안) 두 단백질의 같은 부위 비교(선택성 관점) — **조건부 가능**

- 입력: 구조 2개 + 각각의 부위(번호 대응 또는 사용자 지정) + 같은 리간드. 흐름: M10 정렬, 부위 잔기 대응(계열 공통 번호가 있으면 그것으로), 각각 상호작용·SASA·도킹 점수 비교.
- 배제: "선택성이 있다/없다" 결론. 두 점수 차이는 선택성 예측이 아니다. 화면 이름도 "선택성 예측"이 아니라 "부위 비교"로 둔다.
- 필요 단계: M15(대응) + M16(도킹 쓸 경우).

### H-8. (추가 제안) 포켓 접촉 잔기 변이 스캔 — **조건부 가능**

- 입력: 구조 + 부위(M12 공동 또는 리간드 접촉 잔기) + 허용 아미노산 집합. 흐름: 위치 × 아미노산 열거(상한) → 모델링 → 접촉·SASA·(리간드 있으면) 재채점 비교.
- 배제: 순위를 "가장 좋은 변이"로 제시, ΔΔG.
- 필요 단계: M17.

### H-9. (추가 제안) 보존성·주석 확인 — **조건부 가능(축소된 형태)**

- 원래 계획의 L2 `conservation`은 로컬 UniRef 사본(수십 GB)이 필요해 보류 대상이었다. 축소안: MSA를 만들지 않고 **UniProt 주석·변이 정보와 계열 공통 번호 주석을 확인**하는 기능으로 대체하고, 이름도 "보존성"이 아니라 "참조 주석"으로 둔다.
- 배제: 계산하지 않은 보존도 점수 표시.
- 필요 단계: M15.

### H-10. (추가 제안) 그림·보고서 패키징 — **조건부 가능**

- 입력: 저장된 보기·그림·결과 handle 집합. 흐름: 보고서 생성 + PNG·출처 JSON 묶음 내보내기. 산출: 불변 보고서 바이트 + 그림 + 출처.
- 조건: 고해상도가 필요하면 F′-14. 저장된 보고서 바이트는 바꾸지 않고 재생성은 새 객체다.

## I. 설계 엔진 두 모드: JEV-guided와 GA-guided

두 모드는 **후보 생성기와 평가 엔진을 공유하고, 선택 주체만 다르다.** 둘 다 같은 M13 실행 기반 위에서 돌고, 결과 표의 값 이름은 완전히 같다.

| 축 | JEV-guided | GA-guided |
|---|---|---|
| 선택 주체 | JEV(choice/score 질문) | 로컬 유전 알고리즘 |
| 외부 요청 | 반복마다 게이트 통과 | **0건.** 완전 로컬 |
| 다루는 후보 수 | 적다(수~수십). 토큰·비용 제약 | 많다(수백~수천, 상한 내) |
| 재현성 | 모델 응답이 바뀌면 달라진다. 모델 pin·응답 캐시로 완화 | seed를 고정하면 재현된다 |
| 예산 | USD·토큰·비싼 계산 | 시간·비싼 계산 |
| 기록 | 선택 이벤트 `decided_by=jev`, 보낸 payload 해시 | `decided_by=rule`, seed·세대별 기록 |
| 쓰는 국면 | 임계값으로 안 갈리는 회색 지대 판단, 방향 전환, 중단 | 넓은 조합 공간 탐색 |

**GA 구성**(서열·리간드 공통 골격):
- 개체: 서열 모드 = {허용 위치 → 아미노산} 배정. 리간드 모드 = {슬롯 → building block/규칙 선택} 배정.
- 연산자: 위치·슬롯 단위 변이, 1점·균등 교차, 엘리트 보존, 중복 제거(정규화한 개체 키).
- 적합도: **엔진 이름이 붙은 값의 조합**만 쓴다(예: Vina 점수, 지정 잔기 접촉 수, 매몰 SASA, SA-score, 필터 통과 여부). 다목적은 (a) 가중 합, (b) Pareto 앞면 유지 두 방식을 제공하고, 어느 것을 썼는지 결과에 박는다.
- **적합도 값을 "친화도"나 "품질 점수"로 이름 바꾸지 않는다.** 적합도는 "이 실행의 목표 함수 값"이며 과학 측정값이 아니다. 화면에서 구성 항목의 원래 값·단위를 항상 함께 보여 준다.
- 종료: 최대 세대, 개선 없는 세대 수, 비싼 계산 예산, 시간 상한 중 먼저 오는 것.
- 캐시: 같은 개체가 다시 나오면 기존 호출 키로 결과를 재사용한다(새 물리 계산을 세지 않는다). 이것이 GA에서 가장 큰 비용 절감이다.

**사용자가 편집할 수 있는 파라미터**(전부 상한·enum으로 묶는다):

| 범주 | 항목 | 가드 |
|---|---|---|
| GA | 개체 수, 세대 수, 변이율, 교차 방식, 엘리트 수, seed, 종료 조건 | 각 항목 최소·최대값 고정. seed는 항상 기록(비우면 서버가 정하고 기록) |
| 서열 공간 | 허용 위치 목록(7필드 잔기), 허용 아미노산 집합, 동시 변이 수 상한, 금지 위치(촉매 잔기 등) | 위치는 실제 구조에 존재해야 한다. 금지 위치는 해제하려면 명시적 확인 |
| 리간드 공간 | 슬롯 정의, 사용할 building block 라이브러리, 켤 reaction rule 집합, 열거 상한 | 라이브러리는 등록된 것만. 열거 상한 초과 시 실행 전 거부 |
| 도킹 | 상자 정의(중심·크기 또는 참조 리간드 기준), exhaustiveness, 포즈 수, seed, core 고정 여부 | 상자는 수치로 저장. 엔진 실행 파일·경로는 사용자가 지정 불가(기존 규칙) |
| 필터 | PAINS, Lipinski류 속성 범위, SA-score 임계, 중원자 수 범위 | 필터는 "제외 이유"로 기록. 통과값을 품질로 부르지 않는다 |
| JEV | 질문 템플릿 선택(고정 목록), 반복당 호출 수, state에 넣을 항목 | 질문은 검토된 템플릿만. 자유 프롬프트 입력 불가 |
| 예산·루프 | 루프 반복 상한, 비싼 계산 상한, USD·토큰 상한, 시간 상한 | 기존 run 한도를 넘기려면 별도 기록된 변경 |
| 환경 | 어느 엔진 버전을 쓸지(설치된 것 중 선택) | 버전은 결과 객체에 박는다. 버전이 바뀌면 이전 결과와 같은 것으로 취급하지 않는다 |

**파라미터 편집이 만드는 것**:
- 파라미터를 바꾸면 **새 불변 계획(`analysis_plan@1`의 새 handle)** 이 만들어지고, 이전 계획의 승인은 무효가 된다(M13 규칙 그대로). 화면에서 "설정을 바꿨으니 다시 승인해야 한다"를 명시한다.
- 파라미터는 정규화해서 **호출 키**에 들어간다. 같은 파라미터·같은 입력이면 캐시를 재사용하고, 하나라도 다르면 새 계산이다. seed도 호출 키에 포함된다.
- 조용한 재실행은 없다. 읽기·목록·재열기는 계산하지 않는다(M13 규칙).
- 결과 객체에는 전체 유효 파라미터(기본값 포함), 엔진 버전, seed, 그리고 필터로 제외된 후보 수와 이유가 남는다. 이게 없으면 재현성 주장을 하지 않는다.

## J. 리간드 building block + reaction rule 설계

### J.1 흐름

1. **슬롯 지정**: 사용자가 현재 리간드에서 **바꿀 부분**을 고른다. 원자 선택(M10 AtomRef와 같은 식별 규칙)으로 절단 결합을 지정하고, 남는 쪽을 core, 떨어지는 쪽을 교체 대상으로 둔다. core에는 attachment point(더미 원자)가 붙는다. 슬롯은 여러 개 가능하나 개수 상한을 둔다.
2. **열거**: 선택한 reaction rule(RDKit reaction SMARTS)과 building block 라이브러리로 후보를 만든다. 원자 대응을 유지해 core 원자가 어느 것인지 결과에 남긴다. 실패·불가 조합은 이유와 함께 센다.
3. **필터**: 중원자 수, 속성 범위, PAINS류 구조 경고, SA-score. 각 후보가 왜 제외됐는지 남긴다.
4. **3D 생성**: RDKit ETKDG + 힘장 최소화. core 좌표를 원본에 맞춰 정렬한다.
5. **포즈**: (a) **core 고정 도킹** — core 좌표를 유지하고 교체 부분만 탐색. 원래 결합 양식을 유지하려는 시나리오에 맞고, 결과 해석이 단순하다. (b) 자유 도킹 — 상자 안 전체 탐색. 두 방식 중 무엇을 썼는지 결과에 박는다. **권장 기본값은 (a)**.
6. **평가**: Vina 점수, 지정 잔기와의 접촉·상호작용(M11 또는 기하), 매몰 SASA.
7. **결과 표**: 후보별로 {변형 규칙 ID, building block ID, SMILES, 필터 결과, Vina 점수(kcal/mol), 지정 잔기 접촉 수, 제외 이유}. 정렬은 사용자가 고른 열 기준이며 "순위"라고 부르지 않는다.

### J.2 reaction rule 후보

- **Hartenfeller 2011 "robust organic synthesis reactions"**: 58개 반응을 reaction SMARTS로 인코딩한 공개 데이터셋(논문 지원 정보, [J. Chem. Inf. Model. 2011](https://pubs.acs.org/doi/abs/10.1021/ci200379p), [figshare 데이터셋](https://acs.figshare.com/articles/dataset/A_Collection_of_Robust_Organic_Synthesis_Reactions_for_i_In_Silico_i_Molecule_Design/2568199)). 널리 쓰이지만 **지원 정보 파일의 재배포 조건은 ACS 정책에 따르므로 확인 필요**(미확인). 로컬 개인 사용은 위험이 작다.
- **RDKit 자체 예제·기여 코드**의 반응 세트: BSD-3(RDKit 본체 기준, 미확인).
- **사용자 정의 규칙**: 사용자가 reaction SMARTS를 직접 넣는다. 이 경로는 라이선스 문제가 없고, 처음 구현으로 가장 안전하다.
- **권장**: (1) 사용자 정의 규칙 + 소수의 직접 작성한 기본 규칙(치환기 교체 등)으로 시작, (2) 공개 반응 세트 도입은 라이선스 확인 후 별도 결정.

### J.3 building block 라이브러리 후보

| 후보 | 조건 | 권장 |
|---|---|---|
| 사용자 제공 SDF | 없음 | **1순위.** 사용자가 쓰고 싶은 블록을 직접 넣는다 |
| Enamine building blocks 카탈로그 | 웹에서 SD 파일 배포(2026-09 기준 카탈로그 285만 건, in-stock 세트 별도)([Enamine building blocks](https://enamine.net/building-blocks/building-blocks-catalog)). **이용·재배포 조건은 사이트에서 확인해야 한다(미확인).** REAL Space(수백억 규모 가상 생성물)는 이 도구 범위를 크게 넘는다([REAL Space](https://enamine.net/compound-collections/real-compounds)) | 조건 확인 후 in-stock 소규모 세트만. 로컬 저장·비재배포 |
| ZINC 부분집합 | 무료 연구 사용, 조건은 사이트 확인 필요(미확인, [zinc.docking.org](https://zinc.docking.org/)) | 대안 |
| ChEMBL 유래 조각 | CC BY-SA 3.0 — 파생물 공개 시 동일조건 | 공개 계획이 있으면 주의 |

라이브러리는 **스냅샷 + 파일 해시 + 날짜**로 등록하고, 결과 객체에 어느 스냅샷의 어느 블록 ID를 썼는지 남긴다. 런타임 다운로드는 하지 않는다.

### J.4 규모 상한과 배제

- 열거 상한(기본 제안): 슬롯 4개, 라이브러리당 블록 5,000개, 한 실행의 열거 후보 2,000개, 필터 통과 후 도킹 200개. 상한을 넘으면 **실행 전에 거부하고** 어떻게 줄일지 알려 준다.
- 도킹 시간: 후보당 수십 초~수 분이므로 200개면 수십 분~수 시간이다. 비싼 계산 예약·승인 규칙을 그대로 적용하고, 진행 중 취소가 실제로 동작해야 한다(M13 Stop).
- **배제**: 수만 개 이상 열거, REAL Space류 초대규모 공간 탐색, 합성 경로 제안("이 경로로 합성 가능"), 수율·비용 예측, 특허 침해 판단.
- **표시 문구 고정**: "Vina 점수(kcal/mol, 스코어링 함수 값. 친화도가 아님)", "SA-score(계산 지표. 합성 가능성 판정이 아님)", "PAINS 일치(구조 경고. 활성 판정이 아님)".

## K. 단백질 공학 + 반응 지식 (효소 기질 결합 재설계)

### K.1 흐름

1. **입력**: 단백질 구조(+기질이 있는 복합체면 그대로, 없으면 사용자가 기질을 넣고 도킹으로 포즈를 만든다 — 어느 쪽인지 결과에 박는다), 사용자가 고른 UniProt accession.
2. **반응·촉매 지식 연결(M15)**: M-CSA에서 촉매 잔기, UniProt에서 active site·binding site·EC 주석, Rhea에서 반응 정보를 가져와 번호 대응으로 구조 잔기 7필드에 붙인다. 대응 실패는 `unmapped`로 보여 준다.
3. **금지 위치**: 촉매 잔기와 사용자가 지정한 보호 잔기는 **기본적으로 변이 후보에서 제외**한다. 해제하려면 명시적 확인을 받고, 그 사실을 계획과 보고서에 남긴다. 이것이 이 시나리오의 핵심 안전장치다.
4. **변이 후보 생성**: 기질 접촉 잔기(기하 접촉 또는 M11) ∪ 포켓 접촉 잔기(M12) 중 금지 위치를 뺀 집합 × 허용 아미노산. 선택적으로 ProteinMPNN 제안을 후보 목록에 추가(제안으로 표시).
5. **모델링**: PDBFixer로 변이 적용·누락 원자 보강 → OpenMM 제한 최소화(M7 경로). 결과는 "모델링된 구조"로 표시한다(측쇄 회전이성질체 탐색이 없다).
6. **평가**: 기질 포즈 재채점(Vina), 지정 잔기와의 접촉 수·거리, 매몰 SASA 변화, 모델 구조의 OpenMM 전위(구조가 물리적으로 터지지 않았는지 확인용).
7. **선택**: JEV-guided 또는 GA-guided(I절). 최종 선정은 사람.
8. **보고서**: 변이 집합, 금지 위치와 그 근거(M-CSA·UniProt 인용), 각 평가값의 엔진 이름·단위, 제안과 계산의 분리.

### K.2 정직한 이름과 배제

- 보고 가능: "Vina 재채점 점수(kcal/mol)", "기질 중원자 접촉 수", "매몰 SASA(Å²)", "OpenMM 전위(kJ/mol, 이 모델 구조 기준)", "ESM-2 로그우도"(도입 시), "M-CSA 촉매 잔기 주석(CC BY 4.0, 스냅샷 날짜)".
- **배제**: 활성·kcat·kM·특이성 개선 주장, ΔΔG·안정성·친화도 이름, "기질 결합이 좋아졌다"는 결론 문장, 서열이 다른 두 구조의 OpenMM 전위 차이를 효과로 제시하는 것, 반응 메커니즘이 유지된다는 주장(구조 모델링으로 확인할 수 없다).
- 화면 문구: "기질 결합 개선"이 아니라 "기질 접촉·점수 비교"로 둔다.

## E′. 단계 로드맵 (시나리오 반영 갱신 — E절을 대체한다)

### "완성"의 정의 (갱신)

> **완성 = 탭 네 개가 각자 제 일을 한다.** (1) 구조 분석 탭에서 구조를 열어 부위·상호작용·표면·공동을 로컬 계산으로 보고 논문용 그림을 낸다. (2) 지식 탭에서 그 부위가 계열 지식으로 무엇인지 잔기 단위로 확인한다. (3) 리간드 설계 탭에서 슬롯·building block·reaction rule로 후보를 열거하고 필터·도킹으로 점수 표를 낸다. (4) 단백질 공학 탭에서 촉매 잔기를 보호한 채 변이 후보를 만들고 모델링·평가한다. (5) (3)·(4)에서 JEV-guided와 GA-guided를 각각 파라미터를 바꿔 가며 예산·승인 안에서 돌린다. (6) 모든 수치가 handle·필드·단위로, 모든 인용이 출처·버전으로 역추적되는 보고서를 얻는다.

포함하지 않는 것(H-11 전체 + 다중 사용자·인증·공유, 외부 공개, 플러그인 SDK, MD·자유 에너지, 복합체 OpenMM, 무인 자율 실행, GUI 파이프라인 편집).

**순서 근거**: GA(M19)를 JEV 루프(M20)보다 앞에 둔다. GA는 외부 요청이 0건이고 재현 가능해서, 루프 구조·파라미터 편집·예산 가드를 **돈과 전송 없이** 먼저 검증할 수 있다. 그 위에 JEV를 붙이면 M20이 작아진다.

**병행·축소**:
- M15는 독립이므로 M13·M14와 병행 가능하다. B.10 시제품을 먼저 하면 지식 연결 가치를 가장 빨리 확인한다.
- 최소 경로(리간드 쪽만): M13 → M14 → M16 → M17 → M19. 5단계로 H-5·H-6·H-2(GA 버전)까지 온다. 이 경우 완성 정의에서 (4)와 JEV 부분을 제외하는 결정을 함께 해야 한다.
- 최소 경로(단백질 쪽만): M13 → M14 → M15 → M18 → M19.

## 부록 2: 시나리오 요구 반영분에서 불확실한 것

- Hartenfeller 2011 반응 SMARTS 지원 정보의 재배포 조건(ACS 정책)을 확인하지 못했다. 로컬 사용과 재배포는 다르다.
- Enamine building blocks SD 파일과 ZINC 부분집합의 이용·재배포 조건을 사이트에서 직접 확인하지 못했다.

- 도킹 후보당 실제 소요 시간은 이 환경(macOS arm64)에서 측정하지 않았다. J.4의 상한값은 측정 후 조정해야 한다.
- 현재 프런트엔드 화면을 탭 구조로 이관하는 비용은 코드를 읽지 않고 추정했다. M14 크기(M)는 실제 화면 구조를 본 뒤 다시 잡아야 한다.
