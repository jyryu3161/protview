## Fixed calculation

`openmm_protein_minimize` is a separate durable job protocol. It selects canonical standard protein residues from one `prepared_structure@1`, excludes all other prepared-model components, removes source protein H/D, builds explicit source-to-OpenMM atom and residue mappings, adds hydrogens at pH 7.0, and runs OpenMM's built-in `amber14-all.xml` + `implicit/gbn2.xml` on CPU with `Threads=1`, `NoCutoff`, no constraints, no periodic box, a 10 kJ/mol/nm tolerance, and a cap of 50 minimization iterations. Hydrogen construction explicitly uses the CPU platform after setting its default Threads property to 1 inside the isolated worker; the method record has separate hydrogen-platform properties. The request requires literal `selection_policy=protein_only` and `hydrogen_policy=rebuild_pH7`. Default timeout is 60 seconds and the accepted maximum is 120 seconds. The worker seeds Python and NumPy construction RNGs and records the seed; cross-version bitwise repeatability is not promised.

Preflight requires complete standard heavy templates, including terminal OXT, and rejects internal gaps where successive known label sequence numbers are not consecutive. Author numbers may be arbitrary, and insertion codes remain part of each full residue identity. Each adjacent peptide C–N distance must be between 1.1 and 1.7 Å before OpenMM may create standard bonds. This conservative support policy catches separated fragments and the tested missing 1UBQ residue 10; it is not a general biological structure-quality assessment. A chain without usable label numbering is still subject to the geometry check. No residue filling, heavy-atom repair, or terminal capping is performed.

Water removed by an earlier `prepare_structure` call is still listed from the linked original model as `water_removed_during_preparation`; water retained in the prepared model is listed as `water`. This prevents the default water-stripping choice from hiding source exclusions in the OpenMM preflight and report.

OpenMM distribution is **8.6.0** in the project `.venv`; its engine reports **8.6.0.dev-c6173db**. The built-in XML SHA-256 table recorded in each method result includes transitive includes:

The worker rechecks fixed settings, engine version, and all XML fingerprints before parameterization. Internal topology indices are explicitly mapped to full Gemmi model/auth/label/insertion-code residue references and atom names. The method preparation manifest records source heavy atoms, removed/added hydrogens, excluded components, selected protonation variants, disulfide bonds, source/final bonds, and atom/residue mappings. The scientific result stores exact pre/post potential energies and exact per-atom Å coordinates, construction seed, plus separate viewer mmCIF input/final objects and the actual immutable `openmm_system_xml@1` bytes. The report also records the seed. The System SHA-256 and the canonical topology SHA-256 are linked in the preparation, result, and report. The topology digest is SHA-256 of compact, sorted-key UTF-8 JSON with exactly `{"atoms": atom_mapping, "bonds": final_bonds}`; atom and bond array order is retained. The source prepared structure and old contact/report objects are immutable. A returned 50-iteration minimization is labeled `convergence_not_claimed`; no iteration count is fabricated.

The native potentials and `after − before` change have units **kJ/mol**. They are force-field/GBn2 method-specific, not REU, binding free energy, ΔΔG, affinity, experimental stability, or a cross-protein ranking. GBn2 is implicit solvent. Heavy-atom repair, terminal capping, modified polymers, unresolved alternate sites, arbitrary XML/platform/executable settings, and nonstandard residues are unsupported. Public 1HSG has a missing terminal OXT and is rejected before launch under this policy. If an unsupported template is discovered inside the launched engine attempt, the actual attempt remains charged and fails without an energy result.

The six force-field fingerprint keys are fixed for v1. The saved-evidence validator requires exactly those keys and lowercase 64-character hex digests; it validates recorded bytes and relationships without importing a currently installed OpenMM engine. Preflight checks the installed pinned engine and XML files before loading Amber templates. If OpenMM is absent or its fixed files differ, preflight and submission return the typed `openmm_unavailable` HTTP 412 response before reservation or launch.

## Execution and persistence

The existing `JobQueue` and POSIX guardian own approval, reservation, staging, HELLO/receipt/GO, STOP, process cleanup, terminal CAS, retries, and reconciliation. Submission and validated preflight do not reserve. The first real attempt raises a persisted `expensive_first_call` approval request; the UI has an explicit approval action. One attempt uses one durable expensive reservation. A completed result is published only after guardian output and cleanup checks. Scientific worker JSON, including the actual System XML, is capped at 64 MB on both sides of the guardian boundary. The same engine-free scientific bundle validator checks publication and saved result/report/coordinate reads against typed source, prepared, System, topology, mmCIF, coordinate, mapping, method, job, attempt, and report links. It checks the System's particle and bond topology and exact integer counts without initializing OpenMM for saved reads. These checks prove internal consistency and recorded provenance; they cannot cryptographically prove that arbitrary mutually forged energies came from physical execution. The fixed worker, actual production route, and independent native recomputation provide separate numerical evidence. Repeated submissions of the same semantic input/settings return the existing job, including a failed job, so recovery uses the bounded retry path. The API exposes preflight, submit, start, status, cancel, retry, result, minimized bytes, method-report creation and download.

New owned launches use the [M7 raw process identity correction](M7_PROCESS_IDENTITY.md). The shared adapter is limited to pinned psutil **7.2.2** on Darwin or Linux. It records exact `psutil_raw_start_v1` kind, platform, version and raw start value in the receipt, authenticated HELLO/launch record, STARTED observation and captured cleanup cohort. Public wall-clock `create_time()` cannot authorize a signal. Capability and preflight show the specific `process_identity_unavailable` limitation when the adapter is unavailable, and the queue checks it again before reservation; a mismatch or missing private psutil path fails closed. PID, UID, PGID, session, private nonce, receipt/channel equality, fresh-session anchor, direct-child reap and bounded cleanup remain required. After owner loss, an old active public-time receipt or event does not gain raw identity authority: an independently verified empty group may reconcile, while a live or indeterminate group remains cleanup pending. Completed historical events and reports remain immutable.

Before the first protocol potential evaluation, worker main atomically writes and fsyncs a complete, at most 64 MB `preparation.json` in its private attempt directory, then fsyncs that directory. It contains the actual hydrogenated input CIF and full-precision coordinates, source/selection digest, method and seed, atom/residue/hydrogen/variant/bond mappings, and serialized System/hash. Hydrogen placement has its own internal OpenMM optimization; this checkpoint boundary refers to the subsequent named potential/minimization protocol. After verified group cleanup, the parent validates a complete checkpoint with the shared engine-free preparation validator, stores typed preparation/System/input-coordinate objects, and appends one attempt-bound `job_preparation_recorded` event. A failed, cancelled, or interrupted attempt may therefore expose a preparation handle while its `output_handles` remain empty. Missing or malformed checkpoints do not produce preparation handles or successful energy. Completed results reuse exactly those three objects; recovery can restore them from events after attempt files, uploads and indices are gone. Public job DTOs include validated same-run `input_handles` plus optional `preparation_handle` and `preparation_attempt_id` so the strict frontend selection guard can match submission, list, detail, start, cancel and retry responses.
