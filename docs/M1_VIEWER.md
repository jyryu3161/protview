# M1 viewer and frontend integration

## Component contract

`frontend/src/components/MolstarViewer.tsx` is the reusable canvas-only Mol* component. `source` is `{handle, text, format, modelIndex?}`; `text` must be decoded bytes from a local upload or `GET /runs/{rid}/structures/bytes`, never a remote URL. The production page obtains the bytes from that endpoint and passes the selected one-model structure to the component. The component accepts `representation: cartoon | ball-and-stick | surface`, optional `highlight: ResidueRef`, and reports 3D selections through `onSelect`.

`ResidueRef` uses `model_number`, `chain_auth`, optional `chain_label`, `seq_auth`, optional `seq_label`, `icode`, and `resname`. The focus query combines the available author and label fields plus insertion code, and checks the loaded model number. A separate ligand ball-and-stick representation is kept visible over cartoon and surface modes. The plugin is created inside a per-mount DOM node, and disposed on source change or unmount, including React Strict Mode's repeated mount cycle. Loading, empty and error states are visible.

The component reports loading, ready and error for its exact `ViewerSource`, and reports whether a requested residue was found before the page displays a focus legend. A changed inspection context remounts the viewer and clears its old selection. A model or residue mismatch leaves no success legend.

The canvas background reads the active local design token and updates when the dark/light theme changes.

The plugin uses the raw-data builder, not Mol* download helpers. It registers no UI actions, allowlists only local interaction/camera/structure behaviors (omitting database mapping), and disables volume streaming and state servers. No remote samples, font CDN, or telemetry are required. The Next scripts set `NEXT_TELEMETRY_DISABLED=1`, dev/start bind to `127.0.0.1`, and the `/api` rewrite targets `127.0.0.1:8000`.

## Production route

`frontend/app/page.tsx` uses `docs/M1_API.md` for run creation/list/reopen, raw local upload, explicit model index, supported deterministic preparation settings, exact ligand instance selection, geometric contact calculation, structure bytes, residue identities, handle metadata, events, capabilities, budget and paginated interaction rows. Its timeline is built from actual call events. Clicking a measured row focuses its residue. Empty contact sets show `scientific_null`; unavailable capabilities show the server's reasons. Jobs, energy, reports, remote models, online mode and dry-run controls are absent from the production route. `/gallery` is explicitly marked as design fixtures.

The Inspector binds its metadata and paginated measurement rows to one effective result. Reopen defaults to the newest successful scientific output event, which may be a load, preparation or interaction. A load or preparation result has no borrowed contact table. A selected timeline step inspects that step; “최신 구조로 돌아가기” explicitly selects the latest pipeline and attaches only its input-linked interaction, if any. Every row request is keyed by run, interaction handle and page offset, so switching results, pages or runs cannot show another object's rows. Row loading, failed retrieval and a successful empty `null_result` are separate states. The empty-result message appears only after a successful materialization whose metadata identifies the selected interaction object and declares zero rows and `null_result=true`; a failed request shows an error and one manual retry control. The Inspector wraps long metadata and gives the contact table its own horizontal scroll area at the 360 px panel width. Run switching sets the workflow busy until reopen completes, disabling upload and tool mutation during the transition.

Every effective interaction, including the default newest result, resolves its immutable input `prepared_structure` solely from the selected interaction object's validated `summary.structure`. It verifies that input handle and kind through `/objects/meta`, then loads that handle's local bytes and residue list. A load or preparation result similarly shows its own structure; only when no result structure is selected does the viewer fall back to the latest pipeline structure. One request path handles metadata, bytes, residues, readiness, focus and failure for all view intents. Viewer readiness and row focus are keyed to the run, input handle, view intent and inspection revision, so stale requests or an earlier Mol* canvas cannot make a row actionable. The models rail and selection legend describe the displayed structure after it renders; fetch or render failure is visible and disables focus, with a retry action that reuses the bound input request. The selection legend follows a successful Mol* residue lookup.

Latest pipeline handles are derived by input lineage: the newest successful load, the newest successful preparation whose original `tool_called.args.structure` equals that load handle, then the newest successful interaction whose original input equals that preparation handle. Cached success events use their original call ID and original call arguments. Missing call evidence does not establish lineage; the pipeline leaves that successor absent. This keeps the pipeline ligand choices and tool arguments separate from the displayed result. If a displayed result's input differs from the latest prepared structure, the rail says so and disables mutation. Selecting a historical step also disables mutation. Returning to the latest pipeline explicitly selects its linked result or shows its structure without a foreign contact table; it does not issue a scientific command.

An interrupted run with an upload but no `load_structure` call can reopen its upload ID from the event log. The upload event does not retain `model_numbers`, so this recovery path asks for an explicit zero-based model index rather than displaying invented model metadata; the backend validates it.
