# M5 offline inspections and reports — implementation handoff

Implementation owner: GPT-6 Sol. Architecture and final scientific review: GPT-6 Astra. This file describes implemented behavior; the phase index and Astra review determine gate status.

## Public API

- `POST /runs/{rid}/inspect_complex` takes the strict `InspectionRequest` schema: exactly one same-run `upload_id` or `input_handle`; an upload requires explicit zero-based `model_index`; preparation policies (`altloc`, `waters`, `hydrogens`, `missing_residues`, `symmetry_mates`); optional full ligand residue reference; `cutoff_A`; and nonempty unique geometric `types`. Extra fields are rejected. The HTTP upload branch reuses verified run upload bytes and SHA checks with `O_NOFOLLOW`. An already recorded load step can resume after the upload file is removed. The response status is `complete`, `needs_selection`, `no_ligand`, `checkpoint`, `cancelled`, or `failed`, with actual recorded output handles and real choices where relevant.
- `POST /runs/{rid}/reports` accepts exactly one selected `interaction_handle` and optional matching `prepared_handle`. It returns a saved `report_manifest@1` handle, its `report_markdown@1` handle, JSON manifest and Markdown. `GET /runs/{rid}/reports` lists saved references. `GET /runs/{rid}/reports/selected?handle=...` reopens exact artifact bytes. `GET /runs/{rid}/reports/download?handle=...&format=markdown|json` uses server-generated safe attachment names. No endpoint accepts paths, URLs, arbitrary YAML/tool/executable names, output paths, or freeform explanation text.
- The Inspector enables report creation for the selected successful interaction, including a historic selection. Saved reports reopen automatically for that selection, with local preview and Markdown/JSON downloads. Responses are keyed to run and interaction handle and discarded after selection changes. Preview is React text in a `<pre>`; it does not parse HTML or fetch embedded images.

## Internal contracts

`mw.workflows.inspect_complex` is a finite `Run.call` driver. Its stable workflow ID hashes `inspect_complex@1`, run ID and normalized request, including the upload SHA and format. `workflow_started` records the normalized request and `finite_rules` branch. `workflow_step_completed` records step, child call/observation ID, original call ID, exact output handle and null marker. Resume verifies those explicit step records and executes only missing steps; it never scans for a global latest output. A separate confined workflow lock serializes progress without nesting the nonreentrant run owner. The fixed driver uses `load_structure`, `prepare_structure`, exact candidate resolution and `compute_interactions`. A single ligand may be selected automatically. The YAML file documents the supported defaults and is not HTTP executable input. Existing prepared handles must match requested policy values.

Step progress now also records the normalized tool arguments, semantic call key, workflow proposal ID, child event sequence and physical source-success sequence. Resume requires one matching autonomous branch proposal/observation, the requested workflow/version/step/tool, ordered child events, and a matching physical source call and output. A cache step must have its own workflow cache observation with the requested arguments; its physical source call may be an earlier human call. Loaded upload bytes/hash/format/model, preparation input/model/policies, and interaction structure/ligand/cutoff/types/method are checked against the recorded objects. Missing, foreign, duplicated or ambiguous progress raises bounded `run_corrupt` at the HTTP boundary before subsequent tool calls. This check accepts normal concurrent human cache activity and events-only reconstruction.

Failed inspections retain completed `outputs`, `failed_step`, `failed_tool` and `causal` (`event_seq`, `call_id`, `proposal_id`, each null when absent). A `failed` response carries `failure` with classification, message, optional fix and bounded detail; a `checkpoint` carries either `approval` (gate/tool/pending args/reason) or `loop_stop` (reason/detail); a `cancelled` response carries `cancellation` status/reason. Runtime checkpoint and failure events provide the causal sequence, while no-call cases leave `call_id` null. Detail and fix arguments are restricted to relevant, bounded fields. No retry or approval action is started by the workflow response. `ApprovalRequired` retains pending arguments separately from Python's exception message tuple.

`mw.reports.Claim` is strict and closed to seven local statement IDs: `contact_distance`, `contact_count`, `contacting_residue_count`, `minimum_distance`, `type_count`, `cutoff`, `selected_model`. Each claim binds kind/schema/full SHA handle, allowlisted field path, exact value, rendered value, unit, quantity, rounding, approved operation, selected prepared/interaction/ligand subject, and full row identity plus an index-bound row fingerprint where applicable. `validate_claim` resolves the actual store object and recomputes row count, collision-safe distinct residues, minimum and type counts. Distances use `Decimal(str(value))` with `ROUND_HALF_UP` to exactly two decimal places; JSON retains full finite numeric values. Counts are exact integers. The legacy number-bag verifier remains only in `mw.llm.verifier` and is unused by product reports. `validate_statement` rejects unsupported predicates even when number-free.

All claim paths, including `selected_model`, require `prepared_structure@1`, `interaction_set@1`, `preparation_manifest@1`, `structure_selection@2` and `structure_source@1` at their respective links. They check prepared/interaction/model/input/source cross-links before treating content as evidence. Paired malformed subject links cannot convert an unrelated kind or unsupported schema into a selected model. Existing field, row, unit, exact-value, rounding, closed-language and privacy validation remain in force; valid report content and render bytes are unchanged.

`build_inspection_report` resolves one successful interaction result and its prepared structure, preparation manifest, selected source/model/ligand, all rows, method and child call provenance. It validates all generated claims. The immutable manifest contains the complete table, claims, counts, minimum or null, preparation/method, the four actual optional energy capabilities, limitations and a sequence-bound snapshot of budget, decisions and job context. The Markdown is separately stored as exact UTF-8 bytes through object events. Saved artifact reads neither rerun science nor issue external requests. Reports do not import goal/context, environment, credentials or arbitrary metadata. A geometric empty result is a complete report with zero pairs/residues and an undefined minimum; absent or corrupt evidence is an error. Optional energy protocols remain unavailable with no energy value or ranking.
